# ADR-0089: PKM Git は自動で同期し、Git のコミットは共有の区切りだけで作る

- 状態: 承認
- 日付: 2026-11-08

## 背景

[Issue #89](https://github.com/yamayu-i/pkm-kit/issues/89)。同期の再設計（[Issue #86](https://github.com/yamayu-i/pkm-kit/issues/86)）の第 2 段階。第 1 段階（[Issue #87](https://github.com/yamayu-i/pkm-kit/issues/87)）で、未 push のコミットがあっても fetch が差分だけを取るようになった。

使う人が求めていること（#86）:

- pull と push、コミットメッセージを意識せずに、端末間で同期できる
- 使い続けても Git、特に fetch と clone が重くならない（優先順位 1）
- どこまで共有できたかが分かる

今の振る舞いと困りごと:

- pull と push を手で実行する（コマンドとリボン）。押し忘れると共有されない
- ステータスバーの `Git: ✓` は「検出したコンフリクトがない」だけ。未 push の変更があっても ✓ になる
- push は、リモートが先に進んでいるとモーダルを出して止まる。pull してから push し直す必要がある
- `moveTo`（取り込んだ版を作業ツリーに書く）の途中でアプリが終わると、ブランチは元のままで作業ファイルだけが書きかけになる。次の snapshot が、書きかけのリモートの内容をローカルの変更としてコミットする。次のマージで両側が同じ変更になるので内容は失われないが、不要なコミットが残る。スマホではアプリの終了が普通に起きるので、自動の同期にすると頻度が上がる
- `moveTo` はブランチを `force` で書き換える。snapshot の後に PC の Git CLI（Claude Code など）がコミットすると、そのコミットがブランチから外れる（オブジェクトは残る）

再設計案は、細かな版を端末内の専用のストアに保存し、Git には共有の区切りだけを残す方式を勧めていた。

## 決定

### 1. Git のコミットは同期の区切りで作る

- snapshot（未コミットの変更をまとめてコミットし、`updated` を付ける。ADR-0028）は、**同期でリモートに届いたとき**と、**「この版を残す」を実行したとき**だけ行う。保存のたびやタイマーのたびにはコミットしない
- オフラインでは、自動の同期はコミットしない。編集は作業ファイルにあり、次に届いたときの 1 回の同期で 1 つの snapshot にまとまる
- 1 回の同期が必ず 1 コミットになるとはしない。分岐していれば、snapshot とマージコミットの 2 つになる。`push` が拒否されたまま終わった snapshot は、そのまま残す（書き換えない。下の 3）
- PC の Git CLI のコミットや、他の端末から受け取ったコミットは書き換えない（amend しない）
- `updated` の付与の規則（ADR-0028）は変えない。付与は snapshot のときなので、同期の区切りのたびに付く。自動保存のたびには付かない

### 2. 端末内の細かな復元は Obsidian の「ファイル回復」に任せる

- コアプラグイン「ファイル回復」（`file-recovery`）を有効にする（`.kit/obsidian-required.json` の `core-plugins.json` に足し、移行で子の設定を直す）。ノートの以前の版を端末内に一定の間隔で保存し、期間が過ぎたら消す。間隔と期間はファイル回復の設定で決まり、pkm-git は持たない
- pkm-git は端末内の版を持たない。共有前の細かな途中版は、その端末のファイル回復にだけある（端末を失えば失われる）
- ファイル回復が対象にしないファイル（アセットなど）の、共有の区切りより細かな版は持たない。必要になったら、何が足りないかを確かめてから別の ADR で足す
- 実装の最初に、ファイル回復がスマホで使えるか、対象のファイルの種類、保存の間隔を実機で確かめる。前提が崩れたら、実装を止めてこの ADR を直す

### 3. 同期を 1 つの処理にし、直列のキューで実行する

新しいコマンド「今すぐ同期」（`pkm-git:sync`）と、エンジンの `sync()`。1 回の同期は次の順に進む。

1. 前回の取り込みが途中で終わっていたら、先に復旧する（下の 5）
2. 開いているエディタを保存する
3. fetch する。つながらなければ「オフライン」、認証に失敗したら「接続を確認」として終わる。コミットしない
4. snapshot する（変更があればコミット）
5. リモートと比べる。最新・先行・fast-forward・マージは今の pull と同じ。マージで両側の変更が重なったら、今と同じく止まらずにマーカーか別名で残してマージコミットする
6. ローカルが先行していれば push する。拒否されたら（他の端末が先に push した）3 に戻る。1 回の同期で 3 回まで。それでも拒否されたら「共有待ち」で終え、次のきっかけでやり直す

- きっかけ: 前景で一定の間隔（設定。既定 5 分。0 で止める）、再フォーカス（`visibilitychange` で表示に戻ったとき、Obsidian のウィンドウのフォーカス。前回から 1 分以上たっていれば）、起動（レイアウトの準備ができた後）、「今すぐ同期」、「この版を残す」
- 一定の間隔は、画面が表示されているときだけ数える。バックグラウンドでの実行や、アプリの終了時の処理を前提にしない
- 実行中に別のきっかけが来たら、終わった後に 1 回だけ実行する（何回来ても 1 回にまとめる）。今の「別の処理を実行中です」の Notice は、手で実行したときだけ出す
- 自動の同期が続けて失敗したら（オフライン・接続の確認・エラー）、次の自動の実行までの間隔を倍にする（上限 30 分）。手で実行したときは待たない。成功したら戻す
- 同期の間も編集してよい。取り込みの直前に作業ファイルを確かめる今の仕組み（`WorktreeChangedError`）で、snapshot の後の編集を上書きしない。自動の同期でこれが起きたら Notice を出さずに、次のきっかけでやり直す（その編集は次の snapshot に入る）
- ブランチを書き換える直前に、ブランチがこの同期の始めの値のままかを確かめる。変わっていたら（PC の Git CLI がコミットしたなど）書き換えずに終え、次のきっかけでやり直す。完全には防げない（確かめてから書くまでの間は残る）が、外のコミットをブランチから外す窓を小さくする
- `pull` と `push` のコマンドは残す。どちらも同じキューで実行する。`push` は、リモートが先に進んでいてもモーダルで止めず、`sync` と同じく取り込んでから送る。pkm-ribbon のボタンは pull と push の 2 つを、「同期」の 1 つにする

### 4. 「この版を残す」

- コマンド「この版を残す」（`pkm-git:keep-version`）。名前を任意で入力する（空でよい）。名前はコミットメッセージに入る（`vault: keep <名前> (<端末>)`。改行は空白にし、長さを切る）
- オンラインでもオフラインでも、すぐに snapshot する（変更がなければコミットせず、そう知らせる）。その後に同期する。オフラインなら、そのコミットは次に届いた同期で送る
- コミットなので、ファイル回復の期間が過ぎても消えない

### 5. 取り込みの途中で落ちたときの復旧

- `moveTo` は、作業ファイルを書く前に `.git/pkm-git/apply.json`（`schemaVersion`、ブランチ、取り込む前の版 `from`、取り込む版 `to`）を書き、ブランチを進めた後に消す。`.git` の中なので、コミットにも同期にも入らない
- 同期の始めにこのファイルがあれば:
  - ブランチが `to` なら、ファイルを消すだけ（終わっていた）
  - ブランチが `from` なら、`from` と `to` で違うパスを調べる。作業ファイルが `from` か `to` の内容のパスは `to` に揃える。すべて揃ったらブランチを `to` に進め、ファイルを消す。どちらでもない内容のパス（落ちた後に編集された）が 1 つでもあれば、ブランチを進めずにファイルを消す。この場合は今と同じく、次の snapshot とマージで取り込む（内容は失わない。不要なコミットが 1 つ残る）
  - ブランチがどちらでもなければ、ファイルを消すだけ
  - 読めない、または知らない `schemaVersion` なら、何もせずに同期を止めて知らせる（ファイルは消さない）

### 6. 状態の表示

ステータスバーに、共有の状態と、確認が必要な件数を分けて出す。

| 共有の状態 | 意味 |
|---|---|
| `Git: 共有済み` | 最後の同期の始めまでの編集を送った。その後に編集していない |
| `Git: 共有待ち` | 送っていない編集かコミットがある。オフラインのタイマーの後もこれ |
| `Git: 同期中…` | 同期を実行している |
| `Git: オフライン` | 最後の同期でリモートにつながらなかった（共有待ちの編集がある場合も、こちらを出す） |
| `Git: 接続を確認` | 認証・接続先の設定・トークンの問題 |
| `Git: 同期できません` | それ以外のエラー（メッセージは Notice とコンソールに出す） |

- 確認が必要な件数は、今のコンフリクトの一覧の件数を ` · ⚠ N` として後ろに付ける。クリックすると今と同じく一覧を開く
- 「共有待ち」は、Vault の作成・変更・削除・改名のイベントで分かる編集と、ブランチがリモートの追跡ブランチより先にあることから決める。同期の始めより後のイベントは、その同期の後も「共有待ち」に残す。snapshot が `updated` を書いたイベントは編集として数えない（書いた内容と同じなら無視する）。起動直後は、起動時の同期が終わるまで「同期中…」とし、推測で「共有済み」を出さない
- 「この端末に保存済み」は出さない。保存は Obsidian が行い、端末内の版はファイル回復が持つので、pkm-git は確かめていないことを表示しない
- コンフリクトの一覧の再検索（Vault の全ノートを読む）は、起動時と、同期で作業ファイルが変わったときだけにする。5 分ごとの同期で、何も取り込まなかったときは読み直さない
- 通知: 自動の同期は、成功・オフラインでは Notice を出さない。新しくコンフリクトができたら Notice を 1 回出す（モーダルは出さない。手で実行したときは今と同じくモーダル）。接続を確認の Notice は、起動から 1 回だけ出す

### 7. 失敗の扱い: Git の CLI がなくても先へ進めるようにする

目標は、使う人が Git の CLI を開かなくてよいこと。通信や端末の失敗そのものは防げない（オフライン、サーバーの障害、容量不足）ので、どの失敗でも「データを失わない」「次の同期が同じところから安全にやり直せる」「何が起きたかが Obsidian の中で分かる」を満たす。

- **想定できる失敗は、エラーではなく状態として扱う**: オフライン、接続を確認、他の端末との競合（push の拒否）、同期中の編集（`WorktreeChangedError`）、外からのコミット（ブランチが変わっていた）、途中で落ちた取り込み。どれも自動で次のきっかけに進み、使う人の操作を要らない
- **想定外のエラーでも、Git の状態を壊さない順で止まる**: 記録を書いてから作業ファイルを書き、ブランチは最後に進める（上の 3・5）。止まった後の次の同期は、そのまま最初からやり直せる
- **想定外のエラーは記録に残し（下の 8）、記録から再現テストを足して、想定できる失敗に移していく**。「同期できません」が出たら、それは直す対象の不具合として扱う
- 第 3 段階以降で、CLI でしかできない回復（ほかの端末の版に戻す、壊れた状態からの復旧）を Obsidian のコマンドに置き換えていく

### 8. 同期の記録（エラーのログ）

- 失敗と、自動で回復した出来事を、端末ごとに `.git/pkm-git/log.jsonl` に 1 行 1 件で残す。`.git` の中なので、コミットにも同期にも入らず、同期が壊れていても書ける
- 残すもの:
  - `error`: 想定外のエラー（「同期できません」）、取り込みの記録が読めない
  - `warn`: push の拒否が 3 回続いた、取り込みの途中からの復旧（揃えたか、今の振る舞いに戻したか）、外からのコミットで書き換えを見送った、同期中の編集でやり直した、接続を確認（状態が変わったときだけ）、オフライン（オンラインから変わったときだけ。毎回は残さない）
- 1 件の項目: `schemaVersion`、時刻（秒までの ISO 8601、オフセット付き）、`level`、きっかけ（`interval` / `focus` / `startup` / `manual` / `keep` / `pull` / `push`）、工程（`recover` / `fetch` / `snapshot` / `merge` / `moveTo` / `push` など）、エラーの種類（クラス名、isomorphic-git の `code`）、メッセージとスタックの先頭（`redactSecrets` を通す）、そのときのブランチ・ローカル・リモートのコミット、試行の回数、関わるパス（20 件まで）、プラグインのバージョン、PC かモバイルか
- 残さないもの: トークン、Authorization ヘッダー、URL の認証情報、ノートの本文
- 大きさ: 256 KiB を超えたら `log.1.jsonl` に移して新しく始める（古い `log.1.jsonl` は消す）。2 つで 512 KiB まで
- 記録の書き込みに失敗しても、同期の結果を変えない（例外を外に出さない）
- 見る方法: コマンド「同期の記録を見る」で、新しい順にモーダルに出す。モーダルから記録をクリップボードにコピーできる（Issue やエスカレーションに貼るとき用。パスが入るので、公開する前に確かめるよう添える）。PC では Claude Code がファイルを直接読める

## 理由

- **fetch と clone を重くしないため**: 共有の履歴に入るのは同期の区切りだけになる。オフラインで何回編集しても、タイマーが何回動いても、届いたときの 1 回の snapshot にまとまる。保存のたびに版を作る方式より、送る量も、全端末の clone が取得する量も増えない
- **端末内の版を自前で持たない**: 再設計案の専用のストアは、容量の上限、保持の期間、保護する版の判定、モバイルでの保存の API、ストアを Git に入れない配置を、すべて作って検証する必要がある。Obsidian のファイル回復は、ノートについてそれを既に持ち、スマホと PC の両方で使える（実装の最初に確かめる）。足りない部分（アセットなど）が実際に問題になってから足す
- **同期を 1 つにする**: pull と push を別々に押す理由が使う人にはない。fetch を 1 回にでき、push のモーダルで止まることもなくなる。直列のキューにすれば、タイマー・再フォーカス・手動が重なっても、Git の操作が同時に走らない
- **オフラインでコミットしない**: 共有待ちの編集は作業ファイルにあり、オフラインでコミットしても守れる範囲は増えない（同じ端末にあるだけ）。コミットを分けると、届いたときに中間の版を全部送り、履歴に残る
- **記録を `.git` の中に残す**: 同期が壊れていても書け、履歴を増やさない。モバイルでもコマンドで見られるので、CLI もコンソールも要らない。想定外のエラーを再現テストに変えるための材料になる
- **途中で落ちたときの復旧を今入れる**: 自動の同期では、スマホでアプリを閉じたときに取り込みの途中である頻度が上がる。内容は今でも失われないが、不要なコミットと、作業ファイルが書きかけのまま「共有待ち」に見える状態を減らす。判断できないときは今の振る舞い（snapshot とマージ）に戻すので、復旧が新しい消失の経路にならない

## 却下した案

- **端末内の専用のストアに細かな版を保存する**（再設計案の第一推奨）: 上の理由。ファイル回復で足りないことが確かめられたら、別の ADR で検討する
- **自動保存のたびに Git のコミットを作り、ローカルだけの ref に積む**: isomorphic-git には gc がなく、期限が切れた版のオブジェクトが `.git` に溜まり続ける。保存のたびに変更の探索（`statusMatrix`）が走る
- **未 push の snapshot を amend し続け、区切りで確定する**: 送る履歴は減るが、amend のたびにローカルのオブジェクトが溜まる（同じく gc がない）。プラグインが作った未送信のコミットかどうかを、再起動・CLI のコミット・push の応答の喪失をまたいで判定する仕組みが要る。区切りでしかコミットしないなら、amend で減らせるものがない
- **タイマーのたびにコミットし、届いたときにまとめて送る**: オフラインの間に中間の版が溜まり、すべて共有の履歴に残る
- **バックグラウンドやアプリの終了時に同期する**: モバイルでは届く保証がない。前景のきっかけと、次の起動での復旧に頼る
- **同期の間は編集を止める**: 通信の間、書けなくなる。今の取り込み直前の確認で、編集を上書きしない
- **「この端末に保存済み」を出す**: pkm-git は確かめていない（上の 6）
- **同期の記録を Vault に置いて同期する**（`worklog/<端末名>/` と同じ形）: ほかの端末の記録を PC で読めるが、記録が書かれるたびに同期する変更が増え、失敗の記録そのものが、調べたい同期と履歴に入る。同期が壊れている間は届かない。必要なら、コマンドでコピーして渡す
- **コンソールにだけ出す**: モバイルでは見られず、再起動で消える

## 影響

- `src/git/engine.ts` に `sync()`、`keepVersion()`、取り込みの記録と復旧、ブランチを書く前の確認を足す。`pull()` と `push()` は `sync()` の一部を使う形に整理する。`src/main.ts` にキュー、きっかけ、状態の表示、コマンド（同期、この版を残す、同期の記録を見る）を足す。同期の記録は `src/git/sync-log.ts` に分ける。設定に自動の同期の間隔を足す。`src/git/`・`src/obsidian/` を変えるので、セキュリティチェックの対象
- pkm-ribbon のボタンを pull と push から「同期」の 1 つにする
- `.kit/obsidian-required.json` の `core-plugins.json` に `"file-recovery": true` を足す。子の `.obsidian/core-plugins.json` を直す移行（番号 0089）を付ける
- 既存の Vault でも、更新すると 5 分ごとの自動の同期が始まる。止めたい端末は設定で 0 にする。`.kit/changes/` に書く
- 新しい依存はない
- 文書: `plugin-development.md` の pull / push の節、プロダクトの [PKM Git](../../../harness/docs/product/surfaces/git-sync.md)・[同期と snapshot](../../../harness/docs/product/concepts/sync-snapshot.md)・[端末を持ち替えても、同じ Vault で続ける](../../../harness/docs/product/jobs/sync-devices.md) を、自動の同期に合わせて直す
- 受入テスト（#86 の番号）: L1（オフラインで編集とタイマー → コミットが増えない）、L3（アセットを開く・コピーするだけ → 変更が出ない）、U1（`updated` だけの変更・受け取った変更・push の再試行で付与し直さない）、U2（同じ秒・同じサイズの編集、CLI のコミット）、S1 の一部（`moveTo` の途中で落ちる → 復旧するか、今の振る舞いに戻る）、S3（同期中の編集・手動・再フォーカスが重なる → 直列に実行し、後の編集を共有済みにしない）、S4（2 台が同時に push → 3 回で止まり、force push しない）。本物の git http-backend を相手にする
- 同期の記録は端末に最大 512 KiB を使う
- 第 3 段階（衝突の永続モデル）は、この同期の順の 5 にマージの記録を足す形で入れる
