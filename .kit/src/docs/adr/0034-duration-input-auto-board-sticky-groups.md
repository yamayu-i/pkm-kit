# ADR-0034: estimated の単位入力と 1d = 24h、今日の予定の自動のボード入り、カードの置き場所の記憶

- 状態: 承認（ADR-0012 の estimated の入力と換算、ADR-0009 / ADR-0014 の DailyTaskView の「今日の予定」の段階、ADR-0014 のカードの置き場所を一部置換）
- 日付: 2026-11-06

## 背景

- estimated を自由に入れる欄は日数（`0.5` / `0.5d`）しか読めなかった。`30m` や `2h` と書けず、routine を作るフォームは分の数値だけで、書き方がそろっていなかった
- 表記は 8h = 1d で換算していた（ADR-0012）。`1d` が 24 時間ではないことが画面から分からず、実績の `1d2h` が何時間なのかすぐに読めなかった
- DailyTaskView の「今日の予定」の段階では、今日が実行日の issue を手でボードへ移していた。実行日を今日にした時点で今日やると決めているので、二度手間になっていた
- カードをグループへ移しても、その日のボードにしか残らなかった。同じ issue や routine を翌日もボードに載せると、毎日、未分類から移し直していた

## 決定

### estimated の入力（m / h / d）

- 入力欄は `1m` / `2h` / `1d` の単位付きで読む。小数（`0.5d`、`1.5h`）、組み合わせ（`2d3h33m`、`1h 30m`）、大文字も読む。表示の表記（`formatMinutes`）をそのまま入れ直せる
- 単位のない数字だけなら分として読む（保存の単位、MCP の `estimated` と同じ）
- 読めないもの、同じ単位が 2 回あるもの（`1h1h`）、単位のない数字が混ざるもの（`1h 30`）、0 以下は受け付けない
- 対象は、issue / routine の estimated のメニューの「入力…」と、routine を作るフォーム。プリセット（15m〜8h）はそのまま
- 保存はこれまでどおり分の数値

### 1d = 24h

- 表記の換算を 60m = 1h、24h = 1d にする。データは分なので移行はない。変わるのは表示だけ（480 分は `1d` から `8h` になる）

### 今日の予定を自動でボードに載せる

- DailyTaskView を開いているあいだ、今日が実行日で active な issue のうち、まだ今日のボードに載っていないものを、ボードの操作ログの `add` で自動で載せる。前回のボードを自動で締めるのと同じく、View が書く
- その日にボードから外した issue（その日の最後の add / remove が remove のもの）は自動では載せ直さない。手で載せ直せば、外したことは消える
- 段階は 期限切れ → 前回のボード → 期限が近い → ボード の 4 つにする。「今日の予定」の段階と、そこにあった「Move to Task Board」「すべてボードへ」はなくす
- 自動で載せるのは今日のボードだけ。過去のボードは変えない
- 左サイドバーの Daily の件数と MCP の `scheduledNotOnBoard` は、その日に外した issue を数えない
- 外したことは状態（`BoardState`）ではなく、読み込み時に操作ログから求めて `DailyBoard.removed` に置く

### カードの置き場所を覚える

- カードの置き場所は、その日に移した場所 → **前に置いた場所** → 既定（routine の `group`）→ 未分類 の順に決める
- 前に置いた場所は、そのボードの日付までの、ボードの操作ログの `place`（と既存の frontmatter の `board.groups`）のうち最後のもの。並べる順は、ボードの日付 → 操作の時刻。最後に未分類へ移したなら未分類にする（routine の `group` には戻らない）
- issue と routine の両方に効く。routine の `group` は、一度も移していないときの置き場所になる
- 今はないグループを覚えていたら、これまでどおり未分類に出す
- MCP の `get_board` のグループも同じ順で決める

## 理由

- 単位付きの入力は、表示の表記と同じ書き方で入れられる。単位のない数字を分とするのは、保存の単位と MCP にそろえるため
- 24h = 1d は、`d` を見た人がふつうに思う長さ。見積もりの「1 日分の作業」は `8h` と書けば足りる
- 実行日を今日にすることが、今日やると決めることになる。自動で載せても、外したものを載せ直さなければ、手で決めたことは崩れない
- 置き場所をログから求めると、ファイルに書くものが増えない。issue のファイルを移すたびに変えずに済むので、`updated` やコミットが増えない。issue と routine を同じ仕組みで扱える

## 却下した案

- **単位のない数字を日数として読む（これまでどおり）**: routine のフォーム（分）や MCP と食い違う。日数は `0.5d` と書けば済む
- **ログに書かず、今日が実行日の issue を、載っているものとして扱う（routine と同じ）**: 過去のボードの中身が、後から実行日を変えると変わってしまう。ボードの記録として残らない
- **外したことを `BoardState` に入れる**: 既存のデイリーノートの frontmatter の `board` や、状態を比べるテストまで形が変わる。自動で載せるかどうかだけに使うので、読み込み時に求めれば足りる
- **issue の frontmatter に `group` を足し、移すたびに書き換える**: 人も LLM も読めるが、カードを移すたびにノートが変わり、`updated` とコミットが増える。テンプレートとスキーマも変える必要がある

## 影響

- vault-task の `main.js`、`.kit/bin/` の CLI（MCP）が変わる。移行はない
- 子への影響: 既存の estimated の表示が変わる（`1d` と出ていたものは `8h`）。Daily を開くと、今日が実行日の issue がボードに載る
