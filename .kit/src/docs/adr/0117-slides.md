# ADR-0117: スライドを slide/ に HTML で作り、共通の閲覧機能をビルドで入れ、デザインは規約とパターンのスキルで決める

- 状態: 承認
- 日付: 2026-11-11

## 背景

[Issue #117](https://github.com/yamayu-i/pkm-kit/issues/117)。発表や共有のためのスライドを、Vault の中で AI に作らせて、ブラウザ（Chrome など）で見たい。今は置き場所も、作り方の規約も、共通の閲覧機能もない。

ほしいものは次のとおり。

- `slide/` の下に、スライドごとのフォルダを作る。添付は同じフォルダに置く。整理のためにフォルダを入れ子にできる
- どのスライドも同じ機能を持つ: 全スライドの一覧、Slide Show（最大化、矢印キーでスライドとアニメーションを前後）、テキストを認識できる PDF、部品を選んで付ける AI へのレビューコメント
- 伝わりやすいスライドデザインを調べたうえで共通の規約を作り、目的別のパターンを多く用意して、親のスキルから逆引きする。見た目は Material 3 を元にする

### 調べたこと（2026-11-11）

最初に Web 検索で調べたが、論文の本文を置くサイトの多くはクラウドの環境から開けず、要約までしか確かめられなかった。そこで、同じ項目を別の環境で一次資料の本文まで開いて確かめ直した。結果は、主張ごとに「確かめ方（本文を読んだ / 要旨だけ / 二次資料 / 未確認）」と「確度（高・中・低）」が付いている。

規則の根拠にするのは、**確かめ方が「本文を読んだ」で、確度が高か中のものだけ**にする（ユーザーの指示）。出典どうしの食い違いと、実験の根拠が見つからなかった経験則は、規約の注意書きに書く。

| 採った根拠（一覧はスキルの `evidence.md`） | 規約への使い方 |
|---|---|
| Garner & Alley 2013: 文の見出しと図のスライドは、句の見出しと箇条書きより、理解（推論の問い）で上回った。事実の再生には差がない。複数の要素を同時に変えた実験 | 見出しは主張の文、本文は根拠を見せる。効果を言えるのは仕組みの理解に限る、と注意書きに書く |
| Alley ほか 2006、Alley 2010 の指針、Farkas 2010 の批判 | 見出しは 2 行まで。図は強制せず、文だけのスライドと短い箇条書きを認める |
| Kosslyn ほか 2012: 8 つの原則、スライドでの規則（箇条は 4 項目・2 行まで、20pt 超）、よくある違反、聞き手がいら立つこと（要点が埋もれる、読み上げる、読み切れない）、直感では良し悪しを見分けられないこと | 1 枚 1 主張。話す文を載せない。まとまりは 4 つまで。強調は意味のある違いだけ。色と動きの規則。規則は検査の一覧にする |
| WCAG 2.2 | 既存のトークンの色（検査済み）を使う |

採らなかったもの（本文を確かめられなかった・確度が低い）: Mayer の原則と効果量（二次資料。版によって値が大きく違う）、文字の大きさと視距離の研究、Cowan 2001、Cleveland & McGill 1984、Tversky ほか 2002、Minto のピラミッド原則、Duarte の slidedoc、日本語の文字の大きさ・行間の研究、Material 3 の公式の値（値はこのリポジトリのトークンを使う）。

### 今ある仕組みとの関係

- Vault の HTML は pkm-html（[ADR-0037](0037-html-viewer.md)）が Obsidian の中で開くが、スクリプトをすべて取り除く。Slide Show とレビューコメントにはスクリプトが要るので、スライドはブラウザで開く
- 添付は `asset/` の直下に置く決まり（`.claude/docs/vault-conventions.md`）。スライドは 1 つのフォルダで完結させたいので、例外が要る
- デザインの値は `tokens.json` が正本（[design.md](../design.md)）。CLI は `.kit/bin/` にビルド済みのものをコミットする（`diagram.mjs`、`html.mjs`）

## 決定

### 1. 置き場所

```
slide/
  2026-roadmap/            … デッキ（deck.html があるフォルダ）
    deck.html              … ソース。AI と人が書く
    index.html             … ビルドしたもの。ブラウザで開く。手で編集しない
    chart.svg  photo.jpg   … 添付。同じフォルダに置く
  team/                    … 整理のためのフォルダ（deck.html がない）
    onboarding/
      deck.html  index.html
```

- `deck.html` があるフォルダが 1 つのデッキ。デッキの中にデッキを作らない。フォルダ名は英小文字・数字・ハイフン
- `slide/` は子のもの。git で管理し、端末間で同期する（`tmp/` と違う）。`index.html` もコミットする（モバイルではビルドできないため。プラグインの成果物と同じ扱い）
- 添付は `asset/` ではなくデッキのフォルダに置き、相対パスで参照する（`asset/` の決まりの例外）。`slide/` に md を置かない（ノートの書式の対象にしない）
- ノートからは `[題](slide/2026-roadmap/index.html)` でリンクしてよい

### 2. ソース（deck.html）

HTML の断片で書く。スクリプトとスタイルの値を持たず、決まった部品のクラスだけで書く。

```html
<title>2026 年のロードマップ</title>
<meta name="deck-density" content="present">
<section data-pattern="cover">…</section>
<section data-pattern="assertion-evidence">
  <h2>見出しは主張の文にする</h2>
  <figure>…</figure>
  <ul><li data-step>1 つずつ出す項目</li></ul>
  <aside class="notes">話すこと（発表者ノート）</aside>
</section>
```

- 1 枚は `<section data-pattern="…">`。`data-pattern` はパターンの id（下の 7）
- `data-step` を付けた要素は、Slide Show で 1 つずつ出る（数を書けば順番を決められる）
- `<aside class="notes">` は発表者ノート
- 色は役割の名前のクラス（`blue` など、トークンの色の名前）で付け、値を書かない。図は SVG を直接書くか、D2 で描いた SVG をデッキのフォルダに置く（[ADR-0102](0102-diagram-three-methods.md) の b・c。Mermaid はスクリプトが要るので使わない）

### 3. ビルド（.kit/bin/slide.mjs）

新しいパッケージ `.kit/src/packages/slide/`（Obsidian のプラグインではない。CLI だけ）を作り、`.kit/bin/slide.mjs` にビルドしてコミットする。

| コマンド | すること |
|---|---|
| `new <slide/…のフォルダ> --title <題>` | デッキのフォルダと `deck.html` のひな形を作る |
| `build <フォルダ> \| --all` | `deck.html` を検査し、共通の CSS とスクリプトを入れた `index.html` を書く |
| `check [<フォルダ>] ` | `index.html` が今の `deck.html` と今の CLI から作ったものと同じかを確かめる（手で編集していない、ビルドし忘れていない）。規約の検査も行う |
| `export <フォルダ>` | 添付を `data:` に埋め込んだ 1 ファイルを `tmp/` に書く（外部に渡す用。[ADR-0044](0044-html-standalone-export.md) と同じ名前の付け方） |
| `pdf <フォルダ>` | PC に入っている Chrome 系のブラウザをヘッドレスで動かし、印刷用の表示を PDF にして `tmp/` に書く。ブラウザが見つからなければ、その旨と、画面のボタンでの作り方を出して終わる（依存は足さない） |

- `index.html` は、同じ `deck.html` からは同じバイト列になる（日時を入れない）。`check` はビルドし直して比べる
- `verify.mjs` に `slide.mjs check` を足す（子の Vault と CI で、古い・手で直した `index.html` を止める）
- ビルドは `deck.html` から、スクリプト・イベントの属性・外部の読み込みを取り除く（pkm-html の `stripDangerous` を束ねて使う）。`index.html` の CSP は、共通のスクリプトだけをハッシュで許し、外部への通信を止める
- 規約の検査（機械的に分かるもの）。エラー（`index.html` を書かない）: 知らない `data-pattern`、パターンに要る部品がない、色や文字の大きさの値の直書き、`<style>`、見出しのない `<section>`、デッキの外を指す添付・ない添付。警告: 見出し・項目・1 枚の文字の量（密度ごとの目安）、1 つのリストが 4 項目を超える、入れ子が 2 段を超える、全部大文字・斜体・文まるごとの太字、強調が 2 か所以上
- 解析には linkedom を使う（pkm-html が CLI のために使っているものと同じ版。CLI に束ねるだけ）

### 4. 共通の閲覧機能（index.html）

開くと一覧。スクリプトが動かない場所（Obsidian の中の pkm-html）では、全スライドが縦に並んだ静的なページとして読める。

| 機能 | 内容 |
|---|---|
| 一覧 | 全スライドを縮小して格子に並べる。上に題と「Slide Show」「Download as PDF」「Review」のボタン。スライドを押すとそこから Slide Show |
| Slide Show | Fullscreen API で最大化し、16:9（1920×1080 のキャンバス）を画面に合わせて拡大縮小する。→ ↓ Space PageDown で次（ステップがあれば次のステップ）、← ↑ PageUp で前、Home / End、Esc で一覧に戻る。クリックとスワイプでも進む。進み具合とページ番号を出す。URL の `#/3` でそのスライドを開く |
| アニメーション | `data-step` の要素が、M3 の動き（duration と easing のトークン）で出る。`prefers-reduced-motion` のときは動かさずに出す |
| PDF | ボタンを押すと印刷用の表示（1 枚 1 ページ、ステップはすべて出した状態、背景色つき）にして、ブラウザの印刷を開く。「PDF に保存」を選ぶと、文字がテキストのまま入った PDF になる |
| レビューコメント | Review を押すと、一覧で部品（見出し・カード・図・項目など）を選べる。選んでコメントを書く。スライド全体・デッキ全体へのコメントも書ける。コメントはブラウザに保存する（`localStorage`）。「Copy review」で、AI が読めるレポート（Markdown）をクリップボードにコピーする |
| 直した後の確認 | ビルドし直して再読み込みすると、レビューの画面のまま、前回見たときから変わったスライドに「Updated」が付き、何枚変わったかが上に出る。コメントを付けた部品が変わっていれば、コメントにも「Updated」が付く。直ったコメントは「Done」で消す |
| 発表者ノート | 一覧で各スライドの下に出せる（切り替え）。Slide Show では出さない |
| 発表者ビュー | 「Presenter」のボタン（Slide Show 中は P）で別ウィンドウを開き、今のスライド・次のスライド・発表者ノート・経過時間と時刻を出す。どちらのウィンドウで送っても同期する |
| テーマ | ライト / ダーク（既定はライト。デッキで決め、一覧で切り替えられる） |

レビューのレポートは、デッキのパス、スライドの番号と見出し、部品の位置（`deck.html` の行番号と、部品の種類・文の冒頭）、コメントを、通し番号を付けて並べる。受け取った AI は、スキルの手順で `deck.html` を直してビルドし直し、番号ごとにどう直したかを返す。

作る体験の中心は、この往復に置く: **話し合う（聞き手と目的、見出しだけの話の筋）→ 作る → 使う人がブラウザで見てコメントする → 直す → 変わった所を確かめる**。1 回で完成させず、短い周期で回す。

### 5. デザインの値

- 色・角丸・動きは `tokens.json` の値を使う（design の生成に、スライド用の CSS を足す。ライトとダークの両方）。手で書かない
- 文字は M3 の役割（display / headline / title / body / label）を、1920×1080 のキャンバスに合わせた倍率で拡大する。倍率は密度で決める

| 密度 | 使う場面 | 倍率 | 本文（body-large） | 最小（label-medium） |
|---|---|---|---|---|
| `present`（既定） | 話し手が付いて投影する | 3 | 48（24pt 相当） | 36（18pt 相当） |
| `read` | 画面や PDF で読ませる資料 | 2 | 32（16pt 相当） | 24（12pt 相当） |

- pt 相当は、キャンバスの高さ 1080 を 540pt（PowerPoint の 16:9 の既定）としたもの。`present` の値は、採った根拠の指針（本文 18〜24pt、20pt 超）に合わせた。指針は経験則で、会場の条件を含まない。`read` の値と、日本語の字数の目安には根拠がなく、この仕組みで置いた目安として注意書きに書く

- フォントは端末のもの（外部から読み込まない）。日本語はゴシック体
- デッキごとに primary の色を差し替えられる（`<meta name="deck-primary" content="#RRGGBB">`。ダーク用は `deck-primary-dark`）。値を書いてよいのはここだけ。ビルドが、その色と面の色のコントラスト（文字として 4.5:1、ライトとダークの両方）を確かめ、足りなければ失敗にする。primary の上の文字の色と container の色は、ビルドがその色から作る

### 6. Obsidian から開く

Obsidian の中（pkm-html）ではスクリプトが動かないので、pkm-html に、`slide/` の下のデッキの `index.html` を OS の既定のブラウザで開くコマンド「Open slide in browser」と、ファイルのメニューの項目、タブの右上のボタンを足す。開けるのはスライドだけにする（ほかの HTML は、スクリプトを取り除くこの View で見る）。スマホで使えるかは実機で確かめ、使えなければ通知で知らせる。

### 7. スキル（.claude/skills/slide/）

| ファイル | 内容 |
|---|---|
| `SKILL.md` | 親。流れ（目的と聞き手と密度を決める → 見出しだけで話の筋を作る → 逆引きでパターンを選ぶ → `deck.html` を書く → ビルドと検査 → 目で確かめる）と、**伝えたいことからパターンを引く逆引きの表** |
| `conventions.md` | 共通の規約（1 枚 1 主張、見出しは主張の文、話す文を載せない、まとまりは 4 つまで、強調は 1 か所、文字の大きさ、色、ラベル、動き、密度ごとの目安）。規則ごとに根拠の ID。根拠が割れている点と、実験の根拠がない経験則の注意書き |
| `authoring.md` | `deck.html` の書式、部品のクラス、ステップ、ノート、図 |
| `patterns/<id>.md` | パターンごとに、使う場面・使わない場面・HTML のひな形・書くときの指示・よくある失敗・根拠 |
| `review.md` | レビューのレポートを受け取ったときの直し方 |
| `evidence.md` | 採った根拠の一覧（ID 付き）と、採らなかったものとその理由 |
| `maintaining.md` | パターンを足す・消す・直す手順 |

パターンは次の 34 個で始める（使った記録を見て足す・消す）。

| 目的 | パターン |
|---|---|
| 構成 | `cover`、`agenda`、`section`、`summary`、`next-steps`、`closing`、`appendix` |
| 主張する | `assertion-evidence`、`statement`、`big-number`、`quote` |
| 比べる | `comparison`、`before-after`、`pros-cons`、`decision-table`、`matrix-2x2` |
| 構造を見せる | `cards`、`layers`、`tree`、`definition` |
| 流れを見せる | `process`、`timeline`、`cycle`、`funnel` |
| データを見せる | `chart-bar`、`chart-line`、`chart-share`、`table`、`kpi` |
| 物を見せる | `image`、`screenshot`、`code`、`diagram` |
| 話の型 | `problem-solution` |

### 8. 最初の版に入れないもの

- 画面のボタン 1 つでの PDF のファイル保存（ブラウザの印刷を経由しない方法）
- Obsidian の中のスライドの一覧の View（[ADR-0120](0120-slide-list-view-and-patterns.md) で pkm-slide に足した）
- primary 以外の色の差し替え、16:9 以外の比率

## 理由

- **ビルドを通す**: 共通機能を各デッキに手で書くと、古いものが残り、ばらつく。`check` がビルドし直して比べるので、どの `index.html` も今の共通機能を持つと言える
- **ソースを HTML の断片にする**: AI は HTML を正確に書ける。配置の自由度が要るパターン（比較、マトリクス、図）を Markdown では表せない。部品のクラスに絞るので、値は規約の側で決まる
- **`index.html` をコミットする**: スマホと、ビルドの環境がない端末でも開ける。プラグインの成果物と同じ考え方
- **添付を同じフォルダに置く**: デッキをフォルダごと動かす・渡す・消すことができる。`asset/` に混ぜると、どの添付がどのデッキのものか分からなくなる
- **PDF を印刷で作る**: ブラウザの印刷は、文字をテキストのまま PDF に入れる。スクリプトだけで PDF のファイルを作る方法は、画面を画像にするもの（文字を認識できない）か、大きい依存が要る
- **スクリプトなしでも読める形にする**: Obsidian の中（pkm-html）とスマホでも、内容を確かめられる
- **CSP でスクリプトを共通のものだけにする**: デッキの中身に何が入っても、動くのは検査済みの共通のスクリプトだけ。外部に通信しない（pkm-html と同じ守り）
- **文字を M3 の倍率にする**: M3 の役割どうしの比を保ったまま、採った指針の大きさに合う。密度を変えても倍率 1 つで済む
- **根拠を、本文で確かめた確度の高いものに絞る**: 広く言われていても、確かめられなかったものを規則にすると、レビューで規則とぶつかったときに、どこまで言い張ってよいかが分からなくなる。採らなかったものも一覧に残し、後で確かめられたら足せるようにする
- **変わった所を画面で知らせる**: 直してもらった後、使う人が全スライドを見直さずに済む。往復の 1 周が短くなる
- **パターンをスキルのファイルにする**: research-report の型と同じ形で、足す・消す・直すが 1 ファイルで済む。逆引きは親に 1 つだけ置く

## 却下した案

- **既存のライブラリ（reveal.js、Marp、Slidev）を使う**: 依存が大きく、レビューコメントと規約の検査は結局自前で作る。外観を `tokens.json` に合わせる手間も残る。必要な機能（一覧・送り・ステップ・印刷）は小さく書ける
- **Markdown から作る**: 書きやすいが、配置のあるパターンを表すために独自の記法が増え、AI にも人にも HTML より分かりにくくなる
- **`index.html` をコミットせず、見るときにビルドする**: スマホで見られない
- **共通の CSS とスクリプトを別ファイルにして各デッキから読む**: 1 か所で済むが、フォルダを動かす・渡すと壊れる。`file://` での読み込みの制限も受ける
- **pkm-html でスクリプトを許して Obsidian の中で Slide Show する**: HTML の守り（ADR-0037）を緩めることになる
- **PDF を html2canvas + jsPDF で作る**: 画像の PDF になり、文字を認識できない
- **パターンごとに別のスキルにする**: スキルの一覧が 30 個増え、選ぶのが難しくなる。逆引きを親に置けない

- 追加: `.kit/src/packages/slide/`（ソース、テスト、プレビュー）、`.kit/bin/slide.mjs`、`.claude/skills/slide/`、design の生成（スライド用の CSS）
