# ADR-0156: MCP を PKM 全体に広げ、子での利用ログを貯める

- 状態: 承認
- 日付: 2026-11-15

## 背景

- MCP（`pkm-task-mcp`、[ADR-0025](0025-mcp-and-task-coach.md)）はタスク管理だけを扱う。ノート・wiki・デイリーノート・元資料は、AI がファイルを直接読み書きしている。そのため所有の区分（[LLM wiki の仕組み](../../../../.claude/docs/llm-wiki.md)。daily 本文の保護、`sources/`・`asset/` は追加だけ）が、スキルの手順の約束頼みになっている
- 合成 Vault（ノート 3,000、issue 1,000、デイリー 365、計 4,377 ファイル、5.7MB）で今の MCP を計測した（Issue #156）
  - 起動と `initialize` は 40 ms。ツール 1 回は 110〜150 ms で、呼ぶたびに `readVault` が Vault 全体を読み直して索引を作る。直接の `rg` は 35〜40 ms、Node で全 md を読んで部分一致するのは 33〜42 ms
  - `get_overview` の応答が 880KB あった（`problems` 3,600 件で 410KB、`stalled` で 120KB）。一覧に上限がなく、応答を整形した JSON で返している
  - `tools/list` が 11KB ある。ツールを倍以上に増やすと、AI が常に読む量が増える
- AI の 1 ターンは秒単位なので、100 ms 前後の差は体感にほぼ響かない。効くのはツールを呼ぶ回数とトークン量で、集計と検査をサーバーで済ませれば往復が減る
- どこが足りないかは、子で実際に使ってみないと分からない。子での使われ方を記録し、harness-review → escalate（[ハーネスの ADR-0006](../../../harness/docs/adr/0006-self-improvement-loop.md)）で上流に返せるようにしたい

## 決定

### 1. サーバーと名前

- サーバーは今と同じ `pkm-task/cli/mcp.ts` → `.kit/bin/mcp.mjs` に置き、名前を `pkm` にする（`serverInfo.name`）。外部依存は足さない（ADR-0025 のまま）
- ツールは群ごとに接頭辞を付ける

  | 群 | 接頭辞 | 内容 |
  |---|---|---|
  | task | `task_` | 今のツールすべて（`task_get_overview` など）と、member・routine・label の作成と更新、Calendar の取得 |
  | note | `note_` | ノートの検索・取得・一覧・リンク（出るリンクと被リンク）・作成・追記・frontmatter の更新・改名 |
  | daily | `daily_` | デイリーノートの取得、未処理の一覧（`daily-pending` と同じ判定）、末尾への追記 |
  | wiki | `wiki_` | index の取得、未取り込みの元資料、ページの作成と更新、log と index への記録、元資料の追加 |
  | check | `check_` | 書式・リンク切れ・孤立ページ・タスクの整合性の検査（`wiki-lint` と `lint` の判定を使う）、改名待ちの一覧 |
  | meta | `meta_` | AI からのフィードバック（下の 6） |

- `--toolset=task,note,...` で公開する群を選べる。既定はすべて。旧名（接頭辞なし）は 1 版のあいだ別名として受け付け、呼ばれたらログに `alias` と記録する。次の版で消す
- 子の起動設定は、セットアップが Vault ルートの `.mcp.json`（子のもの）に `pkm` を書く。すでに `pkm-task` があれば移行で置き換える

### 2. 所有の区分をサーバーで強制する

- 生のファイル書き込みのツールは出さない。書き込みはパスの区分を判定してから行う

  | 区分 | 許すこと |
  |---|---|
  | `daily/` | 末尾への追記、frontmatter の更新、改名にともなうリンクのパスの書き換え（ハーネスの ADR-0015） |
  | `sources/`、`asset/` | 新しいファイルの追加だけ |
  | `wiki/`（`feedback.md` を除く） | 作成・更新・削除 |
  | 通常のノート | 作成・追記・frontmatter の更新・改名 |
  | タスク管理のデータ | `task_` のツールからだけ（今のまま） |
  | `tmp/`、隠しパス、`template/`、`slide/` | 読み書きしない（読む群からも既定で除く） |

- 作成するノートは、テンプレート（`.kit/templates/file/` に `template/file/` を重ねる）から作り、`created` と `updated` を入れる
- 書き込んだ後に、そのファイルを書式の検査にかける。問題があれば書き込まずにエラーにする
- エラーは先頭に種類を付ける: `[ownership]` / `[validation]` / `[not_found]` / `[conflict]` / `[internal]`。AI が直し方を判断でき、ログでも数えられる

### 3. 応答の大きさ

- 一覧は既定 20 件、上限 100 件にし、`total` と `truncated` を返す。続きは `cursor` で取る
- `task_get_overview` の `problems` と `stalled` は、件数と上位 5 件だけにする。全件は `check_` と `task_list_issues` で取る
- 応答の JSON は整形しない
- 本文を返すツールは、既定で本文を 8,000 字で切り、`truncated` を付ける。`full: true` で全文を返す

### 4. 検索（単純一致）

- `note_search` は外部依存のない部分一致で始める
  - 検索語とノートの両方を正規化する（NFKC、英字の大文字・小文字、カタカナをひらがなに）
  - 空白で区切った語の AND
  - 順位は `title` → `aliases` → `tags` → 本文の順に当たったものを上にし、同じなら `updated` が新しい順
  - 当たった箇所の前後 80 字を抜粋で返す。`type`、`tags`、パスの先頭、日付の範囲で絞れる
- 表記ゆれと意味の近さは AI が担う（言い換えて何度か検索する、まず `wiki/index.md` から辿る）。意味検索（埋め込み）は今回入れない。見直す目安は、ログで結果が 0 件の検索の割合が高いとき、または 1 回の検索が 1 秒を超えるとき

### 5. 索引のキャッシュ

- stdio のサーバーはセッション中ずっと動くので、解析した結果をメモリに持つ。呼び出しのたびに mtime と大きさを見て、変わったファイルだけを読み直す（Obsidian や git による変更も拾う）
- 目安: 5,000 ファイルの Vault で、2 回目以降の読み取りのツールが p95 で 50 ms 以下

### 6. 利用ログ（子で課題を見つけるため）

- 置き場所は `output-log`（ハーネスの ADR-0013）と同じ考え方にする。子（`.kit-local/` がある）は `.claude/mcp-log/`、上流は `.kit/harness/mcp-log/`。サーバーの起動 1 回 = 1 ファイル（`<置き場所>/YYYY-MM/<起動日時>-<乱数>.jsonl`）に追記するので、端末をまたいでも衝突しない。コミットして端末間で同期する
- 1 行 1 件。種類は次の 4 つ

  | `kind` | いつ | 主な項目 |
  |---|---|---|
  | `start` | 起動と `initialize` | サーバーの版、`clientInfo`（名前と版）、`toolset`、端末名、Vault のファイル数、索引を作るのにかかった時間 |
  | `call` | ツールを呼ぶたび | ツール名、別名で呼ばれたか、引数（下の扱い）、時間（ms）、応答の大きさ（bytes）、件数、`truncated`、エラーの種類、検索なら結果の件数 |
  | `feedback` | AI が `meta_feedback` を呼んだとき | 対象のツール、種類（`missing` ツールがない / `wrong` 結果が誤り / `large` 大きすぎる / `slow` 遅い / `unclear` 使い方が分からない / `rejected` 拒否が不当 / `bypass` MCP を使わずに直接編集した）、200 字以内の要約 |
  | `bypass` | AI が MCP を通さずに Vault のノートを読み書きしたとき（下のフック） | 操作（Read / Edit / Write / Grep / Glob）、パスの区分（`daily` / `wiki` / `sources` / `note` / `task` など） |

- 引数の扱い: 検索語は先頭 100 字まで残す（0 件の検索を見直すため）。本文・追記する内容・frontmatter の値は残さず、項目名と長さだけを残す。`PKM_MCP_LOG=off` で記録を止められる
- `bypass` は、Claude Code の `PostToolUse` フック（`.claude/settings.json` と `.claude/hooks/`）で記録する。パスの区分だけを残し、ファイル名は残さない。Bash（`cat`、`sed`）での読み書きは拾えない
- AI への指示: 子向けの規約とスキル（task-coach、wiki の各スキル、note-rename）に、「MCP で足りずに直接読み書きしたとき、結果が使えなかったときは `meta_feedback` を呼ぶ」と書く
- 集計: `node .kit/bin/mcp.mjs report [--since YYYY-MM-DD]` が、ツールごとの回数・エラーの種類別の割合・時間の p50 と p95・応答の大きさの p95・`truncated` の割合・0 件の検索の割合・別名で呼ばれた回数・`bypass` の区分別の回数・`feedback` の一覧を出す。`usage-report.mjs` はこれを「MCP の利用」の節として含め、harness-review が読む
- 上流に返すときは、集計の数値とツール名、フィードバックの種類だけを使う。検索語とフィードバックの要約は、個人の内容を含みうるので、そのまま escalate に入れない

### 7. 段階

1. 名前と群の導入（旧名の別名）、応答の大きさ（3）、索引のキャッシュ（5）、利用ログ（6）、`note_` と `daily_` と `wiki_` と `check_` の読み取り、`.mcp.json` の移行
2. 安全な書き込み: `wiki_` のページと log・index、元資料の追加、`note_` の作成・追記・frontmatter、`daily_` の追記（今の `append_daily_note` を移す）
3. `note_rename`（リンクの一括書き換え）、`task_` の member・routine・label・Calendar、旧名の削除

段階ごとに PR を分ける。どの段階も、子で使った利用ログを harness-review で見てから次の段階の中身を見直してよい。

## 理由

- 所有の区分をサーバーで判定すれば、スキルの手順を読み違えても daily の本文や元資料を壊さない
- 集計・検査・テンプレートの展開をサーバーで済ませれば、AI の往復とトークンが減る。1 回あたりの 100 ms の差より大きく効く
- 接頭辞と `--toolset` で、ツールが増えても AI が迷いにくく、読む定義も絞れる
- 単純一致は依存がなく、結果を説明でき、端末間で索引がずれない。日本語は単語の区切りがないので、部分一致の方が取りこぼしにくい
- 起動ごとのファイルにログを分ければ、PKM Git の同期で衝突しない。`call` に加えて `bypass` と `feedback` を残すことで、「MCP が使われなかった場所」と「使ったが足りなかった場所」の両方が見える

## 却下した案

- **別サーバー（`pkm-note-mcp`）を足す**: 起動設定とビルドが二重になり、`readVault` と core を共有する利点が薄れる。ADR-0025 が別パッケージを却下した理由と同じ
- **汎用のファイル読み書きのツールを出す**: 所有の区分を守れず、直接編集と変わらない
- **意味検索（埋め込み）を今入れる**: 外部依存かモデルの配布が要る。単純一致で足りないかを、まずログで確かめる
- **ログに引数をすべて残す**: ノートの本文が重複してコミットされ、escalate に個人の内容が混ざりやすい
- **ログを `tmp/` に置く（同期しない）**: harness-review は 1 台で行うので、ほかの端末で使った分が見えなくなる
- **`bypass` を記録しない**: MCP に足りないツールは、呼ばれなかったことからしか分からない

## 影響

- `pkm-task/cli/` に、パスの区分の判定、ノートと wiki の読み書き、検索、キャッシュ、ログの書き込みと集計が加わる。`main.js` のバンドルは変わらない
- 子に `.claude/mcp-log/` と `.mcp.json` が増える（子のもの）。`.claude/settings.json` に `PostToolUse` のフックが増える
- task-coach のツール名が変わる（段階 1 では旧名も動く）。子向けの規約・スキル・`usage-report.mjs`・harness-review、製品の文書（`surfaces/task-mcp.md`）を更新する
- 移行を付ける（`.mcp.json` の作成と置き換え）。`.kit/changes/` に変更を書く
- ログとフックを足すので、セキュリティチェックの対象になる
