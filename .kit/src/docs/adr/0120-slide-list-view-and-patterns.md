# ADR-0120: スライドの一覧の View でフォルダを作ってデッキを動かし、パターンを増やす

- 状態: 提案
- 日付: 2026-11-12

## 背景

[Issue #120](https://github.com/yamayu-i/pkm-kit/issues/120)。[ADR-0117](0117-slides.md) でスライドを `slide/` に HTML で作れるようになった。使ってみて、次の不足が分かった。

1. Obsidian の中にスライドの一覧がない（ADR-0117 の「最初の版に入れないもの」）。どんなデッキがあるかは、ファイルの一覧で `slide/` を開いて `index.html` を探すしかない。整理のフォルダを作る、デッキを別のフォルダに動かす、もファイルの一覧で行うしかない
2. デッキを動かすと壊れる。`index.html` はデッキのパス（`data-deck="slide/…"`。レビューのレポートに出す）を持つので、フォルダの名前が変わると `slide.mjs check` が「古い」と止める。モバイルではビルドし直せない
3. 上流の CLI が変わると、子のすべての `index.html` が「古い」になる。`check` は今の CLI で作り直して比べるため。今は、取り込んだ後にビルドし直す手順がない
4. パターンが 34 個で、写真を大きく見せる、ロードマップ（期間 × 流れ）、振り返り、リスクと対策、決めてほしいこと、などに合うものがない。1 枚に置ける配置の幅（写真と文を左右に、全面の写真）も少ない

画像の見切れ、カードの角丸、語の途中での折り返しは、設計判断を含まない修正として先に直した（同じ Issue のブランチ）。

## 決定

### 1. 一覧の View は pkm-html に置く

pkm-html に View「Slides」（種類 `pkm-html-slides`、コマンド「Open slides」、アイコン `presentation`）を足す。pkm-view-selector の候補に pkm-html を足す。

| 部分 | 内容 |
|---|---|
| 左: フォルダ | `slide/` の下の整理のフォルダの木（デッキは木に出さない）。「All」で全部 |
| 右: デッキ | 選んだフォルダの下のデッキを、カードで並べる。カードは 1 枚目の縮小（`index.html` を pkm-html と同じ sandbox で、スクリプトなしに描く）、題（`deck.html` の `<title>`）、枚数、フォルダ、更新日時 |
| 並び | 更新日時（新しい順）・題。検索（題とフォルダ名） |
| デッキの操作 | 押すと Obsidian の中（pkm-html の View）で開く。メニューに「Open in browser」「Move to…」「Rename」「Reveal in file explorer」 |
| フォルダの操作 | 「New folder」、フォルダのメニューに「Rename」「Move to…」「Delete」（空のときだけ） |
| 動かし方 | 「Move to…」で行き先のフォルダを選ぶ（あいまい検索のダイアログ）。PC ではカードをフォルダにドラッグしても動かせる |

- デッキを作る（`deck.html` を書いてビルドする）のは、これまでどおり Claude Code と CLI。View には作るボタンを置かず、空のときに作り方を出す
- 一覧は `slide/` の下の `deck.html` を探して作る。ファイルが変わったら作り直す（Vault のイベント）

### 2. デッキを動かしても壊れないようにする

- 動かすのは Obsidian の `FileManager.renameFile`（フォルダごと）。ノートからの `slide/…/index.html` へのリンクは Obsidian が書き換える
- 動かした後、動いた範囲のすべてのデッキの `index.html` の `data-deck="…"` を新しいパスに書き換える。`data-deck` はビルドの出力のうちデッキのパスが入る唯一の場所で、ビルドのハッシュ（`data-build`）にも入らない。書き換えた結果は、新しい場所でビルドし直したものと同じバイト列になる（テストで確かめる）。モバイルでも動く
- 行き先の規則: フォルダ名は英小文字・数字・ハイフン。デッキの中や、動かすフォルダ自身の下には動かせない。同じ名前があれば止める
- ブラウザに残るレビューのコメントは、デッキのパスで分けているので、動かすと前のコメントは見えなくなる（View の確認のダイアログで知らせる）

### 3. 上流を取り込んだらビルドし直す

`vault-upgrade` の手順に「`slide/` があれば `node .kit/bin/slide.mjs build --all` を実行して、`index.html` を一緒にコミットする」を足す。CLI を変えるたびに移行を書くのではなく、取り込みの手順で毎回行う（`build` は同じ入力から同じバイト列を作るので、変わらなければ差分は出ない）。今回の PR の CLI の変更（画像・角丸・折り返し）も、これで子に届く。

### 4. パターンを増やす（34 → 下の表で選んだもの）

パターンの追加の案。☆ は勧めるもの。

| 目的 | パターン | 伝えたいこと |
|---|---|---|
| 構成 | ☆ `cover-image` | 写真を全面に敷いた表紙 |
| 構成 | `profile` | 話し手・チームの紹介（写真、名前、役割） |
| 主張する | ☆ `image-statement` | 全面の写真の上に 1 文を載せて、印象で残す |
| 主張する | ☆ `two-numbers` | 2 つの数字を並べて差を見せる（前と後、目標と実績） |
| 主張する | `question` | 問いを投げて、聞き手に考えさせる |
| 主張する | `myth-fact` | よくある思い込みと、実際を対にする |
| 比べる | ☆ `options` | 3 つの案を並べ、勧める 1 つを示す（松竹梅） |
| 比べる | `spectrum` | 2 つの極の間のどこに当たるかを、1 本の軸で見せる |
| 比べる | `venn` | 2〜3 つの重なりと、その真ん中を見せる |
| 構造を見せる | ☆ `split-image` | 写真と文を左右半分ずつに置く |
| 構造を見せる | ☆ `grid` | 5〜9 個の小さな要素を格子に並べる（一覧、機能の地図） |
| 構造を見せる | `hub` | 中心の 1 つと、周りの 3〜6 つの関係を見せる |
| 構造を見せる | `pyramid` | 土台から頂点へ積み上がる層（優先度、成熟度） |
| 流れを見せる | ☆ `roadmap` | 期間 × 流れ（チーム・テーマ）の表に、いつ何をするかを置く |
| 流れを見せる | `journey` | 利用者の段階ごとの行動と気持ちの上下を見せる |
| 流れを見せる | `flow` | 分岐のある判断の流れ（はい / いいえ） |
| データを見せる | ☆ `chart-column` | 縦棒で、期間ごとの量の推移を見せる |
| データを見せる | ☆ `progress` | 目標に対する進み具合を、複数の項目で見せる |
| データを見せる | `chart-waterfall` | 始まりから終わりまでの増減の内訳を見せる |
| データを見せる | `heatmap` | 2 つの軸の交わりの濃淡を見せる（曜日 × 時間など） |
| 物を見せる | ☆ `gallery` | 2〜6 枚の写真を並べて見せる |
| 物を見せる | `screenshot-compare` | 変える前と後の画面を並べる |
| 話の型 | ☆ `risks` | リスクと対策を対にして、大きさを示す |
| 話の型 | ☆ `ask` | 聞き手に決めてほしいこと・お願いしたいことを、期限とともに示す |
| 話の型 | ☆ `retro` | 振り返り（続けること・困ったこと・次に試すこと） |
| 話の型 | `scr` | 状況・問題・解決の 3 段で話の全体を見せる |
| 話の型 | `faq` | よく聞かれる問いと答えを 3〜4 組 |

パターンを増やすのと別に、**部品の変種**を足す（パターンの数を増やさずに配置の幅を広げる）。

| 変種 | 書き方 | 効くところ |
|---|---|---|
| 写真の置き方 | `<figure class="bleed">`（スライドの全面、文字の背に暗い膜）、`<figure class="left">` / `right`（半分） | image、cover、statement、assertion-evidence |
| カードの見た目 | `card outline`（線だけ）、`card numbered`（左上に番号） | cards、options、risks |
| カードの上の画像 | `<div class="card"><img class="cover-img" …>`（カードの上半分に写真。切り取らずに収める） | cards、gallery、profile |

追加したパターンも、これまでと同じく `patterns.ts`・`patterns.css`・スキルの `patterns/<id>.md`・逆引きの表をそろえ、見本の描画ではみ出しがないことを確かめる。根拠のないパターンを足すときは、`conventions.md` の規則（1 枚 1 主張、まとまりは 4 つまで、強調は 1 か所）に反しない形にし、根拠の欄に「規約に従う配置で、パターンそのものの実験の根拠はない」と書く。

## 理由

- **pkm-html に置く**: スライドを Obsidian の中で開く View（スクリプトなし）と、ブラウザで開くコマンドがすでにここにある。縮小の描画にも同じ sandbox を使える。新しいプラグインにすると、有効にする手間と設定が増える
- **一覧で作らない**: デッキを作るのは、目的と聞き手を話し合ってから書く流れ（slide スキル）が中心。View で空のデッキを作っても、中身は Claude Code で書くことになる
- **`data-deck` を書き換える**: 動かすたびにビルドし直す方法は、モバイルで使えない。`data-deck` をなくして実行時に URL から求める方法は、Vault の外のパスと区別できず、レビューのレポートが Vault からのパスを出せなくなる
- **取り込みの手順で毎回ビルドする**: 移行は 1 回だけ実行されるので、CLI を変えるたびに書く必要がある。書き忘れると、子の検査が理由の分からない失敗をする
- **変種を足す**: 写真の置き方やカードの見た目は、どのパターンでも同じ書き方で効く。パターンにすると、組み合わせの数だけ増える

## 却下した案

- **新しいプラグイン（pkm-slide）にする**: 上の理由。pkm-html のスライドの部分と分ける利点が小さい
- **一覧を `slide/index.html`（ビルドが作る一覧のページ）にする**: ブラウザでは見られるが、Obsidian の中でフォルダを作る・動かす、ができない
- **デッキのパスを `index.html` に入れない**: 上の理由
- **CLI を変えたら移行で子をビルドし直す**: 上の理由
- **アイコンの組（Lucide など）を部品にする**: 依存が増え、色以外の装飾で 1 枚の要素が増える。最初は入れない

## 影響

- 変更: pkm-html（View、フォルダの木、デッキのカード、移動と `data-deck` の書き換え。`main.js` をビルドする）、pkm-view-selector（候補に pkm-html）、slide（パターンと変種の CSS、`patterns.ts`）、スキル `slide`（パターンの md、逆引きの表、authoring の変種）、`vault-upgrade` のスキル（ビルドし直す手順）、`design.md`（View）、プロダクトの文書（`surfaces/slide.md`）、ADR-0117 の「最初の版に入れないもの」への注記
- テスト: 一覧の作り方（フォルダの木、デッキの題と枚数）、行き先の規則、`data-deck` の書き換えがビルドし直したものと同じになること、新しいパターンのひな形がビルドの警告なしに通ること、見本の描画ではみ出しがないこと（preview）
- セキュリティ: 縮小の描画は、pkm-html と同じ sandbox（スクリプトなし、CSP）で行う。ファイルの書き換えは `slide/` の下の `index.html` の 1 つの属性だけ
- 子の Vault: 移行なし（`index.html` のビルドし直しは vault-upgrade の手順）。`.kit/changes/` に書く
- 実機で確かめること: PC とスマホでの一覧の表示、フォルダの作成とデッキの移動（ノートからのリンクが書き換わること）、ドラッグでの移動（PC）
