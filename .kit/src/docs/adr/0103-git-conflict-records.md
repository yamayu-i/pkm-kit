# ADR-0103: PKM Git は、中身から分からない衝突を記録に残し、共通祖先が複数あっても変更を黙って戻さない

- 状態: 提案
- 日付: 2026-11-09

## 背景

[Issue #103](https://github.com/yamayu-i/pkm-kit/issues/103) で扱う。これは同期の再設計（[Issue #86](https://github.com/yamayu-i/pkm-kit/issues/86)）の第 3 段階。第 2 段階（[ADR-0089](0089-git-auto-sync.md)）で、同期は自動で 1 つの処理になった。コミットは共有の区切りだけで作る。取り込みが途中で落ちても復旧する。

今のマージは、両側の変更が重なっても止まらない。どの衝突でも内容を捨てずに残す（`src/merge/tree-merge.ts`）。

| 衝突 | 今の残し方 | 後から分かるか |
|---|---|---|
| md / txt の同じ行を両側で変えた | コンフリクトマーカーを入れる | 分かる。本文にマーカーがある |
| それ以外（JSON、図、画像など）を両側で変えた | リモート版を採用し、ローカル版を別名（`… (conflict <端末> <日時>).ext`）で残す | 分かる。別名の名前の形で見つかる |
| 片方が削除し、片方が編集した | 編集側を残す（`kept-modified`） | **分からない** |

マーカーと別名の版は、Vault の中身を走査すれば、どの端末でも、再起動しても一覧に出る。削除と編集の衝突は、マージした端末の Notice とモーダルと、マージのコミットメッセージにしか出ない。再起動すると一覧から消える。ほかの端末では一度も出ない。結果として、削除の意図を黙って捨てたのと同じになる。

共通祖先も問題がある。`mergeBase()` は `findMergeBase` が返す共通祖先の先頭の 1 つだけを使う。共通祖先が複数あるとき（criss-cross）、どれを選ぶかでマージの結果が変わる。たとえば、あるファイルが祖先 1 では v1、祖先 2 では v2 だったとする。ローカルは v2 のまま、リモートは v1 だとする。祖先 1 を選ぶとローカルの v2 を、祖先 2 を選ぶとリモートの v1 を、どちらも衝突なしで採る。片方の変更が「変更なし」と見なされ、黙って戻る。

PKM Git だけが 1 つのリモートに fast-forward で push する使い方では、共通祖先は 1 つになる。複数になるのは次の場合に限られる。

- PC の Git CLI で別のリモートとやり取りした
- 履歴を書き換えた
- 旧版のプラグインやほかのツールが混ざった

まれだが、起きたときに黙って戻すのは安全性の前提（[#86](https://github.com/yamayu-i/pkm-kit/issues/86)：編集・候補・削除の意図を黙って捨てない）に反する。

#86 では、記録を Git に入れる形式について、次の 3 つを懸念に挙げた。

- 旧版のプラグインと混ざること
- 記録そのものが衝突すること
- 解決済みの記録をいつまで持つか

あわせて、「記録だけ増えて解けない状態で出さない」とした。

## 決定

### 1. 記録するのは、中身から分からない衝突だけ

- マーカーと別名の版は、今と同じく Vault の中身の走査で見つける。記録しない。中身と記録が食い違う状態を作らないため
- 記録するのは、削除と編集の衝突（`kept-modified`）だけ。ほかの種類を足すときも、「中身から分からない」ものに限る

### 2. 記録は衝突 1 件に 1 ファイルで、マージのコミットに入れる

- 置き場所は `.pkm-git/conflicts/<ID>.json`
  - Vault のルートの隠しフォルダ。Obsidian のファイル一覧と検索には出ない
  - 隠しパスなので、ノートの書式の検査（`wiki-lint`、frontmatter）の対象外
  - Vault のもの（上流のものではない）
- ID は `<UTC の日時 YYYYMMDDTHHMMSSZ>-<8 桁の 16 進>`。16 進の部分は、パス・端末名・日時から作る。ファイル名に端末名とパスを入れない
- 記録はマージの結果のツリーに入れる。マージのコミットと記録は同じコミットになる。push すれば、ほかの端末にも同時に届く。マージしたのに記録がない状態と、記録だけがある状態を作らない
- 中身（`schemaVersion: 1`）:
  - `kind`（`kept-modified`）
  - `path`
  - `deleted`（削除したのが、マージした端末の側か（`local`）、リモートの側か（`remote`））
  - `device`（マージした端末の名前）
  - `at`（秒までの ISO 8601、オフセット付き）
  - `local` / `remote` / `bases`（マージした 2 つの版と共通祖先のコミット）
- 記録は、作った後に書き換えない。解決したら消す。どちらの端末も記録を書き換えないので、記録そのものがマージで衝突しない
  - 両方が消した場合は、どちらも削除なので衝突しない
  - 片方が消し、片方が変えていない場合は、消した側を採る
- `.pkm-git/` の中のパスどうしの衝突は記録しない（記録の記録を作らない）

### 3. 解決の方法

未解決の一覧（`List unresolved conflicts` と ` · ⚠ N`）に、走査の結果と記録を合わせて出す。記録の行には、次の 2 つのボタンを付ける。

| ボタン | すること |
|---|---|
| `Keep`（残す） | 記録を消す。ファイルはそのまま |
| `Delete`（削除する） | ファイルを Obsidian のごみ箱の設定に従って消し、記録を消す。確認のモーダルを出す |

- どちらも、その後に同期を要求する。解決は次の同期で、ほかの端末にも届く
- ファイルがもうない記録は、解決済みとして自動で消す。一覧を数え直すとき（起動時と、同期で作業ファイルが変わったとき）に行う
- 期間が過ぎても自動では消さない。黙って消すのは「黙って捨てない」に反する。解けない記録が増えないことは、上の 2 つのボタンと、ファイルがないときの自動の削除で保証する
- 読めない記録と、知らない `schemaVersion` の記録の扱い:
  - 一覧に「読めない記録」として出し、`Delete record` だけを付ける
  - 自動では消さない。新しい版のプラグインが書いた記録かもしれないため
  - 同期は止めない（ADR-0089 の 7。想定できる失敗は状態として扱う）
  - 同期の記録（`log.jsonl`）に `warn` で残す

### 4. 共通祖先が複数あるときは、祖先が一致するパスだけを祖先として使う

- `mergeBase()` は共通祖先をすべて返す。1 つなら今と同じ
- 複数のときは、マージに使う祖先のツリーを、パスごとに次の規則で作る
  - すべての祖先で同じ内容（または、すべての祖先にない）パスは、その内容を祖先とする
  - 祖先によって内容が違うパスは、祖先にないものとして扱う
- 祖先にないパスで両側が違えば、今の規則で衝突として残す（マーカー、別名の版、編集側を残して記録）。片方にしかなければ、それを採る。どちらも内容を捨てない。代わりに、本来は衝突でないものが衝突になることがある（まれな場合なので、それでよい）
- 共通祖先が複数だったことを、同期の記録に `warn`（`multiple-merge-bases`、祖先の数）で残す
- 共通祖先がない（履歴がつながっていない）ときは、今と同じく空の祖先でマージする。これも同期の記録に `warn` で残す

### 5. 中断からの復旧の残りを、再現テストで確かめる

第 2 段階で、作業ファイルを書く途中（`moveTo`）の復旧を入れた（ADR-0089 の 5）。ほかの工程で落ちたときに、次の同期が最初から安全にやり直せることを、テストで確かめる。

| 落ちる位置 | 期待 |
|---|---|
| snapshot で、一部のファイルをインデックスに入れた後、コミットの前 | 次の snapshot が残りを入れて 1 つのコミットにする。内容を失わない |
| マージのコミット（と記録）を作った後、`moveTo` の前 | ブランチも作業ファイルも変わっていない。次の同期がマージをやり直す。使われないコミットのオブジェクトが残るだけ |
| push の途中（送ったが応答を受け取る前） | 次の fetch で、リモートが送った版を指していれば最新として扱う。指していなければもう一度送る |

テストで期待と違う振る舞いが見つかったら、その工程に ADR-0089 の 7 の順（記録を書いてから作業ファイル、ブランチは最後）を当てはめて直す。

## 理由

- 中身から分かる衝突まで記録すると、ほかの経路でマーカーを消したときに記録と食い違う。ほかの経路とは、テキストエディタ、PC の Git CLI、ほかの端末での手の解決など。中身から分からないものだけを記録すれば、記録は「中身では見えない意図」だけを持つ。食い違いの検出も解決もいらない
- 1 件 1 ファイルで書き換えない形にすると、Git の通常のマージだけで記録が衝突しない。JSONL を端末ごとに追記する形（`updates/` など）も衝突しない。ただ、解決の状態を全端末の全期間の記録から組み立てる必要がある。今回は「ファイルがあれば未解決」で足りる
- マージのコミットに入れると、マージと記録が必ずそろう。作業ファイルに書いて次の snapshot でコミットする形だと、その間に落ちたとき、または送る前にほかの端末がマージしたときに記録が抜ける
- 隠しフォルダにすると、ノートの一覧と検索を汚さない。手で開いて書き換えられることも減る。同期は `.obsidian` と同じく `.gitignore` に当たらない隠しパスとして普通に行う
- 祖先が一致するパスだけを使うのは、正しさよりも安全を取るため。どの祖先を選んでも、片方の変更を黙って戻す可能性がある。祖先から外すと、最悪でも衝突として両方が残る

## 却下した案

- **記録を `.git/` の中（端末だけ）に置く**: 同期に入らないので、マージした端末でしか見えない。ほかの端末で削除した人が、編集側が残ったことを知る手段がない
- **すべての衝突を記録する**: 上の理由のとおり、中身と食い違う。今の走査で足りているものを二重に持つ
- **マージのコミットメッセージから組み立てる**: すでに `Conflicts:` を書いている。ただ、解決の状態を表せない。履歴を全部たどる必要がある。メッセージの書式をデータの形式として固定することにもなる
- **1 つのファイル（`conflicts.json`）にまとめる**: 2 台が同時にマージすると、同じファイルを両側で書き換えて衝突する。JSON はマーカーを入れられないので、記録自体が別名の版になる
- **Git と同じ再帰マージ（祖先どうしをマージして仮の祖先を作る）**: 仮の祖先の衝突を、マーカー入りの内容として持つ必要がある。今の、別名の版と記録を作るマージとは合わない。まれな場合のために実装とテストを大きくする理由がない
- **一定の期間が過ぎた記録を自動で消す**: 黙って捨てるのと同じになる

## 影響

- `src/git/engine.ts`:
  - `mergeBase()` が祖先をすべて返す
  - 複数のときの祖先のツリーの組み立てを足す
  - マージの結果のツリーに記録を入れる
- `src/merge/tree-merge.ts`: 記録の対象の判定を足す。`.pkm-git/` を除く
- 新しい `src/git/conflict-records.ts`: 記録の形、ID、読み書き、検証
- `src/main.ts` と `src/obsidian/modals.ts`: 一覧に記録の行と `Keep` / `Delete` / `Delete record` を足す。一覧を数え直すときに、ファイルのない記録を消す
- `src/git/`・`src/obsidian/` を変えるので、セキュリティチェックの対象（記録のパスの検証。`assertSafeWorktreePath` を通す）
- 旧版のプラグインとの混在:
  - 旧版は `.pkm-git/` を普通のファイルとして同期する。記録は作らず、一覧にも出さない
  - 記録は書き換えないので、旧版がマージしても衝突しない
  - 旧版で起きた削除と編集の衝突は、今と同じく記録されない
- 移行はない。記録は、新しい版で衝突が起きたときだけできる
- `.kit/changes/` に書く（新しい隠しフォルダが Vault にできること）
- 文書:
  - [ノートの書式と配置](../../../../.claude/docs/vault-conventions.md) の配置の表に `.pkm-git/` を足す
  - プロダクトの [PKM Git](../../../harness/docs/product/surfaces/git-sync.md) と [同期と snapshot](../../../harness/docs/product/concepts/sync-snapshot.md) に、記録と解決を足す
- 受入テスト（本物の git http-backend を相手にする）:
  - 削除と編集の衝突で記録ができ、マージのコミットに入る。ほかの端末に届く
  - 再起動（プラグインを作り直す）後も一覧に出る
  - `Keep` と `Delete` で解決し、ほかの端末からも消える
  - 2 台が同時に解決しても衝突しない
  - ファイルがない記録が自動で消える
  - 読めない記録で同期が止まらない
  - criss-cross の履歴で、上の例が衝突として両方を残す
  - 上の 5 の 3 つの落ちる位置
- 新しい依存はない
- 第 5 段階（解決 UI と履歴ビュー）は、この一覧と記録の上に作る
