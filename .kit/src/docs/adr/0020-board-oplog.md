# ADR-0020: ボードの状態を端末別の操作ログに置く

- 状態: 承認
- 日付: 2026-11-01

## 背景

ADR-0014 はボードの状態をデイリーノートの frontmatter の `board` に置いた。理由の 1 つは「ファイルは日ごとに分かれるので、端末間でぶつかりにくい」だった。

しかしボードを触るのはたいてい当日で、2 台が同じファイルを編集する。同期は手動の pull / push なので、同期していない時間も長い。実際のマージ処理（`mergeText`）で試した結果は次のとおり。

- それぞれ issue を追加する、別の routine を完了する、routine の完了と別の issue の持ち越し、隣の行のカードを移す、同じ日のノートを新規作成する: すべてコンフリクトする。マーカーが frontmatter に入って YAML が読めなくなり、そのボードは画面から消える
- 一方が i-8 をボードから外し、他方が i-8 を持ち越す: マージは成功するが `carried` が `issues` に含まれない状態になり、以後 `parseBoardForWrite` が書き込みをすべて拒否する

Issue #9 の `updated` の自動付与を入れると、2 台が同じ日に編集したノートは必ずコンフリクトするようになる。

## 決定

### 保存先と形式

ボードの正本を `board/<端末名>/YYYY-MM.jsonl` の操作ログにする。月は対象のボードの日付の月。書くのはその端末だけで、追記だけを行う（行の書き換え・削除はしない）。

```json
{"id":"bo_0123456789","at":"2026-11-01T00:00:00.000Z","date":"2026-11-01","op":"add","task":"i-6"}
```

| op | 追加の欄 | 再生したときの効果 |
|---|---|---|
| `add` | `task` | `issues` の末尾に足す（あれば順番を変えない）。`carried` から外す。締めを解く |
| `remove` | `task` | `issues` / `carried` / `groups` から外す |
| `place` | `task`, `group`（null で未分類） | `groups` を変える |
| `routine` | `task`, `result`（`closed` / `canceled` / null） | `routines` を変える |
| `carry` | `task` | `carried` に足す。`issues` にないなら無視する |
| `close` | `tasks`（締めたときの `issues`） | 締める |
| `reopen` | なし | 締めを解く |

### 状態の作り方

- 全端末のログを読み、日付ごとに `at` → 端末名 → 行番号の順で再生して `BoardState` を作る。保存しない（ADR-0002）
- どの順で再生しても `BoardState` は常に有効になる。同じ項目への操作は後の操作が勝つ
- `at` は UTC のミリ秒まで。書くときは `max(今, そのボードで見えている最新の at + 1ms)` にする。時計がずれていても、見えていた操作より後ろに並ぶ
- 読めない行は問題（`Problem`）として報告し、その行だけ飛ばす

### 締める

- 本文の `## Task board` に要約を書いてから、`close` を追記する。途中で失敗しても、もう一度締めれば要約は置き換わる
- 再生の後で、`close` の `tasks` にない issue がボードにあれば締めを解く。他の端末が締めるより前に、同期していない端末で足した issue を見落とさないため
- デイリーノートがなければ作る。`type` と `created` を入れる（`newDailyContent`）。ボードの操作だけではノートを作らない

### 既存の `board`

デイリーノートの frontmatter の `board` は読み取り専用の初期状態として扱い、その上にログを再生する。プラグインはもう書かない。既存のノートは書き換えない。

## 理由

- 1 つのファイルに書くのが 1 台だけならコンフリクトしない（ADR-0004）。Git CLI を含むどの経路で同期しても同じ
- 操作は順序だけで統合できるので、マージの結果が無効な状態にならない
- ボードの状態を frontmatter から出すので、Issue #9 の影響を受けない
- 要約はデイリーノートに残るので、締めた後の記録は今までどおり人も LLM も読める

## 却下した案

- **frontmatter のまま、vault-git に `board` を理解するマージを入れる**: vault-git がタスクの形式を知ることになる。Git CLI のマージには効かない
- **日付ごとに 1 つの JSON（`board/2026-11-01.json`）に置く**: 2 台が同じファイルを編集するのは変わらず、コンフリクトするとリモート優先になる（ADR-0014 と同じ理由）
- **issue の frontmatter に載せた日付を持たせる**: routine の結果と締めの置き場所が別に必要になる。issue が同じ行でぶつかりやすくなる
- **既存の `board` を一度だけログに移す**: デイリーノートの変更と移行スクリプトが必要で、読み取りの互換のほうが安全で小さい

## 影響

- ADR-0014 の「ボードの状態」の節を置き換える。DailyTaskView、グループ、タイマーなどの節は残る
- ボードの操作に端末名が必要になる（タイマーと同じ）
- 同じ端末名を 2 台で使うと、ログがコンフリクトしてローカル版が別名ファイルに逃げ、その操作が読まれなくなる（worklog と同じ制約）
- 締める前の状態は、ログを再生しないと分からない。人が手で直すことは想定しない
- 2 台が同じボードを締めると、要約が違う場合に本文でコンフリクトする。マーカーは本文に入るので、ボードの状態には影響しない
- ログは圧縮しない。1 日数十行の想定で、全件の再生で足りる
- Issue #7（MCP）の「ボードの状態をデイリーノートから移す」案はこれで決まる。AI からの編集も操作の追記になる
