# 2026-11-11 スライド（#117）

## 質問

- 起きたこと: ADR-0117 の承認を尋ねたとき、ユーザーが「ずっと気になっていたが、ts ではなく mjs を使っているのはなぜか」と質問した。理由は 2 つの場所に分かれて書いてある（`.claude/scripts/*.mjs` は ADR-0005 の却下した案、`.kit/bin/*.mjs` は ts のソースを束ねた成果物で ADR-0009 と plugin-development.md）。ユーザーが読む入口（README、ハーネスの設計）からは辿れない。ADR-0005 の理由（古い Node でも動かす）は、mise.toml が Node 26 を指定し、Node が ts をそのまま実行できる今も成り立つかを見直していない
- 改善案: 上流のハーネスの設計に「mjs が 2 種類ある（手で書く検査のスクリプトと、ts から作る CLI）」と理由を 1 か所に書く。ADR-0005 の「ts で書かない」理由を、今の Node の版で見直す

## つまずき

- 起きたこと: デザインの調査で、論文の本文を置くサイト（frontiersin.org、bioone.org など）がクラウドの環境から開けず、検索結果の要約までしか確かめられなかった
- 改善案: 調査が要る作業では、開けないサイトがあることを先に伝え、外で調べるためのプロンプトを渡す手順を dev-plan か research-report に書く

## 訂正

- 起きたこと: 調査の結果を、検索の要約のまま ADR の根拠の表に並べていた。ユーザーが一次資料の本文で確かめ直した結果を渡し、「確かめ方が未確認・要旨だけ・二次資料の行は規則に採らず、確度が高・中の行だけを根拠にすること。食い違いと経験則は注意書きに反映すること」と指示した。Mayer の原則、文字の大きさの 1/25、Cleveland & McGill などは、採れない根拠だった
- 改善案: 規則の根拠にする調査では、主張ごとに確かめ方と確度を書き、採る基準を先に決める手順を research-report（fact-check か landscape）か dev-plan に書く。slide スキルの evidence.md の「採る基準」を、ほかのスキルの根拠の一覧（write-for-reader、research-report）にも当てはめるかを見直す

- 起きたこと: ADR の承認を尋ねた後、ユーザーは「スライド作成時のユーザ体験にこだわって。Claude Code と話し合いながら作成 → スライドを開いてユーザーがレビュー → Claude Code で修正、の繰り返し」と指示した。ADR は機能の一覧（一覧・Slide Show・PDF・コメント）を並べていて、作る → 見る → 直すの往復を体験として設計していなかった（直した後にどこが変わったかを知らせる、番号で返す、再読み込みでレビューの画面に戻る、などが抜けていた）
- 改善案: 機能を足す ADR には、機能の一覧の前に、使う人の 1 周の流れ（何をして、次に何を見るか）を書く節を置く。dev-plan の計画の項目に足す

## つまずき

- 起きたこと: security-scan が、ブラウザで動くページ（スライドの閲覧の画面）の localStorage と、`src/` の中の `node:crypto` を指摘した。前者は許可の一覧に理由つきで足し、後者はハッシュの計算を CLI から渡す形に直した。`src/` に Node の API を置かない決まりは plugin-development.md にあるが、プラグインではないパッケージ（CLI だけ）にも当てはまるとは書いていない
- 改善案: plugin-development.md に「`src/` は Node の API を使わない。CLI だけのパッケージも同じ」と書く

- 起きたこと: 発表者ビューの同期で、`file://` の窓どうしの `postMessage` の送り先に `location.origin`（"file://"）を渡すと届かなかった。送り元の窓の同一性（`e.source === 開いた窓`）も成り立たなかった。プレビュー（Playwright）で見つけた
- 改善案: plugin-development.md の slide の節に書いた（`file://` では送り先を絞れない。ビルドの ID と整数の検査で受ける）
