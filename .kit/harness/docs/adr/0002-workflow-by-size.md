# ADR-0002: 工程は変更の大きさで分ける。wiki の操作は main に直接コミットする

- 状態: 承認（一部置換: ADR-0015）
- 日付: 2026-10-31

## 背景

テンプレートは、すべての作業で、仕様 → Issue と計画の承認 → PR のレビューの 3 箇所で人間が確認する。1 人で開発する場合、小さな修正にまでこれを課すと重い。

一方、このリポジトリの main には、各端末の Vault Git が snapshot を直接 push している。LLM による wiki の操作（取り込みや整理）も、人のノートと同じく頻繁に起きる。

## 決定

作業を 3 種類に分ける。詳細は [進め方](../workflow.md)。

| 作業 | 工程 | 人の確認 |
|---|---|---|
| 大きい変更: 新しいプラグイン・機能、設計の変更、ハーネスと wiki の仕組みの変更 | ADR（必要なら）→ Issue に計画 → 承認 → ブランチで実装 → PR | ADR、計画、PR |
| 小さい変更: 不具合の修正、文言、設計を変えないリファクタリング | チャットで計画を伝えて確認 → ブランチで実装 → PR | 計画（チャット）、PR |
| wiki の操作: 取り込み、回答の蓄積、lint、デイリーノートの整理 | スキルに従って main に直接コミット | なし（git の履歴で戻せる。違反は CI が検出する） |

- ADR は「ちゃんと作る」。設計判断を含む変更では、計画より先に ADR を書いて合意する（[ADR を書く条件](README.md)）
- どちらか迷ったら大きい変更として扱う

## 理由

- 間違った方向の実装を読む時間を省くため、大きい変更は計画の段階で止める。テンプレートと同じ考え方
- 小さい変更で Issue を切ると、1 人では書くことと読むことが同じ人になり、手間だけが増える
- wiki の操作を PR にすると、取り込みのたびにマージが要り、モバイルから使う Vault に反映されるまでが遅れる。人のノートは追記しかしない（[ADR-0004](0004-human-notes-append-only.md)）ので、間違っても git で戻せる

## 却下した案

- すべて PR にする: wiki の操作が溜まり、Vault の利用が止まる
- wiki の操作を内容で分ける（追加は直接、書き換えは PR）: 判定が曖昧で、エージェントが毎回迷う

## 影響

- main への push をツールの権限で拒否しない。代わりに、開発の作業では main に push しないことを手順に書き、wiki の操作の違反は CI で検出する
- クラウドのセッションなど、決められたブランチにしか push できない環境では、wiki の操作もそのブランチから PR にする（件名は同じ `wiki(...)`）
