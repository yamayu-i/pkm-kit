# ADR-0012: ユーザー体験に責任を持つ責務（プロダクト）をハーネスに置く

- 状態: 承認
- 日付: 2026-11-07

## 背景

上流のハーネスには、作れるかを確かめる仕組み（テストを先に書く、`pnpm check`、ADR、移行の fixture）と、見た目とアクセシビリティを守る仕組み（`.kit/src/docs/design.md`、トークン、`preview:ui` の描画した画面の検査）がある。一方で、次のものを受け持つ場所がない。

- **価値**: 誰のどんな場面の困りごとを解くか。依頼はチャットで届き、そのまま解決策（ADR）になる。上流の気づき 4 件のうち 3 件は、大きい変更で Issue の工程を飛ばしたことだった
- **全体の見通し**: 1 つの体験は複数のプラグインをまたぐ（リボン → Daily → ボード → issue 画面 → ボードの締め → デイリーノート）が、それを通して書いたものがない
- **今の体験の正本**: ADR は書き換えないので、今の振る舞いは ADR を重ねて読まないと分からない。View の一覧（`.kit/src/docs/adr/0009-views.md`）は 7 つの ADR に一部置換されている
- **概念と用語**: status、do date、deadline、soft deadline などの意味と、UI の表記・データのキー・文書の用語の対応を決めた場所がない。改名（`.kit/src/docs/adr/0032-action-names-soft-deadline-board-delegate.md`）はその都度判断している
- **出した後の評価**: kit-review がプラグインについて見るのは、開発の流れ・検査で止まった問題・不具合の報告で、体験が良くなったかは見ていない

体験の設計の理論で言うと、Cagan の 4 つのリスク（価値・使いやすさ・作れるか・続けられるか）のうち、価値と続けられるかに持ち主がいない。Garrett の 5 つの層（戦略・範囲・構造・骨格・表面）のうち、表面と骨格の一部しかない。ISO 9241-210 の工程（使われる状況の理解 → 要求の明確化 → 案 → 要求に照らした評価）のうち、最初と最後がない。

## 決定

### 1. 責務

上流のハーネスに、ユーザー体験に責任を持つ責務（以下「プロダクト」）を置く。

| 担い手 | 受け持つこと |
|---|---|
| 人 | 価値の最終判断。戦略（ビジョン、望む成果、原則）の承認。機会を解くかどうかの決定 |
| Claude | **機会を自分で見つける**。体験を定義する（場面・概念・今の体験の正本を保つ）。全体の一貫性を点検する。出した後に評価する |

- 機会（困りごと）を見つけることと、解決策を決めることを分ける。Claude は機会を自分で起票してよいが、解決策は通常の工程（[進め方](../workflow.md)）で人の承認を得る
- 使う人は、当面は**本人だけ**とする（PC・タブレット・スマホ。task-coach や MCP を通した体験も本人の体験として扱う）。他の人を含めるときは、この ADR を見直す
- 上流は公開なので、機会や文書には個人のノートの内容を書かない。本人の使い方から見つけた困りごとは、一般的な場面として書く

### 2. 文書の置き場所と構成

`.kit/harness/docs/product/` に置く。`docs/` の下なので、目次から辿れるか・リンク切れがないかを `check-docs.mjs` が検査する。

```
.kit/harness/docs/product/
├─ README.md        入口。責務、文書の種類の表、書き方と育て方の規則
├─ strategy.md      ビジョン、使う人、望む成果（3 つ以内）、原則、やらないこと、当たり前の品質
├─ jobs/            場面（ジョブストーリー）。1 場面 = 1 ファイル
│  ├─ README.md     一覧と書式
│  └─ <slug>.md
├─ concepts/        概念。1 概念 = 1 ファイル
│  ├─ README.md     一覧、書式、用語の対応表（UI の表記・データのキー・文書の用語）
│  └─ <slug>.md
└─ surfaces/        今の体験の正本。1 つの面（View、画面、コマンド、MCP、セットアップ）= 1 ファイル
   ├─ README.md     一覧と書式
   └─ <slug>.md
```

| 種類 | 1 ファイルに書くこと |
|---|---|
| jobs | 状況・したいこと・期待する結果（「〜のとき、〜したい。〜できるように」）、今の流れ（通る面へのリンク）、関わる概念、うまくいっている兆し、知られている困りごと |
| concepts | 目的、持つ状態、操作、使い方の筋道（Jackson の概念設計）、UI の表記・データのキー |
| surfaces | 今の振る舞い、通る場面と使う概念へのリンク、根拠の ADR |

構成を変えずに育てられるように、次の規則にする。

- **増えるのはファイルの数**。1 単位を 1 ファイルにするので、文書が大きくなっても既存のファイルを分割しない。1 単位が大きくなったら単位を分け、元のファイルは親の単位として短く残す（リンクが切れない）
- **パスは変えない**。ディレクトリの中はフラットにし、まとまり（task、template、git、kit などの領域、場面の時間帯）は README の一覧の見出しで表す。サブフォルダで分けない
- slug は英語の短い名前（例: `task-daily-board`）。領域を接頭辞にしてよい。番号は振らない（場面や概念には順序がない）
- **新しい種類**（たとえば兆しの定義）が要るときは、ディレクトリを足して `product/README.md` の表に 1 行足す。既存の種類には触れない
- `strategy.md` は分けない。長くなるのは戦略が絞れていない兆候として扱い、削る（300 行の警告に任せず、200 行以内を目安にする）
- 各種類の書式（見出しの並び）は、その種類の `README.md` に書く
- 見た目の規則（表面の層）は今までどおり `.kit/src/docs/design.md` に置き、`product/README.md` からリンクする

### 3. 機会の置き場所

機会は GitHub の Issue に置き、ラベル `ux` を付ける。

- 本文: 場面（`jobs/` へのリンク）、困りごと、根拠（何を観測したか）。解決策は候補として書いてよいが、決めない
- 望む成果（`strategy.md`）ごとに親の Issue を作り、機会をその sub-issue にする（Torres の機会ソリューションツリー）。解くことが決まった機会は、通常の工程の Issue につなぐ

### 4. 機会を自分で見つける手順

上流の手順として `product-review` を足す（`.kit/harness/skills/product-review/`）。kit-review と同じ月 1 回に行い、次の観測から機会を探して `ux` の Issue にし、起票したものをユーザーに伝える。

| 観測 | 見方 |
|---|---|
| ユーザーの依頼 | 依頼の背後にある状況と、同じ場面の過去の依頼 |
| 場面の歩き通し | `jobs/` の各場面を `surfaces/` に沿って辿る（認知的ウォークスルー）。手数、迷う分岐、状態の分かりにくさ（Norman の 2 つの溝） |
| 画面の点検 | `preview:ui` のスクリーンショットを Nielsen の 10 のヒューリスティクスで見る |
| 概念の一貫性 | `concepts/` と、UI の表記・文書・データのキーの食い違い |
| 変更の繰り返し | 短い期間に同じ面を何度も変えたもの（git の履歴と ADR の一部置換） |
| 上流の気づきとエスカレーション | kit-note、ラベル `escalation` のうち体験に関わるもの |

Claude の点検は、本人が実際に使うことの代わりにはならない。根拠の弱い機会は、そう書いて起票する。

### 5. 段階

| 段階 | 内容 | 決め方 |
|---|---|---|
| 1 | `product/` の初版（既存の ADR から逆算して書く）、`product-review`、目次へのリンク、ラベル `ux` | この ADR |
| 2 | dev-plan（利用者に見える変更は、ADR の前に場面・成功の兆し・やらないことを書く）、dev-pr（体験の点検、`surfaces/` の更新）、プラグインの ADR のテンプレート | この ADR の方針で、段階 1 の後に計画を立てる |
| 3 | 子の記録（worklog、statuslog、ボードの操作ログ、`wiki/feedback.md`）から体験の兆しを集計し、エスカレーションで上流に返す | 子のものと移行に関わるので、別の ADR にする |

## 理由

- 価値と体験の判断を、実装の工程（dev-*）とは別の持ち主に置くと、依頼から解決策へ直行せずに、場面と困りごとを先に見られる
- 機会を Claude が自分で見つけるのは、利用者が本人 1 人で、困りごとを言葉にする前に慣れてしまうため。見つけるのと決めるのを分ければ、人が知らないうちに仕組みが変わることはない（[ADR-0006](0006-self-improvement-loop.md) の、提案までにする考え方と同じ）
- 1 単位 1 ファイルにすると、PR どうしが同じファイルの同じ場所を書き換えにくい（CHANGELOG や ADR の一覧では、それでぶつかった）。ADR と同じく、規模が大きくなっても構成を変えなくて済む
- 領域でサブフォルダを分けないのは、場面がプラグインをまたぐため。領域で分けると、場面の置き場所が決まらないか、分け直すときにパスが変わる
- 今の体験の正本を ADR と分けると、ADR は「なぜ」の履歴、`surfaces/` は「今どうか」の正本として、それぞれの書き方の規則を守れる

## 却下した案

- **PdM 役のサブエージェントを常に置く**: `.claude/agents/` は子にも届く。上流の手順は Skill として読み込まれない前提で作っている。文書と確認地点がなければ、役だけ置いても判断の基準がない
- **`product/` をフラットなファイル（`jobs.md`、`concepts.md` など）にする**: 場面や概念が増えると 1 ファイルが大きくなり、ある時点でディレクトリに分けることになって、パスとリンクが変わる
- **領域ごとのサブフォルダ（`jobs/task/`、`jobs/template/`）**: 場面がプラグインをまたぐ
- **機会をファイル（`product/opportunities/`）に置く**: 起票・解決・却下の状態の移り変わりと、親子のつながりは Issue のほうが扱いやすい
- **他の人も使う人に含める**: 本人以外の使い方の観測がない。根拠のないペルソナを作ることになる

## 影響

- `.kit/harness/CLAUDE.md` の「作業の流れ」と「文書の地図」に 1 行ずつ足す（100 行以内に収める）
- [上流のハーネスの設計](../harness.md) に、プロダクトの責務と `product/` を足す
- GitHub にラベル `ux` を作る
- 子のものには手を入れない（移行はない）。`product/` は上流のものとして子にも届くが、子では使わない
