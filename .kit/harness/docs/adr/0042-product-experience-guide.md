# ADR-0042: 体験定義と仕様を、実装の画面例付きの HTML として決定論的に配布する

- 状態: 承認
- 日付: 2026-11-15

## 背景

[Issue #42](https://github.com/yamayu-i/pkm-kit/issues/42)。`product/` の Markdown は子にも届くが、隠しフォルダなので Obsidian で読めない。HTML の閲覧（プラグインの ADR-0037）と共有用の書き出し（ADR-0044）は実装済みだが、定義書の生成と配布はない。

利用者から、次の要件が加わった。

- 人が理解しやすいユーザー体験定義書であり、現在の振る舞いを確かめる仕様書でもあること。網羅的かつ丁寧に、実際の UI を見ながら読めること
- 普遍的な HTML の構造・レイアウト・整形は、先に決定論的に構築できるよう準備し、更新のたびに LLM が書き直してトークンを浪費しないこと

推奨は、**Markdown の正本＋共通の生成器＋実装から撮る画面例**の組み合わせ。子には `pkm-guide/user-experience.html` と画像が merge で届く。子に npm・ブラウザ・LLM は不要。

主な負担は、現在不足している仕様の説明と画面例を初回に揃えること、以後 UI を変えた際に画像も更新すること。画面例は合成データによるプレビューであり、Obsidian 本体の表示を完全には再現しない。この前提を各画像で明示する。

## 決定

### 1. 正本と、書く仕事・生成する仕事

体験・用語・振る舞いの正本は引き続き `.kit/harness/docs/product/`。初回の対象は現時点の全 62 文書（戦略、入口、11 の場面、19 の概念、27 の面、各一覧）で、取りこぼさず変換する。さらに各プラグインの View・コマンド・ダイアログの登録を正本と照合し、未記載の面（Tasks Now 等）も補う。以後、対象内に文書が増えれば自動的に含める。

| 人・LLM が判断して正本に書くもの | コードが生成するもの |
|---|---|
| 場面の目的、操作の意味、振る舞い、失敗時の扱い、制約、説明に必要な例 | 章立て、全体と章内の目次、見出し ID、相互リンク、用語索引、場面と画面の対応、前後の章への案内、出典、共通 CSS、画像の配置 |
| 画面例の目的、操作前の条件、注目点、結果の説明 | 実装コンポーネントの描画、ライト／ダーク・広幅／狭幅の画像、入力の指紋、欠落の一覧 |

生成済み HTML・繰り返しのレイアウト・画像の base64 を LLM に出力させない。新しい場面や画面は、小さな Markdown と画面の対応定義を追加して同じ生成器で作る。生成・検査の標準出力は件数、差分のある原本、直す手順だけとし、本文や画像データを大量に出さない。

### 2. 読み進め方と仕様の詳しさ

読み方の案内 → 全体像と戦略 → 目的から読む場面 → 画面と操作 → 概念・用語・データの対応 → 根拠、の順にする。場面から関係する画面へ、画面から用語へ、定義書の中だけで移動できるようにする。既存の文書を短い要約に置き換えず、全文を読める形で収録する。

- 画面の説明には、開き方、表示と状態、操作と結果、入力と制約、保存される内容、自動処理、失敗時と戻し方、端末による違いを揃える。該当しない観点は理由を書く
- 概念には UI の表記・ファイルのキー・型・単位・既定値・制約・状態の対応を、該当する範囲で書く。履歴上の ADR の決定と現在の実装を混同しない
- 場面には、始める条件、手順、期待する結果、つまずいたときに戻る場所を揃える
- 正本と実装を照合する。例えば issue 画面の Parent / Children は現在のサブイシューへの変更と食い違うので、原本を直してから収録する
- UI が存在しない MCP・AI の手順にも、入力例・結果・失敗時の扱いを載せる。UI の画像を無理に付けない
- 内容の網羅と画面例の網羅を別々に一覧化し、読者にも分かるようにする。自動検査は形式上の欠落を止め、説明の正しさは実装との照合で確かめる

### 3. 共通の HTML の仕組み

`.kit/src/packages/product-guide/` に生成器・テンプレート・CSS・画面対応定義・プレビューを置き、CLI を `.kit/bin/product-guide.mjs` にビルドする。

- `build`: 正本、CSS、画面対応定義、検証済みの画像から、HTML を生成する
- `check`: 入力と生成物の一致、文書・見出し・画像の網羅、リンク、画像の指紋とハッシュを検査する。書き込まない
- `inventory`: 原本と必要な画面例、足りない項目を一覧にする。LLM は必要な原本だけを読んで直す
- `capture`: 上流の開発環境だけで画面例を描画し、画像と対応する記録を生成する

Markdown は固定版の既存パーサーをビルド時依存として採用して CLI に束ねる。パーサーを独自実装する手間と、不完全な変換による箇条書き・表・コードの欠落を避けるため。追加する依存は実装前に版と必要性を明示する。子で実行する CLI は Node だけで動く。

本文、入れ子のリスト、表、コード、引用、強調、画像とリンクを保ち、本文中の HTML は安全な文字として扱う。見出し ID は文書のパスと見出しから生成し、重複を解決する。product 内のリンクは内部アンカー、根拠の ADR などは GitHub の該当ファイルへのリンクとし、隠しフォルダへ遷移させない。壊れた内部リンクと未対応の書式は検査で知らせる。

時刻・マシン固有のパス・現在の git HEAD に生成結果を依存させない。同じ正本・生成器・画像からは同じバイト列を作る。画像は別ファイルとし、HTML に巨大な文字列として埋め込まない。

### 4. 実装の UI を見せる

画像は実際のコンポーネントと本番の CSS を使い、Obsidian の API だけをモックにして撮る。既存の pkm-task / pkm-html / pkm-diagram / slide のプレビューを再利用し、不足している面にはプレビューを足す。図として描き直した架空の UI を実装の画像として扱わない。

- Today の各段階、ボード、issue とサブイシュー・Timeline、routine、一覧とサイドバー、入力ダイアログ、ノートの作成・一覧・ヘッダー、Updates、HTML、スライド、図、リボン、View 選択、Git の設定・同期・衝突・履歴などを、各面の画面対応定義で管理する
- 各視覚的な面には最低 1 つの画像を必須とする。主要な状態の違い（空、データあり、編集中、実装されている失敗状態等）も定義し、画像や説明がない状態を黙って省かない
- 時計・タイムゾーン・ロケール・合成データ・フォント・アニメーションを固定する。既存のプレビューは現在時刻を使っているため、撮影の前に時計を固定する
- 各画像には、画面名、条件、注目点、操作の結果、実装から描画したこと、Obsidian 本体を含まないことを表示する。画像の代替テキストも付ける
- ライト／ダーク・広幅／狭幅を撮り、狭い画面では文字が潰れる縮小画像を強制しない。全体を見られる画像へのリンクを用意する。ライト／ダークは本文と画像で合わせる
- 画像ごとに、関連するソース・共有部品・CSS・トークン・依存の固定ファイル・fixture・撮影設定を入力の指紋として記録する。画像のハッシュも持ち、差し替えと古い画像を Node だけの検査で検出する
- 上流 CI は固定した Chromium とフォントで再描画し、画像の再現性とレイアウトを検査する。OS の違うローカル環境との PNG の完全一致を前提にしない

Obsidian 本体の CSS・実行順・モバイル固有の挙動はプレビューで完全には確かめられない。実機で試す項目を PR に明記し、マージ後に確認する。

### 5. 配置と所有、子への配布

`pkm-guide/user-experience.html` と `pkm-guide/ui/**` を上流が持つパスにする。ディレクトリ全体を予約せず、生成物に必要なパスだけを `.kit/owned-paths.json` に追加する。

- HTML と画像は上流で生成してコミットする。新しい子は clone、既存の子は vault-upgrade の merge で最新版を受け取る。setup や移行のたびにコピーを作らないため、写しが古くなる経路を増やさない
- すでに同じパスに子のファイルがある場合は通常の git の衝突として解決し、setup で上書きしない。取り込みの案内に退避の手順を書く
- 子の所有物や設定を変えないので、移行は付けない。`setup` と vault-upgrade の fixture で、配置と所有の検査が通ることを確かめる
- Obsidian のファイル一覧で `pkm-guide/user-experience.html` を開く。README と子向けの案内に入口を載せる
- ノートではなく HTML なので、frontmatter・wiki の索引・updated の付与の対象にしない

### 6. テーマ、安全性、表示の検査

プラグインの ADR-0037 / 0044、デザインルールの HTML の節に従う。Vault 内の HTML はトークンの値を埋め込まず `var(--vt-…)` で書き、pkm-html がテーマを適用する。外部へ渡すときは既存の Export HTML to tmp/ を使う。

- JavaScript、外部 CSS・フォント・画像の読み込みを使わない。目次・アンカー・details 等は HTML と CSS だけで成立させる
- 表とコードは各領域で横スクロールでき、本文全体は狭幅で横に溢れない。見出し階層、代替テキスト、キーボード、コントラストを検査する。印刷でも読める CSS を持つ
- HTML の CSS に既存のデザイン検査をかけ、pkm-html のサニタイズ後にも目次・画像・リンク・テーマが成立することを確かめる
- `.claude/scripts/verify.mjs` に CLI の `check` を組み込み、子の Node だけの環境でも古い HTML・画像・原本の欠落を止める。ブラウザを使う描画検査は上流の CI で行う

## 理由

- 決まった書式を再生成する仕事から LLM を外し、意味のある説明の追加と実装との照合に集中できる
- 既存の文書を唯一の正本として、更新の二重管理と意味の欠落を防げる
- 読み進める入口と全件を引く入口の両方があり、体験の理解と仕様の確認を両立できる
- 静的な生成物を merge で配れば、PC とモバイルのどちらでもビルド不要で読める

## 却下した案

| 案 | 却下する理由 |
|---|---|
| LLM が毎回 HTML 全体を書く | 共通の装飾にトークンを使い、原本とのずれと欠落を機械で検出しにくい |
| Markdown をそのまま連結するだけ | 読む順序・相互参照・画面例が不足し、仕様の抜けも隠れてしまう |
| 子の setup / upgrade で毎回 HTML を生成する | 子の動作にビルド環境や画像生成の仕組みが必要になる |
| iframe の中で UI を動かす | pkm-html のスクリプト禁止と衝突し、定義書を読むためにアプリ状態が必要になる |
| 本番 Vault の画像を使う | 個人のノートが公開物へ入るため。合成データで実装を描画する |
| Markdown パーサーを一から実装する | 既存書式を正しく維持する作業が増え、今回のトークン節約の方針にも合わない |

## 影響と戻し方

新しい生成パッケージと CLI、可視の配布ディレクトリ、画面例、検査、開発・更新手順が増える。正本の不足と食い違いも今回の対象内で修正する。既存の UI の振る舞いはこの Issue のためには変更しない。

PR #168 が issue の本文表示・Pick 操作と関連文書を変更中。画像と記述は PR 提出時の main に合わせ、同じ箇所の変更を取りこぼさない。

取り消す場合は、生成物・所有パス・検査・案内を削除する PR で戻せる。子のノートと設定の移行は不要。正本に加えた、現状を正しく説明する修正は残せる。
