# ADR-0056: 並行する PR がぶつからないように、番号は Issue から取り、書き足す共有のファイルをなくす

- 状態: 承認
- 日付: 2026-11-08

## 背景

並行して AI に作業させると、PR どうしのコンフリクトがよく起きていた。マージコミットを `git merge-tree` でマージし直して数えると（2026-11-08 まで）、ぶつかったファイルは次のとおりだった。

| ファイル | 回数 |
|---|---|
| `.kit/src/docs/adr/README.md`（ADR の一覧） | 13 |
| `.kit/CHANGELOG.md` | 3（できてから毎回） |
| ビルド成果物（`main.js`）、`.claude/CLAUDE.md` など | 6（初期） |
| `.kit/harness/security/last-check.json` とレポート | 2 |
| ソースコード | 2 |

テキストのコンフリクトとは別に、ADR の番号の振り直しが 5 回、移行の番号の振り直しが 2 回あった。振り直すと、ディレクトリ名・テスト・CHANGELOG・ADR の本文・ソースのコメントの参照をすべて直すことになる（`.kit/harness/notes/2026-11-08-html-viewer.md`、`2026-11-08-tmp-folder.md`）。

原因は 2 つある。

1. ADR と移行の番号を、作業を始めたときの main を見て「次の連番」で取る。並行するブランチは同じ番号を取る
2. どの PR も同じ場所に書き足すファイルがある。ADR の一覧の末尾、CHANGELOG の先頭、`last-check.json`（同じ日に 2 本のブランチがセキュリティチェックをすると、両方が書き換える）

dev-pr の「PR の前に main を取り込む」（2026-11-03）は、ぶつかったことに気づく仕組みで、ぶつかるのを防がない。PR を出した後に別の PR が先にマージされると、やはりぶつかる。

## 決定

1. **新しい ADR の番号は、その変更の GitHub Issue の番号にする**（4 桁のゼロ埋め。Issue #56 なら `0056`）。ハーネスとプラグインの 2 つのディレクトリで共通。番号は飛び飛びになってよい。ADR を書く前に Issue を作る。1 つの Issue に ADR は 1 つ（2 つ要るなら Issue を分ける）。既存の 0001〜0038（プラグイン）・0001〜0012（ハーネス）は変えない
2. **新しい移行の番号も、その変更の Issue の番号にする**（`.kit/migrations/0056-名前/`）。1 つの Issue に移行が 2 つ要るなら、名前で分ける（`0056-foo`、`0056-bar`）。実行の順は今までどおり名前の順。既存の 0001〜0006 は変えない
3. **変更の記録は 1 変更 1 ファイルにする**: `.kit/changes/YYYY-MM-DD-名前.md`。`.kit/CHANGELOG.md` は 2026-11-08 までの記録として残し、書き足さない。vault-upgrade は、取り込む範囲で増えた `.kit/changes/` のファイルを読む（[ADR-0010](0010-upstream-updates-and-migrations.md) の CHANGELOG の部分を置換）
4. **ADR の一覧はスクリプトで作る**: `node .claude/scripts/adr-index.mjs --write` が、各 ADR の見出しと `- 状態:` の行から、2 つの README の一覧を書き直す。`verify.mjs` は一覧が ADR と合っているかを検査する。一覧は手で書かない。状態の正本は各 ADR の `- 状態:` の行にする。`.gitattributes` で 2 つの README を `merge=union` にし、手元の merge ではぶつからずに両方の行を残す（その後 `--write` で整える）
5. **セキュリティチェックの記録は、レポートだけにする**: `last-check.json` をやめる。レポートは `.kit/harness/security/reports/YYYY-MM-DD-名前.md`（既存の `YYYY-MM-DD.md` はそのまま）。SessionStart フックは、作業ツリーと `origin/main` のレポートから最新の日付・commit・結果を読む。`origin/main` も見るので、別のブランチがマージしたチェックも数える

## 理由

- Issue の番号は GitHub が 1 か所で振るので、並行するブランチでも重ならない。大きい変更は dev-plan で Issue を作っているので、手間は増えない。ADR が要るのは大きい変更だけで、移行が要るのも子のものに手を入れる大きい変更だけ
- 2 つのディレクトリで番号の空間が分かれていたため、「ADR-0009」がどちらか分からず、パスで書く決まりがあった。Issue の番号なら、新しい ADR はどちらのディレクトリでも重ならない
- 移行は、並行して作ったもの同士は互いに依存しない（作ったときに相手がない）。`migrate.mjs` は適用済みを名前の集合で判定するので、番号の順とマージの順が違っても、未適用のものはすべて実行される
- 1 変更 1 ファイルなら、PR どうしが同じ行を書き換えない（[ADR-0012](0012-product-responsibility.md) の `product/` と同じ考え方）。ファイル名の日付で並べられる
- 一覧を作るのがスクリプトなら、ぶつかっても解き方は「スクリプトを実行し直す」の 1 つで、判断が要らない。状態を ADR と一覧の 2 か所に書かないので、食い違わない（作った時点で 16 件が食い違っていた）
- `merge=union` は git に組み込みのドライバで、設定なしで手元の merge に効く。GitHub の画面での merge には効かないことがあるが、そのときもスクリプトで解ける
- 実施記録を 1 つのファイルにまとめると、チェックのたびにそこを書き換えるのでぶつかる。レポートのファイル名に名前を足せば、同じ日でも重ならない

## 却下した案

- **番号を PR の直前に決める**: PR を出した後に別の PR が先にマージされると、やはり重なる（tmp-folder の PR で起きた）
- **ADR・移行のファイル名を日付と名前にする（`2026-11-08-tmp-folder`）**: 重ならないが、本文やコメントで参照する名前が長くなる。Issue の番号なら「ADR-0056」と短く書け、Issue とも結びつく
- **ADR の一覧をなくす**: 状態を一覧で見られなくなる。生成すれば保守の手間はない
- **CHANGELOG を断片から生成して 1 ファイルにする**: 生成した CHANGELOG がまたぶつかる。子が読むのは取り込む範囲の差分だけなので、断片のままでよい
- **既存の ADR・移行の番号を振り直す**: 移行は子が名前で適用済みを記録しているので変えられない。ADR はリンクとコメントの参照が多く、得るものがない

## 影響

- ハーネスの文書: ADR の README（2 つ）、[進め方](../workflow.md)、[移行の書き方](../migrations.md)、dev-plan（ADR の前に Issue を作る）、dev-pr（番号の振り直しの手順をなくす）、[セキュリティチェックの実施ルール](../security-check-schedule.md)、security-check、上流の CLAUDE.md
- 検査: `adr-index.mjs` を足し、`verify.mjs` に入れる。SessionStart フック `security-check-status.mjs` をレポートから判定するように変える
- 子: vault-upgrade が `.kit/changes/` を読む。子のものは変わらないので移行はない
- 一覧の「状態」が各 ADR の `- 状態:` の行と食い違っていたものは、ADR の側を直した（状態の行は、承認済みでも書き換えてよい）
