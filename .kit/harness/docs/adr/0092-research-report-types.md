# ADR-0092: 調査報告の出力を、調査の型ごとに制御する

- 状態: 提案
- 日付: 2026-11-08

## 背景

### 困りごと

技術選定、フィジビリティ調査、コードベースの理解など、エージェントに調査報告を頼む場面が多い。[ADR-0013](0013-output-by-reader-and-stage.md) の write-for-reader は、読み手が読んだ後に何をするかで段階を決め、どこまで書くか（内容の取捨）を制御する。一方で、調査の種類ごとに何を軸に書くか、どの語彙と粒度で書くかは決めていない。

たとえば技術選定とフィジビリティ調査は、どちらも段階 3（決める）になる。それでも技術選定では、評価軸と、候補を同じ軸で並べた表が要る。フィジビリティ調査では、判定（Go / No-go / 条件付き）と、それを阻むものが要る。段階だけでは、この違いを毎回エージェントが判断することになり、出力がぶれる。

### 想定するユースケース（2026-11-08 にユーザーと洗い出したもの）

技術選定、フィジビリティ調査、コードベースの理解、変更の影響範囲、不具合の原因調査、事実の確認、動向・先行事例の調査、移行・アップグレードの調査、点検（セキュリティ・ライセンス）、性能・コストの調査、実装への引き継ぎ、非エンジニアへの共有、学習・概念の理解の 13 個。

洗い出しの中で、段階のほかに出力を分ける軸が 3 つ見つかった。

1. **判断の型**: 選ぶ、可否を決める、全件を確かめる、原因を特定する、地図を作る。冒頭の結論の形（推奨・判定・件数・答え・地図）がこれで決まる
2. **語彙の層**: コードの言葉（パス・識別子）、技術の言葉、業務の言葉
3. **寿命**: 一度読んで終わるか、蓄積して引き直すか

## 決定

### 1. 調査の型を、write-for-reader の上に置く

新しいスキル `research-report` を `.claude/skills/research-report/` に置く（子向け。上流の手順からもリンクで辿る。write-for-reader と同じ扱い）。

- `research-report` は**調査の型**を決める。型は、既定の読み手と段階、冒頭の結論の形、必須の節、語彙と粒度、省くものを持つ
- 内容の取捨の規則、文体、確かめ方、形式への渡し方、記録は write-for-reader のものを使う。research-report はそれを繰り返さない
- 流れ: 型を選ぶ → 型の既定で write-for-reader の 1（読み手）と 2（段階）を埋める → 棚卸しのときに型の必須の節を観点として使う → 段階の規則で書き、型の確かめ方を足す

### 2. 型を 12 個で始め、語彙の層は型と別に選ぶ

洗い出した 13 個のうち、「非エンジニアへの共有」は調査の種類ではなく読み手の違いなので、型にしない。どの型にも重ねられる**語彙の層**（コード・技術・業務）として選ぶ。たとえば「上司に技術選定を報告する」は、型が技術選定で、語彙の層が業務になる。

| 型の id | 型 | 既定の読み手と段階 | 冒頭の結論の形 |
|---|---|---|---|
| `tech-selection` | 技術選定 | 両方・3 | 推奨 1 つと決め手 |
| `feasibility` | フィジビリティ調査 | 両方・3 | 判定（Go / No-go / 条件付き Go） |
| `codebase-map` | コードベースの理解 | 両方・5 | 地図（入口・層・データの流れ） |
| `impact-analysis` | 変更の影響範囲 | 両方・4 | 範囲と件数、最も重いもの |
| `root-cause` | 不具合の原因調査 | 人・3 | 原因と確度、直し方の推奨 |
| `fact-check` | 事実の確認 | 人・2 | Yes / No / 条件付きの答え |
| `landscape` | 動向・先行事例の調査 | 両方・2 | 分類と、見た範囲 |
| `migration` | 移行・アップグレードの調査 | 両方・3 と 4 | 移行するかの推奨と、Breaking Change の件数 |
| `audit` | 点検（セキュリティ・ライセンス・規約） | 人・4 | 範囲と件数、最も重いもの |
| `performance-cost` | 性能・コストの調査 | 両方・3 | 測った値と、打ち手の推奨 |
| `handoff` | 実装への引き継ぎ | LLM | 何を作るか（確定した仕様） |
| `concept` | 学習・概念の理解 | 両方・5 | 一言の定義 |

### 3. ファイルの構成

write-for-reader と同じく、要素ごとにファイルを分ける。型を足す・消す・直すとき、そのファイルだけを変えればよいようにする。

| ファイル | 内容 |
|---|---|
| `SKILL.md` | 入口。対象、流れ、型の一覧 |
| `select-type.md` | 型の選び方、混ぜ方、どれにも当たらないとき |
| `vocabulary.md` | 語彙の層（コード・技術・業務）と選び方 |
| `types/<型の id>.md` | 型ごとに同じ見出し: 目的、使う・使わない、既定、冒頭の結論の形、必須の節、語彙と粒度、省くもの、書くときの指示、確かめ方、よくある失敗、根拠 |
| `maintaining.md` | 型を足す・消す・直す手順と、型のファイルのひな形 |
| `evidence.md` | 型の規則の根拠。`R1` などの ID で引く（write-for-reader の `E` の ID も引いてよい） |

### 4. 型の選び方

1. 依頼に型の名前か、それと分かる言葉（「どれを使うべきか」→ 技術選定）があれば、その型にする
2. なければエージェントが推定する。推定したときは、出力の冒頭に「型: 技術選定（段階 3）」を 1 行書き、違えばユーザーが言い直せるようにする
3. 1 つの調査が複数の型に当たるなら、読み手が最初に読む節の型を主にし、節ごとに型を混ぜる（write-for-reader の段階の混ぜ方と同じ）
4. どれにも当たらないときは、型を使わずに write-for-reader だけで書き、記録に「型なし」を残す。同じ「型なし」が続いたら、型を足す候補にする

### 5. 記録と見直し

- 記録は write-for-reader の `output-log.mjs` を使い、`--skill research-report --kind "調査報告: <型の id>"` とする。スクリプトは変えない
- 型の追加・削除・調整は、記録の集計（型ごとの件数・上げ下げ・問題の種類）と、ユーザーの指摘から判断する。手順は `maintaining.md` に書く。使われない型は消し、「型なし」が続く依頼には型を足す

## 理由

- 段階は「どこまで書くか」を決めるが、「何を軸に書くか」は調査の種類で決まる。この 2 つは別のつまみなので、型を段階の上に置き、段階の規則は再利用する
- 型ごとに冒頭の結論の形と必須の節を決めると、同じ種類の報告が同じ構造になり、読み手はどこに何があるかを予測できる（ADR-0013 の「同じ種類は同じ構造にする」）
- 語彙の層を型から外すと、型の数が読み手の数だけ増えずに済む
- 型を推定したら冒頭で明示することで、推定の誤りが 1 行で直せる。型の名前を依頼に書かせるだけにすると、毎回の依頼の負担が増える
- 使いながら直す前提なので、1 型 1 ファイルにして、記録で直す先を型の単位で決められるようにする

## 却下した案

- **write-for-reader の中に型を足す**: write-for-reader は調査報告以外（完了の報告、ADR、wiki のページ）にも使う。調査の種類の知識を混ぜると、入口が大きくなり、調査以外の出力でも読むことになる
- **型を段階の代わりにする**: 型ごとに取捨の規則を書くと、段階の規則（判断を変えうるものを残す、全件を書く）の重複が 12 か所にできる。直すときにそろわなくなる
- **非エンジニアへの共有を型にする**: どの調査でも起きうる読み手の違いで、型にすると「技術選定を上司に」のような組み合わせを表せない
- **型を依頼に必ず書かせる**: 依頼の負担が増え、書き忘れたときの扱いが決まらない。推定して明示する方式なら、誤りは 1 行で直せる
- **最初から型を少なく（3〜4 個）する**: 洗い出したユースケースの多くが落ち、使いながら足す材料が集まらない。12 個で始め、使われないものを消すほうが判断しやすい

## 影響

- 新しいスキル 1 つ（ファイル 16 個ほど）を足す。write-for-reader の入口と段階の選び方に、調査報告なら research-report の型から既定を取る、と 1 行ずつ足す。子向けの `.claude/CLAUDE.md` の作業の表に 1 行足す
- 子には merge で届く。子のものには手を入れないので、移行は要らない。`.kit/changes/` に 1 ファイル書く
- 調査報告のたびに型を選ぶ手間が 1 つ増える。推定と明示はエージェントが行う
- 型の根拠の多くは既知の文献（本文を今回は確かめていない）。使いながら、記録の集計を根拠として足す
