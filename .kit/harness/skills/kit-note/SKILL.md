# 上流の開発中の気づきを記録する

気づいた時点で `.kit/harness/notes/` に書く。記録は月 1 回の上流の評価（[kit-review](../kit-review/SKILL.md)）の入力になる（[ADR-0011](../../docs/adr/0011-harness-parent-and-child.md)）。

プラグインの不具合や欲しい機能は、ここではなく上流の Issue にする。

## 記録する条件

| 種類 | 起きたこと |
|---|---|
| 訂正 | ユーザーに、やり方や出力を直された（必ず記録する） |
| 質問 | 文書にあるべきことが書かれておらず、ユーザーに質問した |
| 繰り返し | 同じ失敗を 2 回繰り返した |
| 食い違い | 文書や手順の記述が、実際のコードや挙動と違っていた |
| 迂回 | 検査を迂回したくなった、検査が誤っていると感じた |
| つまずき | 上のどれでもないが、文書や検査が足りずに遠回りや手戻りをした |
| 移行 | 子のものに手を入れる変更で、移行の書き方や fixture が足りなかった |

迷ったら記録する。

## 書き方

ファイルは作業ごとに 1 つ: `.kit/harness/notes/YYYY-MM-DD-<作業を表す英語の短い名前>.md`。同じ作業の中では同じファイルに追記する。

```markdown
# 2026-11-02 テンプレートの重ね合わせ

## つまずき

- 起きたこと: Vault の API で .kit/ のテンプレートを読もうとして見つからなかった。隠しパスは索引に載らない
- 改善案: プラグインの設計と開発の文書に「隠しパスは vault.adapter で読む」と書く
```

- 起きたことは事実を書く（何をして、何が起き、ユーザーが何と言ったか）
- 改善案は省いてよい。検査で防げるなら検査、無理なら文書の修正を書く
- 上流は公開リポジトリ。個人のノートの内容、端末名、秘密情報を書かない

## 記録した後

- 元の作業に戻る。ハーネスはこの場では直さない（直し方が明らかで小さいもの、たとえば誤字や古いコマンドは、今の作業の中で直してよい。そのときも記録を残し、改善案に「直した」と書く）
- 記録のファイルは、今の作業のコミットに含める（上流の作業はすべてブランチから PR にするので、同じ PR に入る）
- プロジェクトについて学んだことを、Claude Code のメモリだけに保存しない
