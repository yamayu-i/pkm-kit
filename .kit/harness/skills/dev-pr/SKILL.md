# PR を出す

## 前提

[実装する](../dev-implement/SKILL.md) の検査がすべて通っている。

## 1. 最新の main を取り込む

PR を出す前に、main とぶつからないかを確かめる。CHANGELOG の先頭と ADR の一覧の末尾は、どの PR も書き足すのでぶつかりやすい。

```sh
git fetch origin main
git merge origin/main      # rebase や force push はしない
```

- コンフリクトしたら解いてからマージコミットにする。両方の変更を残す（CHANGELOG は新しいものを上に）
- ADR の番号が main のものと重なっていたら、こちらの番号を空いている番号に変え、参照（ソースのコメント、CHANGELOG、他の ADR の状態）も直す
- ビルド成果物（`main.js` など）は、merge の結果を使わずに `pnpm build` で作り直す
- 取り込んだら [実装する](../dev-implement/SKILL.md) の検査をもう一度通す

## 2. 差分を自分で読む

```sh
git diff origin/main...HEAD
```

| 観点 | 確かめること |
|---|---|
| 完了の条件 | 計画の条件をすべて満たし、条件ごとにテストか確認方法がある |
| 範囲 | 計画にない変更が混ざっていない |
| 正しさ | 境界の値、空の入力、失敗したときの振る舞い |
| テスト | 削除・スキップ・期待値の変更がない。実装をなぞるだけになっていない |
| 検査 | 検査や CI を緩めていない |
| 設計 | ADR に反していない。ADR に残すべき決定が漏れていない |
| 成果物 | プラグインのソースを変えたなら、ビルド成果物（`main.js`、`styles.css` など）もコミットした |
| 秘密情報 | トークン・個人の情報・デバッグ用の出力がない |

可能なら `code-review` スキルなどで、実装したときとは別の視点でもレビューする。正しい指摘は直し、直さないものは理由を控える。直したら検査をやり直す。

## 3. 気づきを見直す

この作業で、訂正されたこと、文書になくて質問したこと、文書と実際の食い違い、手戻りを思い返す。記録していないものがあれば [気づきを記録する](../kit-note/SKILL.md)。

## 4. push して PR を作る

```sh
git push -u origin HEAD
```

PR は `gh pr create` か GitHub の MCP ツールで作る。タイトルはコミットと同じ形式（`<type>(<scope>): <日本語の要約>`）。本文には次を書く。

```markdown
## 概要

何を、なぜ変えたか。Issue があれば `Closes #N`

## 検証

- 実行した検査と結果（`node .claude/scripts/verify.mjs --plugin` など）
- 自動にできなかった条件をどう確かめたか
- レビューの指摘で直さなかったものと理由

## 気づき

記録した件数（なければ「なし」）
```

## 5. 伝える

PR の URL と検証の結果をユーザーに伝える。PR はマージしない。

## 出力の段階

出力は [write-for-reader](../../../../.claude/skills/write-for-reader/SKILL.md) に従う。下は既定で、上げ下げはその場で判断する。

| 出力 | 読み手 | 段階 |
|---|---|---|
| PR の本文 | 両方 | 3,4（検証の節が 4） |
| PR を出したことの報告 | 人 | 1 |
