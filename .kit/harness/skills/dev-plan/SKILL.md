# 計画を立てる

実装を始める前に、何をどう変えるかを決めて、ユーザーの承認を得る。承認されるまで実装しない。作業の種類は [進め方](../../docs/workflow.md) で判断する。

## 1. 文脈を読む

- 触れる範囲のコードと文書
- 関連する ADR: プラグインは `.kit/src/docs/adr/`、ハーネスと wiki は [adr/](../../docs/adr/README.md)
- プラグインなら [プラグインの設計と開発](../../docs/plugin-development.md)、wiki なら [LLM wiki の仕組み](../../../../.claude/docs/llm-wiki.md)
- 未マージの PR（`gh pr list` か GitHub の MCP ツール）。同じ箇所に触れるものがあればユーザーに伝える

依頼が曖昧で、何をもって完了とするかが決められない場合は、計画を書く前に質問する。

## 2. 大きい変更か小さい変更かを決める

[進め方](../../docs/workflow.md) の表で判断する。迷ったら大きい変更。

## 3. ADR を書く（設計判断を含む場合）

[ADR を書く条件](../../docs/adr/README.md) に当たるなら、計画より先に ADR を `提案` の状態で書き、要点をユーザーに伝えて合意を得る。却下した案と理由も書く。合意したら状態を `承認` にする。

## 4. 計画を書く

- **方針**: どう実現するか。複数の方法があるなら、選んだ方法と理由
- **変更するファイル**: 追加・変更・削除するファイルと、それぞれで何をするか
- **完了の条件とテスト**: 条件ごとに、どのテストか検査で確かめるか。自動にできないものは確かめ方
- **注意が要る点**: 依存の追加（必要性の説明。[CLAUDE.md](../../CLAUDE.md) のルール）、セキュリティチェックが要る変更（[実施ルール](../../docs/security-check-schedule.md)）、`main.js` のビルドが要るか
- **確認したいこと**: ユーザーに決めてほしい点

## 5. 承認を得る

- 大きい変更: Issue を作り（なければ）、計画をコメントする。要点をチャットでも伝える。計画はリポジトリにコミットしない
- 小さい変更: 計画をチャットで伝える

承認されたら [実装する](../dev-implement/SKILL.md) に進む。直すよう言われたら、計画を直してもう一度承認を得る。

## 計画から外れるとき

実装の途中で計画にない変更が必要になったら、止めて伝え、計画を直して承認を得てから続ける。
