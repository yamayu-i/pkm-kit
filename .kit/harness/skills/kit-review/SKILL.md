# 上流の仕組みを評価する

出力は改善案（レポートと上流の Issue）と、エスカレーションへの返事まで。変更は、その Issue から通常の工程（[進め方](../../docs/workflow.md)）で行う（[ADR-0011](../../docs/adr/0011-harness-parent-and-child.md)）。

## いつ行うか

- 月 1 回（前回は `.kit/harness/reviews/last-review.json`。上流での SessionStart フックが期限を知らせる）
- 期限切れのときは、ユーザーの依頼に取りかかる前に一言伝えて実施を提案する。「後で」と言われたら依頼を優先する
- 時間がなければ、一部の手順だけでもよい。その場合はレポートに、行った手順を書く

## 1. 現在の設計を読む

- [上流のハーネスの設計](../../docs/harness.md)（前提、現在地、未決事項）と [ADR](../../docs/adr/README.md)
- 子向けの [ハーネスの設計](../../../../.claude/docs/harness.md) と [LLM wiki の仕組み](../../../../.claude/docs/llm-wiki.md)

## 2. 観測を集める

前回の評価のコミットを `last-review.json` の `commit` から取る（初回は全期間）。

```sh
git log --oneline <前回の commit>..HEAD
```

- 子からのエスカレーション: 上流の Issue のうち、ラベル `escalation`（または本文の先頭が `escalation`）で、まだ振り分けていないもの
- `.kit/harness/notes/` のファイルをすべて読む
- [product-review](../product-review/SKILL.md) で見つけた機会（ラベル `ux` の Issue）と、その状態
- CI の失敗と、移行の fixture のテストの結果（前回から）
- 前回のレポート（`.kit/harness/reviews/`）の改善案がどうなったか（Issue の状態）

## 3. 調べる

- Claude Code の更新（スキル、フック、設定、入れ子の `.claude/` の読み込み、クラウドのセッション）で、今のハーネスに効くもの
- Obsidian の API の更新で、プラグインに影響するもの（ヘッダーの差し込みなど、内部の DOM に依存している箇所）
- LLM wiki の運用例で、取り入れられそうな工夫

調べた情報源はレポートに書く。

## 4. エスカレーションを振り分ける

1 件ずつ、次のどれかに決めて、その Issue にコメントで返す。

| 決定 | 返すこと |
|---|---|
| 受け入れる | 上流の改善の Issue にする（エスカレーションの Issue そのものを使ってよい）。直ったら Close し、どの上流のコミットで直ったか、移行の有無を書く |
| 子で直せる | 子のもの（`template/`、`.claude/local/`、`skills/local-*`、`.obsidian/*.json`）でどう直すかを示して Close する |
| 見送る | 理由を書いて Close する |

個人の内容が書かれていたら、ユーザーに伝えて、本文を直すか消すかを決めてもらう（上流は公開）。

## 5. 評価する

4 つの目的ごとに、根拠を付けて「うまくいっていること」「うまくいっていないこと」を書く。

| 目的 | 見るもの |
|---|---|
| プラグイン | 開発のコミットと PR の流れ、検査で止まった問題、子からの不具合の報告 |
| LLM wiki の仕組み | 子からのエスカレーション、wiki のスキルへの訂正 |
| ハーネス | 繰り返し出た気づき・エスカレーション、使われていない手順や文書、文書と実際の食い違い、CLAUDE.md の大きさ |
| 更新の取り込み | 移行の失敗、取り込みで起きた衝突（境界の違反） |

同じ内容が複数の子・気づきから出ているものを優先する。

## 6. 改善案を出す

改善案ごとに、根拠（どの観測か）、変えるもの、検査で強制できるか、子への影響（移行が要るか）、大きさを書く。規約を足す前に、検査にできないかを考える。

一覧をユーザーに見せ、起票するものを確認してから上流の Issue にする（ラベル `harness` か `wiki`）。ここでは実装しない。

## 7. 記録する

ブランチを切って、次を 1 つのコミットにまとめ（`harness(review): YYYY-MM 上流の評価`）、PR にする。

- レポート `.kit/harness/reviews/YYYY-MM-DD.md`: 期間、行った手順、観測の要約、エスカレーションの振り分け、評価、改善案と Issue の番号、調べた情報源。個人の内容を書かない
- `.kit/harness/reviews/last-review.json`

  ```json
  { "date": "YYYY-MM-DD", "commit": "<短縮 commit>", "report": "YYYY-MM-DD.md", "issues": [12, 13] }
  ```

- [上流のハーネスの設計](../../docs/harness.md) の「評価の記録」の表に 1 行足す。「現在地」と「未決事項」が変わっていたら直す
- 処理した `.kit/harness/notes/` のファイルを消す
