# 体験の機会を見つける

出力は機会（ラベル `ux` の Issue）と、[プロダクトの文書](../../docs/product/README.md)の手直しまで。解決策は決めない。解くと決まった機会は、通常の工程（[進め方](../../docs/workflow.md)）で計画する（[ADR-0012](../../docs/adr/0012-product-responsibility.md)）。

## いつ行うか

- 月 1 回。[kit-review](../kit-review/SKILL.md) と同じ時期に、その前に行う（見つけた機会を kit-review の評価に使える）
- ユーザーの依頼を受けたとき、同じ場面の困りごとが続いていそうなら、依頼に取りかかる前に一言伝えて、その場面だけ行う
- 前回は、ラベル `ux` の Issue のうち一番新しいものと、レポート（`.kit/harness/reviews/`）で分かる

## 1. 読む

- [戦略](../../docs/product/strategy.md)（使う人、望む成果、原則、やらないこと）
- [場面](../../docs/product/jobs/README.md)、[概念](../../docs/product/concepts/README.md)、[今の体験の正本](../../docs/product/surfaces/README.md)
- 開いているラベル `ux` の Issue（同じ機会を二重に起票しない）

## 2. 観測する

次の 6 つから探す。全部を毎回やらなくてよいが、行ったものをレポートに書く。

| 観測 | やること |
|---|---|
| 場面の歩き通し | 場面を 1 つずつ、`surfaces/` とコード（必要ならプレビュー）に沿って最初から最後まで辿る（認知的ウォークスルー）。各手順で、使う人が次に何をすればよいか分かるか、押した結果が分かるか、手数が多すぎないか（Norman の実行の溝と評価の溝）、スマホで同じことができるかを見る |
| 画面の点検 | `pnpm --filter pkm-task preview:ui` のスクリーンショット（ライト / ダーク、広い / 狭い）を、Nielsen の 10 のヒューリスティクスで見る: 状態が見えるか、現実の言葉か、戻れるか、一貫しているか、間違いを防ぐか、覚えなくてよいか、慣れた人が速くできるか、余計なものがないか、間違いから立ち直れるか、助けがあるか |
| 概念の一貫性 | `concepts/` の用語の対応表と、画面の文言・データのキー・文書の食い違い。同じ概念に別の表記があるもの、別の概念に同じ表記があるもの、言語（英語と日本語）が場面の中で混ざるもの |
| 原則との突き合わせ | 戦略の原則とやらないことに反している振る舞い |
| 変更の繰り返し | `git log --since=<前回> --stat` と ADR の一部置換で、短い期間に同じ面を何度も変えたもの。変更のたびに困りごとが言葉にされていれば、まだ解けていない機会がある |
| 気づきとエスカレーション | `.kit/harness/notes/` と、ラベル `escalation` の Issue のうち、体験に関わるもの |

Claude の点検は、本人が使うことの代わりにはならない。観測だけで、使う人が本当に困っているかまでは分からないことが多い。

## 3. 機会を起票する

1 つの困りごとを 1 つの Issue にする。タイトルは `ux: <場面>で<困りごと>`（解決策を書かない）。ラベルは `ux`。

```markdown
## 場面

[場面の名前](.kit/harness/docs/product/jobs/<slug>.md) の、どの手順か

## 困りごと

使う人から見て何が起きるか。

## 根拠

- どの観測で見つけたか（歩き通し、画面の点検、概念の一貫性 など）
- 具体的な箇所（面、文言、ADR、コミット）

確かさ: 高い / 中くらい / 低い（本人の利用で確かめていない など）

## 望む成果

[戦略](.kit/harness/docs/product/strategy.md#望む成果) の番号

## 解決策の候補（任意。決めない）
```

- 上流は公開なので、個人のノートの内容・端末名を書かない
- 起票したら、件名と確かさの一覧をユーザーに伝える。解くかどうかはユーザーが決める
- 解かないと決まったものは、理由を書いて Close する（`not_planned`）

## 4. 文書を直す

- 歩き通しで、`surfaces/` が今の実際と違っていたら直す（コードが正）
- 機会を起票したら、その場面（`jobs/`）の「知られている困りごと」に Issue へのリンクを足す。Close したら消す
- 新しい場面・概念・面が見つかったら、その種類の書式で足す（[育て方の規則](../../docs/product/README.md#育て方の規則)）
- 戦略を変えたほうがよいと思ったら、変えずにユーザーに提案する

直した文書は、ブランチを切って 1 つのコミット（`docs(product): YYYY-MM 体験の見直し`）にし、PR にする。kit-review と同じ時期なら、その PR に含めてよい。

## 5. 記録する

kit-review のレポート（`.kit/harness/reviews/YYYY-MM-DD.md`）に「体験」の節を設け、行った観測、起票した Issue と確かさ、直した文書を書く。kit-review を行わないときは、PR の本文に書く。

## 出力の段階

出力は [write-for-reader](../../../../.claude/skills/write-for-reader/SKILL.md) に従う。下は既定で、上げ下げはその場で判断する。

| 出力 | 読み手 | 段階 |
|---|---|---|
| 機会の Issue | 両方 | 3 |
| `surfaces/`・`concepts/` の文書 | 両方 | 5 |
