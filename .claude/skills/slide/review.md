# レビューを受けて直す

ユーザーは、ブラウザで `index.html` を開き、「Review」で部品を選んでコメントを書き、「Copy review」でレポートをコピーしてチャットに貼る。ここは、そのレポートを受け取ったときの手順。

## レポートの形

```
# スライドのレビュー: slide/demo/deck.html

- コメント: 3 件
- ビルド: 40b7ad0f329c
- 頼みたいこと: …

## デッキ全体

1. デッキ全体
   全体に、数字の出典をそろえたい

## スライド 8「担当が決まるまでの待ちが、応答時間の 7 割を占める」

2. `h2`「担当が決まるまでの待ちが、応答時間の 7 割を占める」（deck.html:64）
   「7 割」ではなく、時間（2 時間 50 分）で言いたい

3. スライド全体（deck.html:63）
   図を大きくしたい
```

| 部分 | 意味 |
|---|---|
| 1 行目のパス | 直すファイル |
| ビルド | ユーザーが見ていた `index.html` の版（`<html data-build="…">`）。今の `index.html` と違えば、ユーザーは古い版を見ていた |
| `## スライド N「見出し」` | スライドの番号（1 始まり）と、そのときの見出し |
| `` `h2`「…」（deck.html:64） `` | 選んだ部品の種類、文の冒頭、`deck.html` の行 |
| 「スライド全体」 | 部品ではなく、その 1 枚全体へのコメント |
| ※コメントの後に、この部品は変わっています | コメントを書いた後にビルドし直されている。今の中身を見てから判断する |

## 手順

1. **場所を確かめる**: `deck.html` の、レポートの行を読む。行はビルドのたびにずれるので、行だけを信じず、**見出しと文の冒頭が合っているか**を見る。合わなければ、見出しと文で探す。見つからなければ直さずに聞く
2. **コメントを分ける**

   | コメントの種類 | すること |
   |---|---|
   | 文言・数字・順番などの、はっきりした指示 | そのとおりに直す |
   | 「分かりにくい」「詰まっている」などの感想 | 原因を規約（[conventions.md](conventions.md)）で考えて直し、何を原因と見たかを返す。パターンを替えるのも選択肢（[逆引き](SKILL.md#3-パターンを選ぶ逆引き)） |
   | 規約とぶつかる指示（文字を小さく、色を足す、文を増やす） | 指示の目的を満たす別の直し方を先に試す（2 枚に分ける、発表者ノートに移す、`read` にする）。それでもぶつかるなら、ぶつかる規約と根拠の強さ（[注意書き](conventions.md#注意書き)）を伝えて、ユーザーに決めてもらう。ユーザーが決めたら従う |
   | 材料が要る指示（数字・図・写真がない） | 作らずに聞く。ほかのコメントは先に直す |
   | 意味が取れない | 推測で直さずに聞く。ほかのコメントは先に直す |

3. **まとめて直す**: すべてのコメントを 1 回の編集で直し、1 回ビルドする（コメントごとにビルドしない）。直すのはコメントのあった所と、それで整合が崩れる所（同じ数字を使う別のスライド、まとめ、道筋）だけ。頼まれていないスライドを作り替えない
4. **ビルドして確かめる**: `node .kit/bin/slide.mjs build <フォルダ>`。新しい警告が出たら直す。画像にできる環境では、直したスライドを見て確かめる
5. **番号で返す**（チャット）

   ```
   1. 出典を「問い合わせ管理の記録（2026 年 9〜10 月）」にそろえました（スライド 8・10・25）
   2. 見出しを「担当が決まるまでに、2 時間 50 分待っている」にしました。まとめ（スライド 4）の 1 項目目も合わせています
   3. 直していません: 図を大きくすると横の 2 項目が入りません。項目を発表者ノートに移してよければ、図を全幅にします
   ```

   - 直したもの: 何をどう変えたか。ほかのスライドに及んだらその番号
   - 直さなかったもの: 理由と、次にできること
   - 最後に 1 行: 「ブラウザを再読み込みすると、変わったスライドに Updated が付きます。直ったコメントは Done で消してください」

## 気づいたことの記録

- 同じ種類のコメントが 2 回続いたら（例: 毎回「文字が多い」）、気づきに記録する（子は harness-note、上流は kit-note）。規約かパターンの直しどころになる
- レポートの形や、部品の選ばれ方で直しにくかったことも記録する
