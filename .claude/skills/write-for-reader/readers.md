# 読み手

出力を書く前に、誰が読むかを決める。読み手によって、困ることも、望ましい書き方も違う。

| 読み手 | 例 | 困ること | 方式 |
|---|---|---|---|
| LLM だけ | サブエージェントへの依頼と返答、棚卸しの一覧、中断の引き継ぎ、気づきの記録 | 落とした情報は後から取り戻せない。曖昧さ。要らない文脈は性能を落とす（E12、E13） | [LLM だけ](#llm-だけ) |
| 人だけ | 会話の返答、作業の完了の報告、点検の結果の報告 | 認知負荷。要点が埋もれる | [段階](select-stage.md)に従う |
| 両方 | wiki のページ、ADR、Issue の計画、PR の本文、スキル・文書 | 人向けに削ると LLM が根拠を失う。LLM 向けに全部書くと人が読めない | [両方](#両方) |

迷ったら、**最初に読むのは誰か**と、**その出力を根拠に次の作業をするのは誰か**を分けて考える。両者が違えば「両方」。

## LLM だけ

段階を持たない。人の認知負荷ではなく、読み手の LLM が文脈を持たないことと、文脈が長いほど性能が落ちることに合わせる（E12、E13）。

### 判断のロジック

1. 受け取る側（スキル、サブエージェント、次のセッション）が決めた形があれば、それに従う
2. 次の作業に要るかで、載せるものを決める。字数では決めない。要るものは全件書き、要らないものは書かない
3. 人が読み返すことがあっても、人向けの推敲はしない。人も読むなら「両方」にする

### 書くときの指示

```
読み手は、この会話の文脈を持たない LLM。これだけを読んで次の作業をする。
1. 受け取る側が決めた構造（見出し・表・JSON など）で書く。なければ、項目名を付けた一覧にする
2. 次の作業に要るものは全件書く。要らない経緯・言い換え・挨拶は書かない
3. 事実ごとに、出典（パス・URL・コマンド）と確度（確かめた・推測・未確認）を書く
4. 確かめたこと、試して失敗したこと、決めていないことを分けて書く
5. 「上記」「それ」などで指さず、ファイル名・識別子で書く
```

### 確かめ方

文脈を持たない読み手として読み、次の作業を始めるのに足りない情報（どのファイルか、何が未確認か）がないかを見る（E8）。

## 両方

層に分ける。人が先に読む層と、LLM と精読する人が読む層を、同じ出力の中で分ける。

1. **冒頭（人の層）**: 人が読んだ後にすることに合わせた段階で書く（多くは 3 か 5）。冒頭だけで用が足りるようにする（E4）
2. **本文の下（詳細の層）**: 出典、全件、前提、決めていないこと。LLM が根拠に使える形にする
3. **同じ種類は同じ構造にする**: どこに何があるかを予測できるようにする（E15）。種類ごとの構造は、その種類を作るスキルや規約が決める
4. **長い詳細は外に置く**: 本文に埋めず、別のファイルやページにしてリンクする（[形式への渡し方](formats.md)の「詳細」）

詳細を層に分けても、認知負荷は要約だけのときと変わらず、判断の質はよくなる（E5）。
