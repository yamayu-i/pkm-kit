# 段階 1 知らせる

## 目的

読み手が状況を知る。読み手は読んだ後に何もしないか、次の 1 手だけをする。

- 使う: 作業の完了、途中の進み具合、記録や保存をしたことの報告
- 使わない: 読み手に選ばせる・承認させるなら [3](3-decide.md)。失敗の原因を読み手が判断するなら 3、失敗の一覧を読み手が点検するなら [4](4-verify.md)

## 判断のロジック

1. 読み手が知るべき状態の変化を 1 つに決める（完了・失敗・途中・待ち）
2. **期待との差**を探す: 飛ばした工程、通らなかった検査、想定外の変更、できなかったこと。この段階で唯一、省いてはいけないもの。省くと、読み手は完了したと誤って受け取る
3. 読み手がすることがあるかを決める（承認、確認、次の指示）。あれば 1 つだけ
4. それ以外（工程の説明、理由、次の予告、繰り返し）は書かない。詳細は置き場所（パス・URL・コミット）だけを示す

## 書くときの指示

```
読み手は、作業の結果を知るだけ。次の順に、合わせて 3 行以内で書く。
1. 結果（完了・失敗・途中）と、その対象
2. 期待と違ったこと（飛ばした工程、通らなかった検査、想定外の変更）。なければ書かない
3. 読み手がすることがあれば、その 1 つ
工程を順に並べない。理由・次の予告・まとめの繰り返しを書かない。詳細は置き場所（パス・URL）だけを示す。
```

## 構成の部品

結論（1 行）→ 注記（期待との差。あれば）→ 参照（置き場所）。部品は [形式への渡し方](../formats.md)。

## 確かめ方

- 3 行以内か
- 期待との差を省いていないか（棚卸しで見つけた差が、すべて書かれているか）
- 読み手がすることが 2 つ以上あるなら、段階 3 に上げる

## 根拠

- 状況の報告は短くするものの代表（E3）。道具を使った作業の後は短い要約を求める指示が公式の例にある（E9）
- 短くてよい問いへの余計な長さは、得るものなく読み手の時間を使う（E11）
- 最も大事なことを先頭に置く（逆ピラミッド。E16）

## よくある失敗

- やったことを工程の順にすべて並べる
- 失敗や省略を末尾に埋める、または書かない
- 「次は〜します」と予告する
