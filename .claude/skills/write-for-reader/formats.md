# 形式への渡し方

このスキルはファイル形式に依存しない。決めるのは、**何を書くか**（内容の取捨）と、**どう並べるか**（構成の部品の並び）まで。部品をどう描くか（記法、見た目、ファイルの置き場所、メタデータ）は、形式ごとのスキルや規約に任せる。

## 構成の部品

段階のファイルの「構成の部品」は、次の部品で書く。どの形式でも意味が同じになるように、部品は役割で定義する。

| 部品 | 役割 | 形式の側で決めること（例） |
|---|---|---|
| 結論 | 冒頭に置く要約・答え・決めてほしいこと。単独で読める | 見出しの下の最初の段落か、要約の枠か |
| 節 | 内容のまとまり。見出しを持つ | 見出しのレベル、目次 |
| 一覧 | 並列の項目 | 箇条書きの記法 |
| 表 | 同じ項目を持つ要素の比較・全件 | 表の記法。狭い画面での見せ方 |
| 詳細 | 本文から外して置くもの（付録、根拠の全文、長い一覧） | 付録の節、別のファイル・ページ、折りたたみ |
| 参照 | 出典、置き場所、関連するもの | リンクの書き方（Vault の中はパス、外は URL） |
| 注記 | 確度、未確認、期待との差、注意 | 注記の記法、目立たせ方 |

## 渡し方

1. 段階の規則で内容を決め、部品の並びにする（例: 結論 → 表 → 節「対象外」→ 詳細）
2. 出力の形式を決める。依頼か、出力を作るスキルが決めていなければ、読み手が読む場所で決める
3. 下の表の、その形式を受け持つスキル・規約を読み、部品をその形式で描く
4. 形式の規約が段階の規則と食い違ったら（例: 形式の型が結論を冒頭に置けない）、形式の規約に従い、食い違いを記録する（`issue --type format`）

| 形式 | 描き方を受け持つもの |
|---|---|
| 会話の返答 | 実行環境の表示の規則（Claude Code では Markdown として表示される）。詳細はファイルに置いてパスを示す |
| Vault のノート（Markdown） | [ノートの書式と配置](../../docs/vault-conventions.md)。wiki のページは [LLM wiki の仕組み](../../docs/llm-wiki.md) と wiki のスキル |
| GitHub の Issue・PR・コメント | 子は [進め方](../../docs/workflow.md)、上流は [上流の進め方](../../../.kit/harness/docs/workflow.md) |
| HTML | 上流に専用のスキルはまだない。今は[デザインルール](../../../.kit/src/docs/design.md)の「HTML のページ」と [ADR-0037](../../../.kit/src/docs/adr/0037-html-viewer.md) に従う。実行環境に HTML の成果物を作るスキルがあれば、それも使う |
| その他（docx、pptx、pdf など） | 実行環境の、その形式のスキル |

形式を受け持つスキルがないときは、部品の意味が保たれる最も素朴な描き方を選ぶ。そのうえで、ないことを記録に残す（子は harness-note、上流は kit-note に「形式のスキルがない」と書く）。

## このスキルが決めないこと

- 記法、見た目、色、レイアウト
- ファイル名、置き場所、frontmatter などのメタデータ
- 形式ごとの検査（`wiki-lint.mjs` など）
