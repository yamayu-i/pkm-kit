# 型: 学習・概念の理解（`concept`）

## 目的

読み手が、ある概念・仕組みを理解し、後で引き直す。

- 使う: 「〜とは何か」「〜はどういう仕組みか」「A と B の違いは」
- 使わない: 特定のコードベースの作りなら [codebase-map](codebase-map.md)。事実を 1 つ確かめるだけなら [fact-check](fact-check.md)。手順を知りたいなら、手順の文書を書く（この型にしない）

## 既定

| 読み手 | 段階 | 語彙の層 | 寿命 |
|---|---|---|---|
| 両方 | 5 | 技術 | 引き直す（残すなら wiki に取り込む） |

## 冒頭の結論の形

```
<概念>は、<何のために・何をするもの>。<一言の定義>。
<最も大事な性質 1 つ>。
```

## 必須の節

1. **定義**: 一言の定義と、それを少し広げた説明
2. **なぜ要るか**: その概念がない場合に何が困るか
3. **仕組み**: どう動くか。図が効くなら図を 1 つ
4. **具体例**: 最小の例 1〜2 個。できれば読み手がすでに知っているもの（Vault の wiki のページ、触ったことのあるコード）に結びつける
5. **似た概念との違い**: 混同しやすいものと、違いを同じ観点で
6. **誤解しやすい点**: よくある誤解と、正しい理解
7. **出典**: 一次資料と、深く知るための資料

## 語彙と粒度

- 新しい用語は、初めて出たときに定義する。定義していない用語で説明しない
- 抽象の説明と具体例を交互に置く。抽象だけを続けない
- 読み手の既存の知識（wiki にあるページ）に、パスでつなぐ

## 省くもの

- 手順（どうやるか）。手順は別の文書にする
- 網羅的な仕様（参照の文書にリンクする）
- 歴史・経緯（理解に要るものだけを 1〜2 文）

## 書くときの指示

```
読み手は、これで仕組みを理解し、後で引き直す。
1. 冒頭に、何のための何かと、一言の定義、最も大事な性質を書く
2. なぜ要るか（ないと何が困るか）を書く
3. 仕組みを説明し、最小の具体例を 1〜2 個、抽象の説明と交互に置く
4. 似た概念との違いを同じ観点で並べ、誤解しやすい点を書く
5. 新しい用語は初めて出たときに定義する。読み手の既存の知識（wiki のページ）につなぐ
手順と網羅的な仕様を混ぜない。
```

## 確かめ方

- 冒頭だけで「何か」に答えているか
- 定義していない用語が本文に出ていないか
- 残すなら、wiki-ingest で取り込むときに、既存の wiki のページと重複していないか

## よくある失敗

- 仕様の一覧になり、なぜ・どう動くかがない
- 具体例がない、または例が大きすぎる
- 手順と説明が混ざる

## 根拠

- 説明の文書は理解を目的にし、背景・理由・別の見方・関連を扱い、手順と参照を混ぜない（R10）
- 引き直すための文書は冒頭に要約を置く（write-for-reader の段階 5、E15、E16）
