# 型: フィジビリティ調査（`feasibility`）

## 目的

読み手が、やるか・やめるか・PoC に進むかを決める。

- 使う: 「〜できるか」「この制約で実現できるか」「この方式で足りるか」
- 使わない: 複数の候補から選ぶなら [tech-selection](tech-selection.md)。仕様の 1 つの事実を問うだけなら [fact-check](fact-check.md)

## 既定

| 読み手 | 段階 | 語彙の層 | 寿命 |
|---|---|---|---|
| 両方 | 3 | 技術 | 一度読む |

## 冒頭の結論の形

```
判定: Go / No-go / 条件付き Go（条件: <1〜3 個>）。確度: <確かめた・推測>。
<判定を覆しうる、まだ分からないこと 1 つ>。
```

## 必須の節

1. **問いと成功の基準**: 何ができれば「できる」とするか（機能・性能・費用・期限）
2. **判定の根拠**: 基準ごとに、満たすか・満たさないか・分からないかと、その確かめ方
3. **阻むもの**: 技術の制約、環境・権限・規約の制約、費用・期間。基準を満たさない理由になるもの
4. **未知のことと潰し方**: 分からないことごとに、それを確かめる最小の手（PoC、問い合わせ、計測）と、かかる手間
5. **次の一手**: 判定ごとに、読み手が次にすること

## 語彙と粒度

- 「できる」と「やるべき」を分ける。この型が答えるのは「できる」だけ。やるべきかの意見は分けて書く
- 確かめた深さを書く: 動かして確かめた、ドキュメントにそう書いてある、似た例がある、推測。この 4 つを混ぜない
- 条件付き Go の条件は、確かめられる形で書く（「性能が足りれば」ではなく「1 万件で 1 秒以内なら」）

## 省くもの

- 実装の詳細な設計
- 判定に関係しない利点の説明

## 書くときの指示

```
読み手は、これを読んで、やるか・やめるか・PoC に進むかを決める。
1. 冒頭に判定（Go / No-go / 条件付き Go）と確度を書く。条件付きなら条件を確かめられる形で書く
2. 成功の基準を先に決め、基準ごとに、満たすか・満たさないか・分からないかと、確かめ方を書く
3. 確かめた深さ（動かした・ドキュメント・似た例・推測）を基準ごとに書き、混ぜない
4. 阻むものを、技術・環境と規約・費用と期間に分けて書く
5. 分からないことごとに、確かめる最小の手と手間を書く
「できる」と「やるべき」を分け、この報告では「できる」に答える。
```

## 確かめ方

- 判定と、基準ごとの結果が食い違っていないか（分からない基準があるのに Go にしていないか）
- 「動かして確かめた」と書いた基準に、動かした手順か結果があるか

## よくある失敗

- ドキュメントに書いてあるだけで「できる」と判定する
- 判定を保留し、何が分かれば判定できるかを書かない
- 「やるべきか」の意見が判定に混ざる

## 根拠

- 技術がどこまで実証されたかを段階で表す（R2）
- 決められないときは、何が決まれば決められるかを結論にする（write-for-reader の段階 2・3）
