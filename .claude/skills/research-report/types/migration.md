# 型: 移行・アップグレードの調査（`migration`）

## 目的

読み手が、移行するか・いつ・どの手順でするかを承認し、移行で直す箇所を漏れなく知る。

- 使う: 依存・言語・フレームワーク・サービスの版を上げる、別のものに乗り換える
- 使わない: 乗り換え先を選ぶ段階なら [tech-selection](tech-selection.md)。自分のコードの変更の影響なら [impact-analysis](impact-analysis.md)

## 既定

| 読み手 | 段階 | 語彙の層 | 寿命 |
|---|---|---|---|
| 両方 | 3 と 4（冒頭と手順は 3、Breaking Change の全件は 4） | 技術（全件はコード） | 一度読む |

## 冒頭の結論の形

```
推奨: <移行する・今はしない・<条件>まで待つ>。理由: <1〜2 個>。
Breaking Change <N> 件のうち、このコードに当たるもの <M> 件。最も手間がかかるもの: <1 つ>。
```

## 必須の節

1. **今と移行先**: 今の版、移行先の版、間の版。サポートの終了日
2. **移行する理由としない理由**: 移行で得るもの（修正、機能、サポート）と、しないことのリスク
3. **Breaking Change の全件**: 件ごとに同じ項目（変更・このコードに当たるか・当たる場所・対応・手間）。当たらないものも「当たらない」と書く
4. **非推奨になったもの**: 今は動くが、次で消えるもの
5. **手順**: 順番、途中で止めて確かめる所、戻し方
6. **見ていない範囲**: 間接の依存、実行時にしか分からない変更

## 語彙と粒度

- Breaking Change・追加・修正・非推奨を分けて書く
- 各件の出典は、公式の移行ガイド・CHANGELOG の節で書く
- 「当たる場所」は `file:line` か、検索の条件と件数で書く

## 省くもの

- 新しい版の追加機能の紹介（移行の理由になるものだけを書く）
- 当たらない変更の詳しい説明（「当たらない」と理由 1 語でよい）

## 書くときの指示

```
読み手は、冒頭と手順を読んで移行を承認し、全件の表で直す箇所を確かめる。
1. 冒頭に、推奨（する・しない・待つ）と理由、Breaking Change の件数と当たる件数、最も手間のかかるものを書く
2. 移行で得るものと、しないことのリスクを書く
3. Breaking Change を全件、同じ項目（変更・当たるか・場所・対応・手間）で書く。当たらないものも書く
4. 非推奨になったものを分けて書く
5. 手順に、途中で確かめる所と戻し方を書く
出典は公式の移行ガイドと CHANGELOG の節で書く。
```

## 確かめ方

- 移行ガイドの Breaking Change の件数と、表の件数が一致するか
- 間の版（飛ばす版）の変更も含めたか

## よくある失敗

- 移行先の版の変更だけを見て、間の版の Breaking Change を落とす
- 「当たらない」と判断した理由を書かない
- 戻し方がない

## 根拠

- 互換性を壊す変更・追加・修正・非推奨を分ける（R7）
- 決める節と確かめる節で段階を混ぜる（write-for-reader の段階の選び方）。決定の要因を先に挙げる（R1）
