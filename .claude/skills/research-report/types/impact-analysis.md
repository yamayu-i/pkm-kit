# 型: 変更の影響範囲（`impact-analysis`）

## 目的

読み手が、ある変更で影響を受ける箇所を漏れなく知り、変更の可否と工数を見積もる。

- 使う: 関数・API・スキーマ・設定・依存を変えるとき、どこを直す必要があるか
- 使わない: 外部の製品の版を上げるなら [migration](migration.md)（影響範囲の節はこの型の形で書く）。コードの全体を知りたいなら [codebase-map](codebase-map.md)

## 既定

| 読み手 | 段階 | 語彙の層 | 寿命 |
|---|---|---|---|
| 両方 | 4 | コード | 一度読む |

## 冒頭の結論の形

```
<変更>で影響を受けるのは <件数> 箇所（直す必要あり <N>、確かめるだけ <M>）。
最も重いのは <箇所と理由>。見ていない範囲: <あれば>。
```

## 必須の節

1. **変更の起点**: 何を変えるか（ファイル・識別子・値）
2. **調べた範囲と方法**: 対象のディレクトリ、検索の条件（`grep` の式など）、たどった依存の深さ、見ていない範囲（生成コード、別のリポジトリ、動的な呼び出し）
3. **影響の全件の表**: 件ごとに同じ項目（場所・どう影響するか・重さ・対応・テストの有無）。重さの順
4. **分類ごとの結果**: コード、テスト、設定、文書、データ、外部の利用者。0 件の分類は「なし」と書く
5. **見積もり**: 直す件数と、手間のかかる件

## 語彙と粒度

- 場所は `file:line` で書く。件はまとめてよいが、まとめた件数と場所をすべて書く
- 重さの基準を書く（例: 壊れる ＞ 振る舞いが変わる ＞ 文言だけ）
- 動的な呼び出し・文字列での参照など、検索で拾えないものがありうる所は「拾えない可能性」と書く

## 省くもの

- 「主なもの」に絞ること。絞るとこの型は成り立たない
- 影響のない箇所の説明（分類の「なし」だけでよい）

## 書くときの指示

```
読み手は、これで影響を受ける箇所を漏れなく確かめる。見落としは長さより高くつく。
1. 検索・依存の追跡を機械で行い、全件の一覧を先に作る。使った条件を書く
2. 冒頭に、件数（直す・確かめるだけ）、最も重いもの、見ていない範囲を書く
3. 全件を重さの順に、件ごとに同じ項目（場所・影響・重さ・対応・テストの有無）で書く
4. 分類（コード・テスト・設定・文書・データ・外部の利用者）ごとに結果を書き、0 件は「なし」と書く
5. 検索で拾えない参照がありうる所を書く
```

## 確かめ方

- 検索の出力の件数と、表の件数が一致するか
- 起点の識別子の別名（再エクスポート、文字列での参照）を検索に含めたか

## よくある失敗

- 検索の条件を書かず、どこまで見たかが分からない
- テスト・文書・設定を見ない
- 0 件の分類を書かない

## 根拠

- 変更の起点から依存をたどり、推定の範囲と方法を示す（R5）
- 全件を同じ項目で、0 件の分類も書く（write-for-reader の段階 4、E7）
