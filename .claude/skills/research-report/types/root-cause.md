# 型: 不具合の原因調査（`root-cause`）

## 目的

読み手が、不具合の原因を知り、直し方を選ぶ（または直す）。

- 使う: 壊れた・期待どおりに動かない・検査が落ちる、の原因を調べる
- 使わない: 遅い・重いなら [performance-cost](performance-cost.md)。直したときの影響の全件が主なら [impact-analysis](impact-analysis.md) を混ぜる

## 既定

| 読み手 | 段階 | 語彙の層 | 寿命 |
|---|---|---|---|
| 人 | 3 | コード | 一度読む |

## 冒頭の結論の形

```
原因: <1 文>（確度: 確かめた・推測）。場所: <file:line>。
推奨する直し方: <1 つ>。副作用: <あれば>。
```

## 必須の節

1. **症状**: 何が起きたか（期待と実際）、いつから、どの環境で
2. **再現手順**: 読み手が同じ手で再現できる最小の手順。再現できなかったらそう書く
3. **原因**: 直接の現象・引き金・根本の原因を分けて書く
4. **証拠**: ログ、差分、`git bisect` の結果、試した入力。原因を支える順に
5. **否定した仮説**: 調べて違った仮説と、違うと分かった理由
6. **直し方の候補**: 候補ごとに、直る範囲・副作用・手間。推奨を 1 つ
7. **再発を防ぐもの**: テスト、検査、型。あれば

## 語彙と粒度

- 「原因」と「引き金」と「直接の現象」を分ける（例: 現象は null の参照、引き金は空のファイル、原因は読み込みの失敗を捨てていたこと）
- 確度を、原因の段ごとに書く。根本の原因が推測なら、そう書く
- 人を責める言葉を使わない。何がそれを起こしうる作りだったかを書く

## 省くもの

- 調べた順の時系列（否定した仮説に要点だけを残す）
- 直し方の候補の実装の全文（差分の要点か、場所と方針で足りる）

## 書くときの指示

```
読み手は、これを読んで直し方を選ぶ。
1. 冒頭に、原因（確度付き）、場所、推奨する直し方と副作用を書く
2. 症状は期待と実際の差で書き、再現手順を最小の形で書く
3. 原因を、直接の現象・引き金・根本の原因に分ける
4. 原因を支える証拠を、ログ・差分・試した入力で示す
5. 否定した仮説を、違うと分かった理由とともに 1 行ずつ書く
6. 直し方の候補ごとに、直る範囲・副作用・手間を書き、推奨を 1 つ選ぶ
調べた順に書かない。
```

## 確かめ方

- 再現手順で本当に再現するか（できるなら自分でもう一度通す）
- 推奨する直し方で、症状の全部が説明できるか（原因で説明できない症状が残っていないか）

## よくある失敗

- 引き金を原因と書き、直しても別の入力で再発する
- 調べた順に書き、原因が最後に来る
- 再現できていないのに、確かめたように書く

## 根拠

- 影響・根本原因・引き金・対応を分け、責める言葉を使わない（R4）
- 結論を先に、理由を下に置く（write-for-reader の E17）
