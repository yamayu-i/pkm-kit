# 型: 技術選定（`tech-selection`）

## 目的

読み手が、候補の中から採用するものを 1 つ選ぶ。

- 使う: ライブラリ・サービス・方式・ツールの比較と選定
- 使わない: 候補が 1 つで「使えるか」を問うなら [feasibility](feasibility.md)。他でどうしているかを広く見るだけなら [landscape](landscape.md)

## 既定

| 読み手 | 段階 | 語彙の層 | 寿命 |
|---|---|---|---|
| 両方 | 3 | 技術 | 一度読む（決めた結果は ADR に残す） |

## 冒頭の結論の形

```
推奨: <候補>。決め手は <評価軸で 1〜2 個>。
<推奨を選ばない理由になりうるもの 1 つ>。戻すときの費用: <小・中・大と理由>。
```

## 必須の節

1. **要件と評価軸**: 依頼と制約から導いた軸。軸ごとに重み（必須・重い・軽い）を付ける。必須の軸を満たさない候補は比較の前に外す
2. **比較の表**: 行が候補、列が評価軸。候補は 2〜4 個。セルは数か短い事実で書き、評価の言葉（「優秀」）を書かない
3. **推奨と理由**: 決め手になった軸と、トレードオフ（推奨で失うもの）
4. **却下した候補**: 候補ごとに理由を 1 行
5. **リスクと戻し方**: ロックイン、乗り換えの手間、保守が止まったときの影響
6. **確かめていないこと**: 試していない・資料だけで判断した軸

## 語彙と粒度

- 成熟度・保守の状況は数で書く: 最終リリースの日付、リリースの頻度、未対応の Issue の数、メンテナの数、ダウンロード数
- ライセンス、対応する実行環境（バージョン）、依存の数は事実で書く
- 「人気がある」「モダン」「軽量」は使わない。何と比べてどれだけかを書く

## 省くもの

- 各候補の機能をすべて並べること。評価軸に関係する機能だけを書く
- 候補の歴史、作者の紹介
- 要件と関係のない軸（「GitHub の Star が多い」は、要件が保守の継続性なら代わりに保守の数で書く）

## 書くときの指示

```
読み手は、これを読んで候補から 1 つを選ぶ。
1. 冒頭に推奨と決め手（評価軸）を書き、推奨を選ばない理由になりうるものを 1 つ添える
2. 評価軸を要件から導き、重みを付ける。必須の軸を満たさない候補は比較の前に外し、外した理由を書く
3. 候補を同じ軸で並べた表にする。セルには数か事実を書き、評価の言葉を書かない
4. 却下した候補には理由を 1 行ずつ付ける
5. ロックインと戻すときの費用を書く
6. 試していない・資料だけで判断した軸を「確かめていないこと」に書く
```

## 確かめ方

- 表のすべてのセルに出典か確かめ方があるか
- 推奨の決め手の軸で、推奨が本当にほかの候補より上か（表と推奨が食い違っていないか）
- 必須の軸を満たさない候補が、表に残っていないか

## よくある失敗

- 候補を 6 個以上並べ、どれも浅くなる
- 評価軸が後付けで、推奨に有利な軸だけになっている
- 推奨を書かず、「用途によります」で終わる

## 根拠

- 決定の要因を先に挙げ、選択肢を同じ要因で比べる（R1）
- 判断を変えうるもの（リスク、戻し方）は本文に書く（write-for-reader の段階 3、E4）
