# 型の選び方

調査の型は、**読み手が報告を読んだ後に何をするか**と、**冒頭に置く結論の形**で選ぶ。調べた対象（ライブラリ、コード、仕様）では選ばない。同じライブラリでも、「どれを使うか」なら技術選定、「使えるか」ならフィジビリティ調査になる。

## 決め方

1. **依頼に型の名前か、それと分かる言葉があれば、その型にする**

   | 依頼の言葉（例） | 型 |
   |---|---|
   | どれを使うべきか、比較して、選定して | `tech-selection` |
   | できるか、実現できるか、やれそうか | `feasibility` |
   | このコードを理解したい、構成を教えて、どこに何があるか | `codebase-map` |
   | 変えたらどこに影響するか、どこを直せばよいか | `impact-analysis` |
   | なぜ壊れたか、原因を調べて | `root-cause` |
   | 本当か、仕様ではどうなっているか、〜できる？（事実を問う） | `fact-check` |
   | 何があるか、他ではどうしているか、最近の動向 | `landscape` |
   | 上げたい、乗り換えたい、移行したい | `migration` |
   | 漏れなく確かめて、点検して、監査して | `audit` |
   | 遅い、重い、高い、費用を見積もって | `performance-cost` |
   | 調べたうえで作業に渡す（サブエージェント・次のセッション） | `handoff` |
   | 仕組みを分かりたい、〜とは何か | `concept` |

2. **なければ推定する**: 「読み手は読んだ後に何をするか」に答え、[型の一覧](SKILL.md#型の一覧)の「読んだ後にすること」で選ぶ
3. **推定したら冒頭で明示する**: 報告の冒頭に `型: 技術選定（段階 3）` を 1 行書く。形式の質問（[出力先と形式](SKILL.md#出力先と形式)）をするなら、そこで型の推定も伝える。違えば、ユーザーはそれを言い直すだけで直せる
4. **上げ下げ**: 段階の上げ下げは write-for-reader の[段階の選び方](../write-for-reader/select-stage.md#上げ下げ)に従う。型は変えずに段階だけを動かしてよい（例: 「全部」と言われた影響範囲は 4 のまま、要点だけと言われた技術選定は 2 に下げる）

## 混ぜる

1 つの調査が複数の型に当たるときは、節ごとに型を決める。

- 主な型は、読み手が最初に読む節の型。冒頭の結論はその型の形にする
- ほかの型の節は、その型の「必須の節」だけを使う。冒頭の結論は 1 つにする
- よくある組み合わせ
  - 技術選定 ＋ フィジビリティ調査: 推奨の候補が実現できるかを、候補ごとの節に入れる
  - 不具合の原因調査 ＋ 変更の影響範囲: 直し方の推奨の後に、直したときの影響範囲の全件を置く
  - 移行の調査: もともと 3（移行するか）と 4（Breaking Change の全件）を混ぜる型

3 つ以上の型が混ざるなら、調査を分けられないかを先に考える。読み手がすることが 2 つ以上あるので、報告を分けたほうが決めやすい。

## どれにも当たらないとき

- 型を使わずに、write-for-reader だけで書く。出力先と形式は、このスキルの[出力先と形式](SKILL.md#出力先と形式)に従う
- 記録の `--kind` は `調査報告: 型なし（<依頼の種類を短く>）` にする
- 同じ種類の「型なし」が 2 回続いたら、型を足す候補として [maintaining.md](maintaining.md) の手順で記録する

## よくある誤り

- **対象で選ぶ**: 「ライブラリの調査だから技術選定」としない。読み手が選ぶのでなければ技術選定ではない
- **全部を技術選定にする**: 候補が 1 つしかないなら、選ぶことはない。フィジビリティ調査か事実の確認
- **推定を黙る**: 型を推定したのに冒頭に書かないと、読み手は書き方が違う理由が分からない
