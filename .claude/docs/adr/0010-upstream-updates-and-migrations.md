# ADR-0010: 上流の更新は merge と移行で取り込み、Breaking Change は AI が移行する

- 状態: 提案
- 日付: 2026-11-02
- 前提: [ADR-0009](0009-upstream-and-child-vaults.md)（上流と子の 2 層）

## 背景

子は `upstream/main` を merge して、上流の更新を取り込む（ADR-0009）。上流のもののファイルは、merge だけで新しくなる。

一方で、上流の変更が子のものに手を入れる必要を生むことがある。例を挙げる。

- frontmatter の項目の改名
- テンプレートの重ね合わせで、子が上書きしているテンプレートへの、新しい必須の項目の追加
- `.obsidian/*.json` の必要なキーの追加
- ノートの置き場所の変更

後方互換は必須にしない。そのかわり、こうした変更を子の側で確実に追従できる仕組みが要る。

## 決定

### 1. 子のものに手を入れる上流の変更には、移行を付ける

移行は `.kit/migrations/NNNN-短い名前/` に置く。番号は上流の中で連番にする。

| ファイル | 必須か | 中身 |
|---|---|---|
| `migrate.mjs` | 必須 | 機械的にできる部分を行うスクリプト。依存なしの Node。何度実行しても結果が同じになるように書く。`--dry-run` で、何を変えるかだけを表示する |
| `check.mjs` | 必須 | 移行が終わった状態かを確かめる検査。終わっていなければ、残っているものを列挙して失敗する |
| `README.md` | 必須 | 何が変わったか、なぜか、スクリプトで扱えない場合に AI が何をするか |

- 子のものを変えない上流の変更（上流のもののファイルだけの変更）には、移行は要らない
- 判断が要る部分は AI に任せてよい。ただし、終わったかどうかは `check.mjs` で機械的に判定できなければならない。判定できない移行は、Breaking Change として出さない
- 移行は、DailyNote の本文の保護（CLAUDE.md のルール 3）を守る。本文を変える必要がある移行は作らない。frontmatter は対象にしてよい

### 2. 上流の CI で移行を試す

- `.kit/fixtures/` に、子を模した Vault を複数置く。たとえば、初期のまま、テンプレートを上書きしたもの、古い形式のノートが残ったものである
- 上流の CI は、各 fixture に対して、未適用の移行の `migrate.mjs` を順に実行する。続けて、`check.mjs` と、子の `verify.mjs` に相当する検査が通るかを確かめる
- 2 回目の実行で何も変わらないことも確かめる

### 3. 子は `vault-upgrade` のスキルで取り込む

子向けのハーネスに、スキル `vault-upgrade` を置く。手順は次のとおり。

1. ブランチを切って `upstream/main` を fetch し、merge する。衝突したら、ADR-0009 の境界に従って解く。上流のものは上流の版を採る。子のものが衝突した場合は境界の違反なので、上流に報告する（[ADR-0011](0011-harness-parent-and-child.md)）
2. `.kit-local/upstream.json` に記録した適用済みの番号を見て、未適用の移行を番号の順に実行する
   - まず `migrate.mjs` を実行する
   - `check.mjs` が失敗したら、`README.md` に従って AI が残りを直す
   - もう一度 `check.mjs` を実行する
3. すべての移行の `check.mjs`、`verify.mjs`、子の CI に相当する検査を通す
4. `.kit-local/upstream.json` に、取り込んだ上流のコミットと、適用した移行の番号を記録する
5. PR にする。本文には、取り込んだ上流の変更の要約、実行した移行、AI が判断して直した箇所を書く。マージはユーザーが行う

移行が `check.mjs` を通せず、AI でも直せない場合は、そこで止める。その場合は上流に報告する（[ADR-0011](0011-harness-parent-and-child.md)）。

### 4. 取り込みは定期的に提案する

- 子の SessionStart フックは、`upstream/main` に未取り込みのコミットがあれば知らせ、`vault-upgrade` を提案する（`harness-review` の期限の知らせと同じ形）
- GitHub Actions での無人の取り込み（定期的に merge と移行を行い、PR を出す）は、手動で何回か取り込んでから決める

### 5. 上流の変更の記録

- 上流は、ユーザーに見える変更と移行を、`.kit/CHANGELOG.md` に書く
- `vault-upgrade` はこれを読んで、PR の本文を書く

## 理由

- 移行を自然文だけにすると、子が増えるほど結果がばらつく。スクリプトと検査を必須にすれば、結果を確かめられる。終わったかどうかの判定が機械的なら、AI が判断する部分の結果も検証できる
- fixture で移行を試せば、Breaking Change が子で壊れるかどうかを上流の側で事前に確かめられる
- 取り込みをブランチと PR にすると、子の人が変更を確かめてから受け入れられる。モバイルは、マージされた後に pull するだけでよい

## 却下した案

- **移行を自然文の指示だけにする**: 書くのは簡単だが、終わったかどうかを確かめられない
- **後方互換を必須にする**: 仕組みを改善するたびに古い形式を残し続けることになり、上流が重くなる
- **最初から無人で取り込む**: 移行の質が分からないうちに、子の Vault が人の知らないうちに変わる
- **子のノートを上流の変更に合わせない（古い形式を読める範囲で放置する）**: プラグインが古い形式を読み続けなければならない。後方互換を必須にするのと同じになる

## 影響

- 上流で子のものに関わる変更をするときは、移行と fixture のテストを同じ PR に入れる。上流の dev のスキルと PR の観点に加える
- 子の SessionStart フックに、未取り込みの更新の知らせを足す。fetch にネットワークが要るので、失敗したら知らせを出さない
- 子のハーネスに `vault-upgrade` のスキルを足す
