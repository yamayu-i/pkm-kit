# ADR-0011: ハーネスを親と子に分け、子で見つけた上流の改善はエスカレーションする

- 状態: 提案
- 日付: 2026-11-02
- 前提: [ADR-0009](0009-upstream-and-child-vaults.md)（上流と子の 2 層）、[ADR-0010](0010-upstream-updates-and-migrations.md)（更新の取り込みと移行）
- 置換: [ADR-0006](0006-self-improvement-loop.md) の評価の対象と出力の部分

## 背景

今のハーネスは一つで、次の 3 つを同じ改善のサイクル（ADR-0006: 気づきの記録 → 月 1 回の評価 → Issue）で扱っている。

- プラグインの開発
- LLM wiki の仕組み
- この Vault の使い方

上流と子に分けると、改善のサイクルが 2 つになる。

| | 何を良くするか | 観測できるもの |
|---|---|---|
| 親（上流） | 仕組みそのもの。プラグイン、子向けのハーネス、移行、セットアップ | 上流の開発中の気づき、CI の結果、移行の fixture の結果、子からの報告 |
| 子 | その Vault の使い方。子のテンプレート、子のスキル、子の CLAUDE.md | 子の作業中の気づき、`wiki/log.md`、`wiki/feedback.md`、git の履歴 |

子で見つかる問題には、子の中で直せるものと、上流を変えないと直らないものがある。たとえば、上流のスキルの誤り、プラグインの不具合、移行の失敗、重ね合わせで上書きできない箇所が後者である。後者を子が直接直すと、境界（ADR-0009）を破り、次の取り込みで衝突する。

また、子を持つ人ごとに、上流へ伝えられる手段が違う。上流の管理者本人なら Issue を立てられる。他人の子は GitHub を使わないかもしれないし、報告したくないかもしれない。

## 決定

### 1. ハーネスを 3 つに分ける

| ハーネス | 置き場所 | 所有 | 内容 |
|---|---|---|---|
| 子向け | `.claude/`（上流のもの） | 上流 | Vault を使う手順と、子の改善のサイクル |
| 子の追加 | `.claude/local/`、`.claude/skills/local-*`、`.claude/notes/` などの記録 | 子 | その子だけの規約・スキルと、子の記録 |
| 親 | `.kit/harness/` | 上流 | 上流を開発する手順と、親の改善のサイクル |

子向けのハーネスに含めるもの:

- 使う手順: wiki のスキル、task-coach、worklog-review、`vault-upgrade`（ADR-0010）
- 子の改善のサイクル: `harness-note`、`harness-review`（子の版）、`escalate`
- 子のものを変える工程: 子のテンプレートやスキルを変えるときの、小さな計画 → 実装 → PR
- 子の検査: `verify.mjs`（境界、ノートの書式、Obsidian の必要なキー）、子の CI

親のハーネスに含めるもの（`.kit/harness/` の下）:

- `CLAUDE.md`
- 上流の開発の工程: 今の dev-plan・dev-implement・dev-pr・dev-handoff を、上流の開発用にしたもの
- 移行の書き方
- プラグインのセキュリティチェック
- 親の改善のサイクル: `kit-note`、`kit-review`
- 上流の ADR（今のハーネスとプラグインの ADR）
- 親の記録: 気づき、評価、セキュリティのレポート

親のハーネスの読み込み方:

- 子向けの `.claude/CLAUDE.md` の冒頭に、次のように 1 行だけ書く。「上流の作業（`.kit/` や上流のものを変える）は `.kit/harness/CLAUDE.md` に従う。子の Vault では上流のものを変えず、`escalate` で報告する」
- 親のスキルは、Claude Code のスキルとして自動で読み込まれることを前提にしない。`.kit/harness/CLAUDE.md` から手順の文書としてリンクする。入れ子の `.claude/skills/` が自動で読み込まれることを確かめられたら、そちらに移してよい
- 親のハーネスは子にも merge で届くが、子では使わない。子の `harness-review` の対象にもしない

### 2. 子の改善のサイクル

ADR-0006 の 4 つの観測（git の履歴、気づき、`wiki/log.md`、`wiki/feedback.md`）を子で続ける。違うのは、出力を 2 つに振り分けることである。

```
子の作業 ──▶ harness-note（.claude/notes/）──┐
wiki/log.md・feedback.md・git の履歴 ────────┼─▶ 子の harness-review（月 1 回）─┬─▶ 子のもので直せる ─▶ 子の Issue ─▶ 子の工程で直す
vault-upgrade の失敗 ─────────────────────────┘                                 └─▶ 上流を変えないと直らない ─▶ escalate
```

振り分けの規則:

- **子で直す**: 子のもの（ADR-0009 の境界）だけを変えれば直る。またはその子の好みである
- **エスカレーションする**: 上流のものを変えないと直らない。またはどの子でも起きる
- 好みであっても、上流に上書きの手段がないせいで子で直せない場合は、好みそのものではなく「上書きの手段がほしい」ことをエスカレーションする

`harness-note` は、記録するときに「改善先」（子・上流・未定）を書く。上流で、かつ作業が止まるもの（移行の失敗、プラグインの不具合で使えない）は、月 1 回の評価を待たずに、その場で `escalate` を提案する。

### 3. 親の改善のサイクル

```
上流の開発 ──▶ kit-note（.kit/harness/notes/）──┐
子からのエスカレーション ──────────────────────┤
CI・移行の fixture の結果 ─────────────────────┼─▶ kit-review（月 1 回）─▶ 上流の Issue ─▶ 上流の工程で直す（必要なら移行を付ける）
Claude Code・Obsidian の更新 ─────────────────┘
```

- `kit-review` は、子からのエスカレーションを読んで振り分ける。受け入れる（上流の Issue にする）か、子で直せると返す（手段を示す）か、見送る（理由を返す）かを決める
- 結果はエスカレーションの経路で返す。Issue ならコメントと Close で返す
- 直した変更は、子の `vault-upgrade` で届く。子の `harness-review` は、エスカレーションした件が上流で閉じたかを確かめ、取り込み済みなら記録を消す

### 4. エスカレーションの方法は、子のセットアップのときに決める

`node .kit/setup.mjs` が方法を尋ね、`.kit-local/config.json` に書く。後から変えてもよい。

```json
{ "escalation": { "method": "issue", "repo": "<上流の owner/name>", "label": "escalation" } }
```

| method | 動き | 向いている子 |
|---|---|---|
| `issue` | 上流に GitHub の Issue を立てる。同じ件があれば、そこにコメントする | 上流の管理者本人や、GitHub を使う人 |
| `file` | `.kit-local/escalations/YYYY-MM-DD-<名前>.md` に書くだけ。上流に伝えるのは人が行う | GitHub に書きたくない人、ネットワークのない環境 |
| `none` | 子の評価のレポートに「上流の改善」として残すだけ | 上流に伝える必要がない人 |

`escalate` のスキルが守ること（方法によらない）:

- 送る内容に、個人のノートの内容、ファイル名、端末名、秘密情報を入れない。再現の手順は、汎用の例で書く。上流は公開なので、この規則は特に重要である
- 上流のどのファイル・スキル・移行に関わるかと、取り込んでいる上流のコミット（`.kit-local/upstream.json`）を必ず書く
- 送る前に、下書きをユーザーに見せて確認を得る（外に出す操作なので）
- `issue` のときは、先に上流の Issue を検索し、重複を避ける
- 送った件は `.kit-local/escalations.json` に記録する（方法、日付、Issue の番号かファイル名、元の気づき）。子の `harness-review` はこれを見て、状態を追う

### 5. 子の境界の違反は、直さずにエスカレーションする

子の作業の中で上流のものを変えたくなったら、変えずに `escalate` で報告する。子の `verify.mjs` は、上流のものが merge 以外で変わっていたら失敗にする（ADR-0009）。

急ぎで回避が要る場合は、上流のものは変えずに、子の追加（`local-*` など）で回避する。回避した件もエスカレーションに書く。

## 理由

- 子の改善と親の改善では、見るものと変えられるものが違う。同じサイクルにすると、子が上流のものを直接直して境界を破るか、上流の改善が子の評価の中に埋もれる
- エスカレーションを明示の経路にすると、子で見つけた問題が上流に届く。上流の判断も子に返る
- エスカレーションの方法を子ごとに選べるようにすると、上流の管理者本人の子と、他人の子の両方に対応できる
- 上流は公開なので、子から上流への経路で個人の情報が漏れないことを、スキルの規則で保つ

## 却下した案

- **ハーネスを一つのままにして、子でも上流のものを直してよいことにする**: 次の取り込みで衝突し、直した内容は他の子に届かない
- **子の気づきをすべて上流に送る**: 子の好みが上流に溜まる。個人の情報が漏れる危険も増える
- **親のハーネスを上流の `.claude/` に置く**: 子にも merge で届いて、子のセッションで有効になる。子で上流の開発の手順が動いてしまう
- **エスカレーションの方法を `issue` に固定する**: GitHub を使わない人、伝えたくない人の子に対応できない

## 影響

- 今の `.claude/` を、子向け（上流のもの）、子の追加、親（`.kit/harness/`）に振り分ける。振り分けの一覧は、上流を作るときの計画（ADR-0009 の 5）に入れる
  - 今の dev-* のスキル、security-check、`plugin-development.md`、ハーネスの ADR は、主に親に移す
  - wiki のスキル、task-coach、worklog-review、`harness-note`、`harness-review`、検査のスクリプトは、子向けにする
- この Vault（最初の子）のエスカレーションの方法は `issue` にする（上流の管理者本人なので）
- `harness-note` と `harness-review` に、改善先の振り分けを足す。新しいスキル `escalate`（子向け）、`kit-note`・`kit-review`（親）を作る
- 親の `kit-review` の期限を知らせる仕組みは、親のハーネスの中に置く。子の SessionStart フックは、子の `harness-review` の期限だけを知らせる
