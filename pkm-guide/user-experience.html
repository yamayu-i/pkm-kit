プロダクト

pkm-kit を使う人の体験に責任を持つための文書（ADR-0012）。誰のどんな場面のために、何を、どういう考え方で作るかを書く。

  • 人: 価値の最終判断と戦略の承認、どの機会を解くかの決定
  • Claude: 機会（困りごと）を自分で見つけて起票する（product-review）。場面・概念・今の体験の正本を保ち、全体の一貫性を点検する

使う人は、当面は本人だけ（戦略）。上流は公開なので、ここには個人のノートの内容を書かない。本人の使い方から分かったことは、一般的な場面として書く。

文書の種類

種類置き場所書くこと体験の層（Garrett）
戦略strategy.mdビジョン、使う人、望む成果、原則、やらないこと、当たり前の品質戦略
場面jobs/使う人の状況・したいこと・期待する結果と、今の流れ範囲
概念concepts/使う人が頭に置くもの（issue、Calendar など）の目的・状態・操作と、用語の対応表構造
今の体験の正本surfaces/画面・コマンド・MCP などの面ごとの、今の振る舞い構造・骨格
見た目デザインルール色・文字・部品・アクセシビリティ骨格・表面
機会GitHub の Issue（ラベル ux）場面、困りごと、根拠—

ADR は「なぜそう決めたか」の履歴で、書き換えない。surfaces/ は「今どうか」の正本で、振る舞いが変わるたびに書き換える。

育て方の規則

構成を変えずに大きくできるようにしている（ADR-0012 の 2）。

  • 1 単位 = 1 ファイル。増えるのはファイルの数で、既存のファイルを分割しない。1 単位が大きくなったら単位を分け、元のファイルは親の単位として短く残す
  • パスは変えない。ディレクトリの中はフラットにし、まとまりは各 README.md の一覧の見出しで表す。サブフォルダを作らない
  • ファイル名（slug）は英語の短い名前。領域を接頭辞にする（task-、note-、sync-、wiki-、kit-）。番号は振らない
  • 新しい種類が要るときは、ディレクトリと README.md を足し、上の表に 1 行足す
  • strategy.md は分けない。200 行を超えそうなら、絞れていない兆候として削る
  • 各種類の書式は、その種類の README.md にある。どのファイルも、その種類の README.md からリンクする（check-docs.mjs が、辿れないファイルとリンク切れを検査する）
  • 単位どうしは相対パスでリンクする（場面 → 面・概念、面 → 概念・場面・ADR）

いつ書き換えるか

きっかけ書き換えるもの
利用者に見える振る舞いを変える PR変えた面の surfaces/。概念や用語が変わるなら concepts/
新しい場面に応える機能を足すjobs/ に場面を足す
product-review歩き通しで見つけた食い違いを直す。機会を起票する
望む成果や原則を変えるstrategy.md（人が承認する）

子へ配布する HTML

正本の全文と実装の画面例を pkm-guide/user-experience.html に生成する。共通の HTML の構造はコードで作り、LLM は原本の意味のある差分だけを書く。更新は product-guide の手順 に従う。体験の変更時は定義書も更新し、verify で原本と生成物が一致することを確かめる。

戦略

pkm-kit が誰のために、何を目指すか。ここの判断は人が承認する（ADR-0012）。初版は、これまでの ADR と変更の記録から Claude が逆算して書いた。

ビジョン

考えたこと・やること・知ったことを 1 つの Vault に置き、一日の始まりと終わりを短く、迷わずに済ませられるようにする。どの端末でも同じことができ、データはずっと自分のファイルとして読める。

使う人

当面は本人だけ（ADR-0012）。他の人を含めるときは、このファイルと ADR を見直す。

使い方場所特徴
PCObsidian（広い画面。一覧ペインとノートペインを並べる）計画、整理、ノートを書く、wiki を育てる、開発
タブレットObsidianPC と同じく画面を分けられる
スマホObsidian（画面を分けない。ホバーがない）思いつきの捕捉、スキマ時間の整理、ボードの確認、同期
AI 経由Claude Code（task-coach、wiki のスキル、MCP）計画と振り返りの相談、wiki の取り込みと回答

AI を通した体験も、本人の体験として扱う。

望む成果

3 つまでにする。機会（ラベル ux の Issue）は、どれかの成果に結び付ける。

  1. 一日の計画と締めが、短く迷わず終わる: Today を開けば今日やることが揃っていて、終わりにはボードを締めて記録が残る（朝の計画、一日の締め）
  2. 思いついたこと・知ったことを取りこぼさず、後で見つけて使える: その場で置け、後で整理され、必要なときに引き出せる（思いつきの捕捉、スキマ時間の整理、wiki を育てる）
  3. どの端末でも、データを失わずに同じことができる（端末間の同期）

原則

判断に迷ったときの基準。機能の一覧ではない。

  • 正本は素のファイル: ノートは素の Markdown、タスクは frontmatter と jsonl。プラグインがなくても読め、git で差分が見える（ADR-0002、ADR-0007）
  • 決めることを減らす: 決まっていることは仕組みが行う（今日の予定を自動でボードに載せる、置き場所を覚える）。ただし、自動で行ったことは見えるようにし、手で戻せる（ADR-0034）
  • 間違えても戻せる: 操作は取り消せるか、後から直せる。見張って止めるより、後で直せるようにする（status の取り消し、worklog の見直し。ADR-0031）
  • 同じものは同じ名前で呼ぶ: 画面・データ・文書の用語は 概念 の対応表に従う
  • どの端末でも同じことができる: スマホでできない操作には、代わりの道を用意する（ホバーの代わりに「…」メニュー。ADR-0018）
  • 1 つの画面は 1 つの場面のために: 画面を増やす前に、どの場面のための画面かを書く（場面）

やらないこと

  • 他の人と共有する、一緒に作業する（チームのタスク管理）。委任先（member）は、自分が誰に任せたかを覚えておくためだけに持つ
  • コミュニティプラグインを使う（必要なものは自作する）
  • 作業を見張る（タイマーの止め忘れの警告や自動停止。ADR-0009）

当たり前の品質

ないと不満になるが、あっても満足は増えないもの（狩野モデル）。他の改善より先に守る。

  • 同期でデータを失わない（コンフリクトでも消さない。プラグインの設計と開発）
  • スマホで開けて、主な操作ができる
  • 文字が読め、押せ、キーボードで選べる（WCAG 2.2 AA。デザインルール）
  • 書いたノートの本文を、仕組みが勝手に書き換えない（ADR-0007）

体験定義と仕様を確認する

  • 端末: PC / スマホ
  • 望む成果: 1、2

ジョブ

何ができるかを知りたいとき、操作の意味や保存結果を確かめたいときに、今の体験と仕様を画面と並べて読みたい。

今の流れ

  1. ファイル一覧の pkm-guide/user-experience.html を開く（HTML の表示）。
  2. 最初は全体像を読み、したいことに合う場面へ進む。特定の画面や用語が分かっていれば目次から直接引く。
  3. 画面の開き方、入力と制約、操作後に保存されるもの、失敗時の戻し方を確かめる。
  4. 実装の画面例と説明を見比べる。追加の状態は折りたたみを開く。画像を押すと全体を開ける。
  5. 細かい決定の理由が必要なら根拠を開く。根拠のリンクは GitHub なので、オフラインでは定義書に収録した本文を参照する。

始める条件と期待する結果

上流のセットアップか更新を取り込んであり、PKM HTML が有効なこと。期待する結果は、どの画面で操作し、何が保存され、困ったときにどう戻すかを説明できること。

つまずいたとき

HTML が開けなければ PKM HTML の有効化を確認する。画像が欠けたら同期を完了させる。本文と画面の違いを見つけたら子のエスカレーションで上流へ伝える。子で定義書を直接修正しない。

関わる概念

ノートの type（定義書はノートではない）、同期と snapshot

うまくいっている兆し

  • 操作の結果を推測せず、定義書から確認できる。
  • 画面例と条件を見て、自分の現在の状態との違いが分かる。
  • スマホの幅でも本文と表を読める。

知られている困りごと

画面例は実装の部品と CSS を描画したプレビューであり、Obsidian 本体の枠や個別の端末を完全に再現するものではない。

端末を持ち替えても、同じ Vault で続ける

  • 端末: PC / スマホ
  • 望む成果: 3

ジョブ

PC とスマホを行き来するとき、どこで書いたものも失わずに続きから使いたい。どの端末で作業しても安心できるように。

今の流れ

  1. 書くだけでよい。画面を表示している間、戻ってきたとき、起動したときに自動で同期する（PKM Git）。急ぐときは Git: Sync
  2. 同期の区切りで、未コミットの変更が snapshot としてコミットされる。オフラインの間はコミットせず、つながったときに送る。コンフリクトしても止まらず、マーカーを残したまま同期する
  3. 送れたかどうかは、ステータスバーの Git: Synced / Not synced で分かる
  4. 残しておきたい版は Keep this version で名前を付けて残す

図（SVG・Mermaid）

  • 種類: 画面（図に浮かべる操作バー・拡大表示・縮めすぎの印）・コマンド
  • 開き方: ノートの図（asset/ の SVG の画像と、Mermaid の図）にマウスを載せる（タッチでは押す）。コマンド「Copy a diagram in this note」「Save a diagram in this note as PNG」「Expand a diagram in this note」「Export this note to tmp/ (embed diagrams)」。ファイルエクスプローラーの .svg の右クリック
  • 場面: ノートを書く

今の振る舞い

  • 図は Claude Code が内容に合わせて 3 つの方式で作る（スキル diagram、ADR-0102）: Mermaid（ノートのコードブロック）、D2（asset/*.d2 から asset/*.svg を描く）、SVG を直接書く（asset/*.svg）。色はデザイントークンから作った配色（ライト・ダーク）で、Mermaid はスニペット pkm-theme.css が、SVG と D2 は CLI（node .kit/bin/diagram.mjs の svg-style / d2）が付ける。CLI は描いた SVG の安全性・色・ノートの幅での文字の大きさも検査する
  • SVG の図は ![説明](asset/<名前>.svg) で参照する。表示は Obsidian の普通の画像の表示（プラグインを無効にしても見える）
  • 以前の Draw.io の図（asset/*.drawio.svg）も、普通の SVG の図として同じように扱う。編集する手段はない（直すなら 3 方式で描き直す。ADR-0111）
  • 図にマウスを載せると、右上に「Copy」「Save PNG」「Expand」が出る（Reading view と Live Preview の両方）。タッチでは図を押すと出て、ほかの場所を押すと消える。対象は Vault の SVG の図と、ノートの Mermaid の図。PNG・JPEG などの普通の画像には出ない
  • 「Copy」は PNG / SVG を選ぶ。SVG は、以前の Draw.io の図なら編集用 XML を除いたもの。画像として書けない環境ではテキストとしてコピーし、そう知らせる
  • PNG（コピーと保存）は、ノートをダークテーマで見ていても常にライトの色で、ライトの面の色を背景にする（貼り付け先の多くは白い背景）。2 倍の大きさ
  • 「Save PNG」は、PC では保存のダイアログ、モバイルでは共有シート（画像を保存・ファイルに保存など）を開く。どちらも使えなければ tmp/<図の名前>.png に書いて知らせる
  • ノートの中で縮めて出した図のいちばん小さい文字が 9px 未満になると、図の右下に「Expand to read」の印が出る（ペインを広げて読める大きさになれば消える）。印は押せない飾りで、拡大は操作バーの「Expand」で行う
  • 「Expand」は全画面に図を出す。ホイール・ピンチで拡大・縮小し、ドラッグで動かす。ボタンで縮小・拡大・全体を表示・100%。キーは 0（全体）・1（100%）・+ / -。ダブルクリックで 2 倍。画面の大きさが変わると全体を表示し直す
  • 「このノートを tmp/ に書き出す」は、md / html の asset/ の SVG の図の参照を、SVG の data URI に置き換えて tmp/<ファイル名> に書く（あれば番号を付けた別名。以前の Draw.io の図は編集用 XML を除く）。元のノートと図は変えない。見つからない図・壊れた図があれば何も書かない。コードブロックの中の例は変えない。Mermaid はコードブロックのまま残る
  • 同期（PKM Git）で両側が変えた SVG の図は行単位で混ぜず、リモート版と <名前> (conflict <端末> <日時>).svg を残す

PKM Git

  • 種類: コマンド・リボン・ステータスバー
  • 開き方: リボンの Git: Sync、コマンド「Sync now」「Keep this version」「Show sync log」「List unresolved conflicts」「Resolve conflicts in this note」「Show file history」（ファイルのメニューの Git: File history も）「Clone the remote into this vault (first time only)」。以前の「Pull」「Push (commit and send)」も同期になる
  • 場面: 端末間の同期

今の振る舞い

  • 自動で同期する。画面を表示している間は一定の間隔（既定 5 分。設定で変える。0 で止める）、戻ってきたとき、起動したとき。バックグラウンドでは同期しない
  • 1 回の同期で、取り込んでから送る。他の端末と送るのが重なったら、取り込み直して 3 回まで送る
  • Git のコミットは、同期でリモートに届いたときと「Keep this version」のときだけ作る。オフラインではコミットせず、つながったときに 1 つの snapshot にまとまる。変更したノートの updated は snapshot のときに入る
  • 保存のたびの細かな版は、Obsidian のコアプラグイン「ファイル回復」が端末内に持つ
  • clone は最新の版だけを取る。新しい端末の最初の clone は、履歴の長さによらず Vault の今の大きさだけを取る。その端末には clone より前の履歴がなく、古い版はほかの端末と GitHub にある（ADR-0106）
  • 分岐していればファイルごとに 3-way マージ。両側の変更が重なったら、Markdown とテキストはマーカーを入れ、それ以外はリモートを採って手元の版を (conflict <端末> <日時>) の名前で残す。削除と編集なら編集を残し、その記録（.pkm-git/conflicts/）をマージコミットに入れる。止まらずにマージコミットする。共通祖先が複数あれば、祖先によって違うファイルは衝突として両方を残す（ADR-0103）
  • ステータスバー: Git: Synced（共有済み）、Not synced（共有待ち）、Syncing…、Offline、Check connection（認証・接続先）、Sync failed。未解決のコンフリクトがあれば · ⚠ N。押すと一覧を開く。削除と編集の衝突の行には Keep（ファイルを残す）と Delete（ファイルを消す）があり、押すと記録を消して同期する。ファイルがもうない記録は自動で消える。マーカー入りのノートの行の Resolve は、衝突した箇所ごとに Use local / Use remote / Use both を選んで解く（開いた後に本文が変わっていたら書かない）。別名の版の行には Use this version（元のファイルをこの版にする）と Discard（別名の版を消す）がある（ADR-0110）
  • ファイルの履歴: そのファイルを変えたコミットを新しい順に、日時・端末・種類（Synced / Kept / Merged / Other）で出す。Preview で中身を見て、Restore で前の版に戻す。戻す前に今の内容を keep before restore としてコミットするので、戻したことも後から戻せる。最新の版だけを持つ端末では、Load older で 30 コミット分ずつ履歴を取り足す
  • 自動の同期では、成功とオフラインでは通知しない。新しいコンフリクトと、接続の確認（起動から 1 回）は通知する
  • 取り込みの途中でアプリが終わっても、次の同期の始めに続きから直す
  • 失敗と自動の回復は、端末ごとに .git/pkm-git/log.jsonl に残る。「Show sync log」で見て、コピーできる
  • スマホでも動く。トークンは SecretStorage に置く

使う概念

同期と snapshot

根拠

プラグインの設計と開発、ADR-0028、ADR-0089

入力と制約

remote は HTTPS。トークンは許可したホストにだけ送り SecretStorage に置きます。自動同期間隔は分単位で、0 は停止、既定は 5 分です。

取り込み後に送信し、重なれば最大 3 回まで再試行します。衝突でも両方の内容を残します。Restore の前には現在の内容を keep before restore としてコミットします。

失敗時と戻し方

Offline は接続後に再同期します。Check connection では認証と接続先を確認します。マーカーの衝突は箇所ごとに選び、開いた後に変更されていたら書きません。同期ログと履歴で結果を確認します。

端末の違い

PC とスマホのどちらでも同期できます。バックグラウンドでは同期しません。SecretStorage と端末名は各端末で設定し、ログも端末内に残ります。

MCP と task-coach

  • 種類: MCP・手順（AI 経由）
  • 開き方: Claude Code で task-coach のスキルを使う（「今日の計画を立てたい」「振り返りをしたい」など）。worklog の見直しは worklog-review
  • 場面: 朝の計画、一日の締め、週の見直し、作業しながら残す

今の振る舞い

  • MCP サーバー pkm（.kit/bin/mcp.mjs。Vault ルートの .mcp.json で登録する）が、ツールを群の接頭辞で分けて公開する。--toolset で群を選べる
    • task_: ボード・issue・worklog・routine を読み、検査を通して書く。AI の書き込みは端末名 ai の記録に入る。旧名（接頭辞なし）も 1 版のあいだ呼べる
    • note_ / daily_ / wiki_: ノートの検索（単純一致。全角・半角、カタカナ・ひらがなの違いを無視）、取得、一覧、リンク、デイリーノート、wiki の目次と記録、未取り込みの元資料（読み取りだけ）
    • check_: ノートの書式とタスク管理のデータの検査、改名の候補
    • meta_feedback: 足りなかったことを AI が記録する
  • 起動中は索引をメモリに持ち、変わったファイルだけを読み直す。一覧は既定 20 件で、task_get_overview の問題と停滞は上位 5 件と件数
  • 使われ方を .claude/mcp-log/ に記録する（呼び出し、MCP を通さないノートの読み書き、フィードバック。本文は残さない）。harness-review が usage-report.mjs の集計を読み、上流で直すものを escalate する
  • 把握: 今日の負荷（未完了の estimated の合計と、使える時間。既定 240 分）、期限切れ・期限が近い、Inbox の件数、締めていないボード、記録中のタイマー、持ち越し常連、停滞、見積もりの精度
  • 介入: ボードの操作（載せる・外す・★ を付ける・並べ替える。サブイシューも合成キーで扱う）、持ち越し、締める、issue の作成と更新、タイマー、デイリーノートの末尾への追記
  • task-coach は朝・日中・夕・週次の進め方を持ち、まとめて変えるときは対象を示して確かめてから行う
  • AI からの status の変更には、取り消しのトーストは出ない

使う概念

task board、estimated と実績、worklog とタイマー、デイリーノート

根拠

ADR-0025、ADR-0156、ADR-0031、子向けの task-coach（.claude/skills/task-coach/SKILL.md）

入力と制約

タスクは ID、サブは親 ID と sub の ID の組で指定します。依頼の曖昧な日付や作業の 1 日を、勝手に Calendar や 24 時間へ変換しません。

操作と保存

AI は MCP のツールで素のファイルを読み書きします。相談の提案だけでは保存されず、選択した操作で初めて状態が変わります。

失敗時と戻し方

エラーの対象 ID・不正なフィールド・不足の条件を確認します。曖昧な依頼は対象と期待する結果を明らかにし、結果を読み直して重複操作を防ぎます。

端末の違い

Claude Code の PC 上の操作です。スマホからは Obsidian の対応する画面で同じ正本を使います。

操作の例

「今日の残りを確認して、次にやる 2 件を相談したい」と頼む。AI は get_overview と get_board で状況を読み、提案する。選んだ後に add_to_board で載せ、get_board で結果を確認する。相談しただけでは Calendar の日を書かない。

存在しない ID で get_issue を呼んだ場合は、list_issues で対象を調べ直す。create_issue を繰り返す前には Inbox を読み、すでに作ったものを重複して作らない。

画面例: AI の操作面です。本文に依頼・入力・結果の例を記します。

Tasks Now

  • 種類: ダイアログ
  • 開き方: リボンの Tasks Now、コマンド「Tasks Now」
  • 場面: 作業しながら残す

今の振る舞い

現在の日時、PKM State（最後に整理してからの時間、worklog が止まっている時間、連続して記録している時間）、記録中のタスク群、今日の残りのタスクを表示します。値がない場合は経過時間を断定せず「–」を出します。

  • Running の Pause は群を再開するために保持し、Stop は群を破棄します。
  • Paused の Resume は保持した群を再開し、Discard は保持だけを捨てます。
  • 各行の再生／停止はそのタスクだけに作用します。
  • Space は一時停止／再開、Shift+Space は停止／保持した群の破棄です。入力欄では発動しません。
  • 操作中は群の操作を無効にし、失敗は通知で知らせます。

使う概念

worklog とタイマー、task board

根拠

ADR-0154

入力と制約

経過時間は保存済みの整理・worklog と現在時刻から計算します。まだ記録がない項目は値なしの表示になります。

操作と保存

Pause は群のログを止めて、この端末の設定に再開対象を残します。Stop はログを止めて群を破棄します。Resume は保持した群の記録を新しく開始し、Discard は群だけを捨てます。

失敗時と戻し方

保存中は群の操作を重ねられません。失敗は通知で知らせます。Pause 前までの worklog は残り、止めた時間帯を再開時に遡って記録しません。

端末の違い

PC とスマホで同じダイアログを使います。一時停止した群は端末ごとの設定で、端末間の共有を前提にしません。

実装の画面例

同時に記録中の群と PKM State を見ます。

操作と保存

Today

  • 種類: View
  • 開き方: リボンの「Open Today」、Tasks サイドバー、コマンド。一覧ペインに開く
  • 場面: 朝の計画、一日の締め

今の振る舞い

  • 段階を順に進む: Calendar → Previous boards → Pick → Board。件数のある段階を順に通り、「Next」で飛ばせる。手で選んだ段階は、片付くと次へ進む。上の段階表示は、今の段階だけ名前と件数を出し、ほかは番号（済みはチェック）の丸に縮める。残りがある段階には赤い点が付き、名前と件数はツールチップで分かる。丸を押すといつでも移れる
  • Calendar: 期限切れ（Overdue）・期限が近い（Due soon。3 日以内）は deadline と soft deadline の表が別々。操作は Add to today's board、Change Deadline / Change Soft Deadline、Tickler、Cancel、Inbox、行の編集。Missed（Calendar の日が過ぎて片付いていないもの）は Add to today's board、Move date、Back to Next、Close、Cancel、Inbox。どの表にもサブイシューが出て、同じ issue のサブは親の小さい見出し（ID と題）の下にまとまる
  • Previous boards: 締めていない過去のボードの未完了を、ボードの日付ごとに issue・サブイシュー・routine をまとめて出す。Add to today's board、Back to Next、Tickler、Move date（Calendar の日を持つものだけ）、Close、Cancel、Inbox で片付ける（サブイシューには Tickler と Inbox がない）。未完了がなくなった過去のボードは自動で締まる
  • Pick: Next（整理済みで、Calendar の日も Tickler もない open の issue）を priority → deadline → 見直しが古い順に出し、選んで今日のボードに載せる（日付は書かない）。Tickler・Someday・Cancel・Inbox もできる。サブイシュー（Calendar の日がなく、start が今日以前）は、親の小さい見出しの下に並べて「Add to board」で載せる。サブを持つ親は行に出さない
  • 開いているあいだ、今日が Calendar の日の issue とサブイシューを自動で今日のボードに載せる（その日に外したものは載せない）
  • 最後の段階は task board

使う概念

deadline と soft deadline、Calendar、Tickler、task board、Inbox

根拠

ADR-0009、ADR-0014、ADR-0018、ADR-0032、ADR-0034、ADR-0150、ADR-0152。段階表示を縮めたのは変更の記録（.kit/CHANGELOG.md の「Daily の段階表示を縮める」）

入力と制約

Calendar の日は必須の予定です。今日やりたいだけのものは Pick で選び、scheduled を書きません。

操作と保存

今日の予定と routine をボードに自動で載せます。同じ日に手で外したものは再追加しません。Pick は board の add 操作として記録されます。

失敗時と戻し方

前の日に未完了が残った場合は Previous boards へ戻り、日付変更・Next・完了等で片付けます。期限と作業日の意味を混同した場合は Calendar を直します。

端末の違い

同じ段階を PC とスマホで進めます。幅が狭くなると操作が折り返されます。AI には MCP から同じ状態を読ませます。

  • 1 つのモーダルで、テンプレートを選び、ファイル名（ID で決まるテンプレートではタイトル）と、テンプレートの追加の入力を入れる。作られるパスがその場で見える

PKM Updates

  • 種類: View
  • 開き方: リボンの「Open PKM Updates」、コマンド「Open PKM Updates」。一覧ペイン に開く
  • 場面: 朝の計画、端末間の同期、週の振り返り

今の振る舞い

  • 一覧 View ごとのセクションに、前回の確認より後に updated が新しくなったノートを、新しい順に出す。セクションは Issues、Inbox、Organize、Scheduled、Someday、Routines、Members、Daily notes、Notes、Sources の順。0 件のセクションは出さない
  • 各セクションに載るノートは、その一覧を開いたときに載るものと同じ。ただし Issues は closed / canceled / someday も含む（閉じた変更も見えるように）。1 つのノートが複数の一覧に当たるなら、そのすべてに出る
  • セクションの見出しを押すと、その一覧を一覧ペインに開く。行を押すとノートをノートペインに開く（Ctrl/Cmd+クリックで新しいタブ）
  • 50 行ずつ出し、下まで見ると次の 50 行が出る
  • 画面の下に固定した Viewed を押すと、その日時を記録してリストが空になる。記録は端末間で同期し、どの端末で押しても、最も新しいものが基準になる。端末名がない（pkm-task と pkm-git の設定のどちらにもない）と押せない
  • まだ一度も Viewed を押していなければ、updated があるノートをすべて出す
  • updated はコミットのときに付く。コミットしていない変更はまだ載らず、確認の前に書いて確認の後にコミットした変更は、もう一度載る

根拠

ADR-0070、ADR-0028、ADR-0033

入力と制約

見たはずのノートが再表示される場合は確認後にコミットされた変更かを確かめます。保存失敗の通知が出たら、端末名と同期状態を確認します。

同期と snapshot

目的

PC とスマホで同じ Vault を使い、どこで書いたものも失わない。Git の CLI を開かなくてよい。

状態

Vault は git のリポジトリ。各端末の PKM Git が、同期のたびに未コミットの変更を snapshot としてコミットし、main に送る。共有の状態は、共有済み（Synced）、共有待ち（Not synced）、オフライン、接続を確認、同期できない（Sync failed）のどれか。

操作

自動の同期（前景の一定の間隔、戻ってきたとき、起動）、Sync now、Keep this version、Show sync log、未解決のコンフリクトを一覧（コマンド・リボン・ステータスバー）して解く、ファイルの履歴を見て前の版に戻す。

使い方の筋道

書くだけでよい。同期の区切りで snapshot を取り、取り込んでから送る。オフラインの間はコミットせず、つながったときにまとめて 1 つにする。残しておきたい版は Keep this version で名前を付けてコミットする。保存のたびの細かな版はファイル回復にある。両方の端末で同じ行を変えると、マーカーを入れたまま同期し、止まらない。後で、一覧から箇所ごとにどちらを残すかを選んで解く。マーカーを入れられないファイルはリモート側を採り、手元の版を別名で残す。片方が消し、片方が編集したときは編集側を残し、その記録を全端末に届ける。一覧で残すか消すかを選ぶまで、件数に出続ける。ほかの端末で書いた版やしばらく前の版に戻すときは、ファイルの履歴から選ぶ（今の内容は先にコミットされる）。同期できないときは、内容を失わずに次の同期でやり直し、記録（Show sync log）に残す。

プラグインの設計と開発、ADR-0028、ADR-0089、ADR-0103、ADR-0110

目的

繰り返しの入力と判定

項目入力・既定値判定
everyday / week / month日・週・月単位
interval1 以上の整数。省略時 12 なら 2 日／週／月ごと
on（week）mon / tue / wed / thu / fri / sat / sun。1 つ以上必須指定した曜日
on（month）1〜31、last、2th-tue（2nd-tue も可）、last-fri 等。1 つ以上必須日、月末、第 1〜5 の曜日、最後の曜日

on は複数指定できる。月の 31 日や第 5 曜日が存在しない月は、その条件の回を作らず、月末に繰り上げない。interval は start を起点に数え、週の境界は月曜。起点より前は出さない。不正な every・interval・on は lint の問題として報告する。

例: repeat が every: week、interval: 2、on: [mon, thu] なら、起点を含む週から 2 週ごとの月曜と木曜。月末なら every: month、on: [last] とする。start を省いたときの起点は created の日付を使う。両方ともない場合は起点を決められず、ボードの予定に出ない。継続的に使うものは start を明示すると確認しやすい。

status

目的

やることが今どこにあるかを、1 つの値で表す。

状態

status: open / in-progress / waiting / delegated / someday / closed / canceled。それぞれに色と ○ を土台にしたアイコンがある。補足は status-detail（20 文字以内）。変化は statuslog/ に追記される（分析用。正本は frontmatter）。

操作

バッジのメニューで選ぶ。ボードのカードでは「次の status」ボタンで 1 クリックで進める。変えた直後は右下のトーストでまとめて取り消せる。

使い方の筋道

タイマーを始めると open は in-progress になる。closed か canceled にすると、記録中のタイマーが止まる。someday にすると Calendar の日・期限・Tickler が消える（Someday）。

サブイシュー

目的

1 つの成果に必要な行動を、別のノートを増やさず、親の issue の本文に持つ。

状態

親の issue ノートの末尾で、HTML コメントの sub-issue ブロックに項目、その後に本文を置く。ID は親の中で一意で、外からは親と ID の組（例: i-12#k3f9a2）で指定する。サブの下にサブは作らない。旧 parent の frontmatter で別 issue を結ぶ方式は使わない。

操作

使い方の筋道

成果を親の summary に書き、次に取れる行動をサブにする。実行したサブの worklog は親の ID と sub を持つ。親の実績には親への直接の時間とサブの時間を 1 回ずつ数え、二重計上しない。親の見積もりは全体の予算として扱う。

Tickler

目的

今は決めず、その日に思い出して整理し直したいもの（例: 返金が届いたか確かめる、更新するか考える）を、その日まで目から外しておく（GTD の Tickler）。その日にやらなければならない行動は Calendar で表す。

状態

tickler: 日付 1 つ。issue だけが持つ（サブイシューは整理の対象ではないので持たない）。整理の先送りなので、clarified は変えない。

操作

Organize の「Tickler」（↑。既定は明日）、Today の Pick と前のボードの「Tickler」、Inbox・Someday・Issues の一覧の「Tickler」、issue 画面の「tickler」、MCP の tickler と task_carry_issues の tickler。

使い方の筋道

日付の前は、Inbox・Next・Today の Pick・Organize のどこにも出ない（期限は Tickler があっても Today に出る）。日付が来ると Inbox に戻り、Organize で整理し直す。整理の操作（Next・Calendar・Someday・Cancel・Already done・Inbox に戻す）は tickler を消す。

worklog とタイマー

目的

いつ、どのやることに時間を使ったかを残す。

状態

worklog/<端末名>/YYYY-MM.jsonl に 1 行 1 件（task_id、サブなら sub、from、to、description）。記録中は to が空。書くのはその端末だけ。

操作

ボードのカードの再生 / 停止、サイドバーの停止、issue 画面での編集。間違ったログは worklog-review で直す。

使い方の筋道

再生するとログが始まり、停止すると終わる。止め忘れの警告や自動停止はしない（戦略）。closed か canceled にすると止まる。

根拠

ADR-0004、ADR-0014、ADR-0031

記録と再開

Tasks Now の Pause は現在のログを終え、この端末に群を保持する。Resume は新しいログを始める。停止していた時間を作業として埋めない。同時に複数のタスクを記録した区間の実績は、重なっていた数で配分し、実際の経過時間より総計が増えないようにする。
